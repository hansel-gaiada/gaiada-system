§00

Executive Summary

What we are building, why the render gateway exists as a second deployable, and the shape of the four locked decisions this design conforms to.

Creative becomes a platform-nest module vertical (ModuleContract key creative, tables creative_* — extending, not duplicating, the shipped creative_assets table from migrations 0031/0032) plus one new deployable, the Creative Render Gateway (render-gateway-go/, the mirror of ai-gateway-go for diffusion workloads), plus the expanded Creatives department console. Six moves shape the architecture:

1 · The only door to GPU compute

A typed render job is created as an RLS-scoped creative_render_jobs row, dispatched to the gateway, which routes it to the cheapest capable RenderBackend — serverless GPU, self-hosted headless ComfyUI, or commercial API — filtered by capability + license class + cost cap + scope + health. Platform-nest owns job state; the gateway owns GPU keys and holds no tenant data at rest.

2 · License discipline is structural

Every ComfyUI workflow is a versioned JSON artifact carrying a model manifest with license classes. The gateway stamps provenance; platform-nest computes an asset's license_class as the weakest link of its derivation chain; the reuse gate refuses any chain that isn't fully commercial/licensed. FLUX quality is reachable only through the premium tier. v1 ships zero non-commercial workflows enabled.

3 · DAM = the extended asset domain

Version stack, collections + brand kits, rights/licensing with expiry, provenance, CLIP embeddings → pgvector search + dedup, BLIP captions/auto-tags, and imgproxy as a stateless signed-URL rendition sidecar. Cross-dept consumers see approved assets only, through the module's BFF surface.

4 · Two gates, not one

The spend gate (per-client scope → ledger stop-loss chain client → tenant → global, fail-closed, WS4-suspended for automation and above-threshold/premium jobs) and the reuse gate (human WS4 approval promoting an asset to cross-dept/deliverable status, where the license chain is verified). Generative spend and generative publication are different risks.

5 · AI assist is local-first

Prompt expansion, tag normalization, and alt-text ride ai-gateway-go (Hermes default, Claude polish flag). Vision models run as analyze render jobs — CLIP + BLIP on a cheap CPU worker backend — deliberately not the gateway /embed, which is not CLIP-space. Retrieval-shaped RAG stays in WS8.

6 · The Magnific bleed stops in week one

Phase 0 is a 1-day spike onto clarity-upscaler via Replicate (~$0.019/run, ~10× cheaper than Magnific credits) before any platform code lands. Build order: P0 contracts → P1 upscale (Magnific kill) → P2 image generate/edit → P3 DAM search/tagging + cross-dept supply → P4 video. 27 tickets (CR-00–CR-26), /army-ready (§12).

The Magnific head-to-head (quality · quantity · price)

Apples-to-apples on Magnific's home turf — creative upscale/enhance (our stack also does gen/edit/video/DAM, not credited here):

  • Quality — parity for client work. clarity-upscaler is the open engine powering ClarityAI.co (same SDXL + ControlNet-Tile recipe, same "hallucinated detail" glow). SUPIR would exceed Magnific but is non-commercial → off-limits, so on the clean stack we match, not beat. Magnific keeps a "turnkey polish" edge until we tune presets.
  • Quantity — uncapped vs. credit-capped. Magnific: Pro ~500/mo, Premium ~1,500, Business ~5,000 credits. Ours: limited only by GPU budget/throughput. The same $39 buys ~500 Magnific upscales vs. ~2,000 on Replicate; on an owned box it's unlimited at ~$0 marginal.
  • Price + the seat point — the whole game. Magnific bills per account/seat with a credit cap. Our stack is a backend service the whole team hits via the platform (MCP-mediated) — cost is decoupled from headcount. Zero seats, one backend; billing is compute, not people.

§02

System Overview

All state, tenancy, judgment, and money controls live in Zone A. The Render Gateway is Zone-A infrastructure with egress-only GPU traffic; no inbound internet path exists to any of it.

Reading the diagram

  • All state, tenancy, judgment, and money controls live in Zone A. The Render Gateway is Zone A infrastructure with egress-only GPU traffic (allowlisted hosts, per-job audit of every byte of client pixels leaving — §03).
  • Bytes flow storage → gateway → backend → gateway → storage via short-lived signed URLs platform-nest issues per job; the gateway persists nothing tenant-owned.
  • imgproxy is a stateless sidecar reading the same storage, serving signed, on-the-fly renditions to the UI and to consuming departments.
  • No inbound internet path exists to any of it; commercial-API webhooks are not used — the gateway polls providers.

Domain Model & Schema

Every tenant table carries the third-wall RLS predicate; the render job is the state-machine spine; the extended asset row is the DAM.

Design rules (inherited, not optional)

  • Every tenant table: tenant_id uuid NOT NULL REFERENCES companies(id), origin_site, created_at/updated_at, soft-delete deleted_at where user-facing.
  • FORCE-RLS with the WSD-3 third wall — policy predicate tenant_id = ANY(app_current_tenants()) AND app_module_allowed('creative') on both USING and WITH CHECK, byte-identical in shape to 0028_module_hr.sql. App side reaches these tables only via withTenants(tenants, { modules: ['creative'] }).
  • Migration numbering — stated assumption: the module block starts at 0036_module_creative.sql (+ 0037 if a follow-up is needed). Basis: as of 2026-07-23 the ledger runs through 0035_integration_connections_search_providers.sql (the SEO design's "0034+" was drawn down by the search module). CR-01 takes the next unused number at merge time and coordinates with SMM-01 (which also targets next-unused) — whichever merges second rebases. No in-migration GRANTs; no sync_app grants (creative tables do not sync in v1).
  • Money: GPU/provider cost is numeric(12,6) USD (serverless unit prices go to fractions of a cent — same rationale as the SEO ledger). No client-facing money in this module's v1.

The two RLS decisions this module makes explicitly

  1. creative_workflows is global, no-RLS, admin-write-only — it holds pipeline definitions (workflow JSON + model manifests), zero client data; per-tenant duplication would fork the license source of truth. Same class of deliberate exemption as social_platform_apps (SMM D-4), narrower than SEO's search_data_cache.
  2. creative_assets (shipped with a plain tenant wall in 0031) is upgraded to the third wall in this module's migration, in lockstep with moving CreativeController into the module. The HTTP contract (/api/:t/creative/assets, used by the studio UI and creative-grading-trainer) is preserved as a stable alias; new surface lives under /api/:t/modules/creative/*. This is the one behavior change to shipped code and it ships atomically in CR-01+CR-02 (D-3).

§05

Creative Render Gateway

The centerpiece. A separate Go service — mirroring ai-gateway-go's key-custody, egress, and failure-isolation discipline, applied to GPU compute instead of LLM tokens.

Verdict and shape

A separate Go service, render-gateway-go/ (compose service render-gateway) — not a platform-nest in-process worker, for the same reasons ai-gateway-go is separate: key custody isolation (GPU provider keys never enter the platform process), egress-allowlist enforcement at the dialer, independent failure/restart behavior for long-running jobs, and Go's fitness for concurrent poll/stream workloads. Platform-nest stays the source of truth for job state; the gateway is a stateless-ish executor (in-flight leases in memory/Redis; crash ⇒ platform reconciler re-drives by lease timeout, idempotent on job_id).

Job lifecycle

States live on creative_render_jobs, not in the gateway:

  • Create (console button or MCP tool): platform-nest validates capability against the effective creative_scopes, resolves the workflow (key@version, must be active), computes the license floor (client-attributed job ⇒ commercial|licensed only), asks the gateway POST /estimate for cost, then runs the stop-loss chain (below). Outcome: queued, pending_approval, or refused.
  • Approval (spend gate): required when (a) the principal is an automation/agent OBO user — always, D14; (b) estimated_cost_usd > per_job_approval_threshold in scope; (c) the resolved route is a premium backend (BFL FLUX tier, commercial video API); or (d) capability class video for any non-human requester. Approved rows are one-shot: dispatch consumes approval_id transactionally, replay-proof.
  • Dispatch: platform-nest → POST /jobs on the gateway with the job envelope (capability, workflow + definition hash, params, signed input/output URLs, constraints, callback token). Idempotent on job_id. Gateway picks the backend (routing policy below) and leases the job.
  • Execute: backend-specific — serverless (submit, poll), ComfyUI (POST /prompt, ws/poll /history, fetch artifacts), commercial API (submit, poll). Progress callbacks are optional; terminal callback is mandatory and idempotent.
  • Callback: POST /api/internal/creative/render-callback — platform-nest verifies the per-job token, transitions the row (one-way), creates the output asset or version with provenance + computed license_class (weakest of the license stamp's models ∪ input assets' classes), true-ups the ledger row, emits creative.render.completed|failed, and enqueues an analyze job (fail-soft).
  • Reconciler: a periodic module task re-drives dispatched/running rows past lease_expires_at (GET /jobs/:id first; re-dispatch only for never-started jobs — mid-run failures fail closed to human retry, never silent re-spend).

The RenderBackend abstraction (gateway-side) and routing

RenderBackend routing

A cost-ordered, config-driven candidate list per capability (hot-reloadable like the bot's groups.yaml). At dispatch the router filters by capability ∧ license floor (a commercial floor excludes every non-commercial route and excludes licensed unless the scope has the premium tier) ∧ deny_cloud ∧ max_cost_usd ∧ circuit-breaker health, then takes the first.

Fail-closed stop-loss

(0) capability enabled in scope → (1) license floor satisfiable → (2) estimate ≤ cap, threshold/premium/automation ⇒ pending_approval → (3) month-to-date spend per cost class vs. client → tenant → global cap (image $200/mo, video $300/mo, analyze $10/mo defaults; also fires at 80%) → (4) advisory-lock single-flight per job id → dispatch → true-up on callback.

License wall

Every workflow's model manifest carries a license class; the router filters routes below the job's floor; the callback stamps the actual models used; an asset's license_class = weakest of the derivation chain. approve_reuse refuses any chain element ∉ {commercial, licensed}. There is no admin override.

// Design sketch — capability-based so drivers can be partial (SearchDataProvider's sibling).
type RenderBackend interface {
    Key() string                    // 'replicate' | 'fal' | 'runpod-serverless' | 'comfy-selfhost'
                                    // | 'bfl-api' | 'video-api' | 'analyze-cpu' | 'echo' (tests)
    Capabilities() []Capability
    // License class of what THIS backend runs for a given workflow/model — the router's filter input.
    LicenseClass(workflow WorkflowRef) LicenseClass   // commercial | licensed | noncommercial
    EstimateCostUsd(job JobSpec) (float64, error)     // consulted BEFORE dispatch (stop-loss + approval threshold)
    Submit(ctx context.Context, job JobSpec) (BackendRef, error)
    Poll(ctx context.Context, ref BackendRef) (JobUpdate, error)
    Cancel(ctx context.Context, ref BackendRef) error
}

Failover: pre-start errors (429/5xx before compute starts) advance to the next candidate; mid-run failures never failover (no double spend) — they fail the job with the backend's error for a human decision. Per-tenant concurrent-job caps and a global concurrency cap are gateway config.

ComfyUI workflows as versioned JSON

The unit of pipeline definition is a creative_workflows row: the exact ComfyUI graph JSON (or API template), a params schema (prompt, image refs, denoise, creativity/HDR sliders mapped to denoise-strength + ControlNet weight), and the model manifest with license classes. Platform-nest resolves key@version and sends the definition hash; the gateway verifies hash before execution (a tampered workflow refuses).

Seeded v1 set: upscale-clarity@1, upscale-precision@1, relight-iclight1@1, gen-qwen@1, gen-sdxl@1, gen-zimage@1, edit-qwen@1, bgremove-birefnet@1, analyze-clip-blip@1, t2v-wan22@1, i2v-wan22@1, flf2v-wan22@1, interp-rife@1, vupscale-esrgan@1; premium: gen-flux-bfl@1 (api engine). Quarantined-inactive (documentation of the boundary, not tribal knowledge): upscale-supir@0, relight-iclight2@0.

The ledger powers the Jobs & Usage panel, tenant rollups, and the creative.render_cost.month metric that feeds billing. Manual override = creative:provider:admin + audit.

Trust & Security

Nothing new to invent — every control reuses an existing platform mechanism, applied to GPU keys, generative pixels, and their license provenance.

Key custody

GPU/model provider keys (RunPod, fal, Replicate, BFL, Veo, Kling): render gateway env → OpenBao target-state; never in platform-nest, platform-ui, or n8n. Storage access: per-job signed URLs only. imgproxy signing key: imgproxy + platform-nest env.

RLS

All creative_* tenant tables: FORCE-RLS, third-wall predicate, fail-closed empty-set semantics. creative_assets policy upgraded in the same migration (D-3). The single exemption is creative_workflows (global, admin-write-only — D-4).

Cerbos resources

resource_creative_asset (read/write/set_rights/submit_reuse/approve_reuse/revoke_reuse), resource_creative_render_job (read/submit/submit_video/submit_premium/cancel), resource_creative_scope, resource_creative_ledger, resource_creative_workflow (platform-admin only).

License wall (structural)

Router filters routes below the job's license floor; callback stamps the actual models used; asset license_class = weakest of the derivation chain; approve_reuse and deliverable paths refuse any chain element ∉ {commercial, licensed}. No admin override exists.

Money safety

Single dispatch choke point (scope → license → estimate/approval → MTD caps per cost class → advisory-lock → dispatch → true-up); one-shot approvalId with payload-hash match; no cross-backend failover after compute starts; daily cr-ledger-guard as the independent watchdog.

Egress control + privacy

DialContext-enforced allowlist of backend hosts; per-job egress audit (tenant/client hashes, backend, bytes); opaque job ids in anything a provider sees; allow_cloud_gpu:false scope pins a client to self-host routes (OQ-5).

Untrusted compute

Outputs from any backend are size-capped, content-type-validated, and re-encoded on ingest; workflow definition hash verified before execution; callback token is per-job and single-purpose.

Audit

Ledger row per dispatch, Cerbos decision audit, hub JSONL for every MCP call, approvals decisions, egress audit lines — nothing new to invent.

Module permissions declared in the contract: creative:asset:read|write, creative:asset:approve_reuse, creative:render:submit, creative:render:video, creative:render:premium, creative:scope:write, creative:ledger:read, creative:provider:admin, creative:workflow:admin.
