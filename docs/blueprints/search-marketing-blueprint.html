§00

Executive Summary

What we are building, why it lives inside platform-nest rather than as adopted tools, and the shape of the decisions already locked.

Search-marketing becomes a platform-nest module vertical (ModuleContract key search, tables search_*) plus a department console on the dept-interface-template — the same shape as Web Dev, not a second UI bolted on top of somebody else's SaaS. The professional moat in this discipline is data, not workflow, so the architecture follows that truth end to end.

1 · Provider abstraction

SearchDataProvider drivers (DataForSEO primary, Semrush premium, free-scraper fallback) behind a Postgres cache and a per-client usage/cost ledger that enforces budget stop-losses before money is spent. A human sets which tools run at all, per client.

2 · Self-hosted crawlers

SEONaut, open-seo-crawler, and Unlighthouse run as job-mode workers — $0 API cost, egress-guarded, ingested into RLS-scoped search_audits. Their own UIs and auth are never exposed.

3 · Mine, don't run

open-seo and SerpBear are data-only references: retrofitting single-tenant apps with FORCE-RLS + Keycloak + Cerbos costs more than native implementation, and their UIs are redundant behind our console.

4 · Local-first AI

Hermes via ai-gateway-go handles bulk work (clustering, intent-tagging, triage, first drafts); Claude is reserved for client-facing polish only. GEO/brief RAG rides the existing WS8 knowledge store.

5 · WS4-gated, dual-mode execution

Everything touching a live site or live ad spend is approval-gated. Every live action ships as a manual twin (export, human applies, zero OAuth, P3) and an automated twin (API push behind WS4, P4, committed) — the human picks per action.

6 · GEO/AEO first-class

AI-visibility snapshots, extractability audits, and citation-oriented tooling ride the same entities and provider abstraction as SEO/SEM — enabled per client like every other paid pull, not a bolt-on premium tier.

Build order is cost-honest: P0 contracts → P1 $0-value (crawls + AI on own data) → P2 paid data (needs the $50 DataForSEO deposit) → P3 SEM planning/reports + manual-apply path → P4 live-ads OAuth writes (committed) + decision-gated extras. 26 tickets P0–P3 plus 2 committed P4 tickets, /army-ready (§13).

§01

Foundation & Cost Model

What SEO and SEM actually are, what clients pay for, the professional toolchain, and the locked provider-cost decision this design conforms to.

1.1 · Two disciplines, converging on a third

Both SEO and SEM are search marketing — capturing demand from people (and now AI answer engines) actively searching. They differ in how visibility is won and how fast.

SEO — organicSEM — paid (SEA)
MechanismEarn organic rankingsBuy placement via ad auctions
SpeedSlow — compounding asset over monthsInstant — traffic the day a campaign goes live
Cost shapeLabor-heavy, no per-click costMedia spend + management fee; stops when budget stops
DurabilityDurable asset that keeps payingRented traffic; ends with the budget
2026 framingThe modern view is not "free vs paid" — it's portfolio management of search intent across SERP formats and AI answer engines. A third discipline has emerged: GEO / AEO / LLMO — optimizing to be cited by ChatGPT, Google AI Overviews, Gemini, Claude, Perplexity. This design treats GEO/AEO as first-class, not an afterthought.

1.2 · What clients actually pay for

Clients don't buy rankings or clicks — they buy business outcomes. KPIs sit in four SEO buckets (visibility → traffic → engagement → outcome) and four SEM metrics (CPC, CTR, Quality Score, ROAS). The ERP must model this as an outcome-tracked engagement, not a task list — intake the goal, audit current state, execute, measure against a committed KPI, report the outcome.

DisciplinePrimary client outcomeTimeframe
SEODurable, compounding organic traffic → leads/revenue at falling CPA3–12 months
SEMImmediate qualified traffic at a controllable, predictable CPA/ROASDays
GEO/AEOBrand presence & citation inside AI answers — the new zero-click surfaceEmerging

1.3 · The professional stack — and the moat

A practical stack = Search Console + GA4 + one crawler + one research platform + one reporting layer + Google Ads for SEM. The commercial layer is where the real cost lives:

Key insightThe professional moat is data (SERP volumes, backlink index), not the UI. Open-source tools replicate the workflow; they still need a paid data API for volume/difficulty/backlink numbers. Our build = OSS workflow + pluggable data provider — never adopted external UIs.

1.5 · LOCKED decision — provider & cost model (2026-07-23)

ContextGaiada serves many smaller clients with variable needs from Indonesia; IDR/USD pressure means the stack must be cheapest-yet-professional. This decision is locked and this design does not relitigate it.

DataForSEO (Standard queue) is primary; Semrush MCP is an optional premium upsell, behind a pluggable provider abstraction. Rationale: pay-as-you-go maps to per-client billing with no dead subscription floor, and it's a data layer suited to build-it-yourself.

Cost-control levers

  1. AI bulk work → local Hermes; paid Claude reserved for client-facing polish only.
  2. Default DataForSEO Standard queue ($0.0006/SERP, ~5-min) — 3× cheaper than Live.
  3. Self-hosted crawlers do all audit/crawl/speed work — $0 API cost.
  4. Cache SERP/volume in Postgres — no re-querying the same keyword within a window.
  5. Meter per client in the ERP; one shared $50 DataForSEO deposit pool across all clients.

§03

System Overview

All state and judgment live in Zone A. Three arrows cross to the internet: crawler egress, provider API calls, and notification-only inbound webhooks.

Reading the diagram

  • Every arrow that touches money or a live site passes through platform-nest — there is no path where n8n, the UI, or an agent calls a provider or a client site directly.
  • Crawler egress is allowlisted per registered+verified property domain; provider calls use server-side keys only; inbound webhooks (DataForSEO postbacks, Ads-Scripts) are triggers only — the authoritative fetch always happens over the authenticated API.
  • Umami, which must receive public traffic, follows WebDesk doctrine and sits in Zone B; the ERP only ever pulls read-only summaries.

§05

Domain Model & Schema

Every tenant table carries the third-wall RLS predicate; the engagement is the outcome-tracked unit; the change-proposal is the dual-mode execution artifact.

Design rules (inherited, not optional)

  • Every tenant table: tenant_id uuid NOT NULL REFERENCES companies(id), origin_site, created_at/updated_at, soft-delete deleted_at where user-facing.
  • FORCE-RLS with the WSD-3 third wall — policy predicate tenant_id = ANY(app_current_tenants()) AND app_module_allowed('search') on both USING and WITH CHECK, byte-identical to 0028_module_hr.sql.
  • Migrations: next unused number (0034+ as of 2026-07-23); no in-migration GRANTs; no sync_app grants (search tables do not sync in v1).
  • Money: minor units bigint + currency for client-facing money (SEM budgets/spend); provider cost is numeric(12,6) USD (DataForSEO unit prices go to $0.00012).

The dual-mode execution artifact

search_change_proposals is the mechanism that makes every live-account action safe regardless of which twin executes it — a launch, pause, budget/bid change, negatives batch, or ads batch is always a row first:

CREATE TABLE search_change_proposals (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL REFERENCES companies(id),
  campaign_id uuid NOT NULL REFERENCES search_campaigns(id),
  kind text NOT NULL CHECK (kind IN
    ('launch','pause','budget','bid','negatives_batch','ads_batch')),
  payload jsonb NOT NULL,             -- the exact intended change (hashed for approval match)
  status text NOT NULL DEFAULT 'proposed'
    CHECK (status IN ('proposed','approved','applied','dismissed')),
  mode text NOT NULL DEFAULT 'manual' CHECK (mode IN ('manual','api')),
  approval_id uuid REFERENCES automation_approvals(id),  -- WS4 link (api mode; one-shot)
  export_file_id uuid REFERENCES files(id),   -- Ads-Editor-ready artifact (manual mode)
  proposed_by uuid REFERENCES users(id), approved_by uuid REFERENCES users(id),
  applied_by uuid REFERENCES users(id), applied_at timestamptz,
  origin_site text NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(), deleted_at timestamptz
);

Manual mode records who applied it in the ad platform (applied_by/applied_at, artifact attached); api mode executes only by consuming the one-shot approval (§08, §12). The human picks the mode per action — no approval, no API execution, including for humans in the console.

Custom fields & agency-vertical relations

  • D17 customFieldTargets: search_engagement, search_campaign.
  • Clients are the existing core clients rows — no duplicate client table.
  • Deliverables/time: reports link into core deliverables; hours log through the normal time_entries path against the optional project_id.
§06

Data-Provider Abstraction

The provider layer lives inside platform-nest — metering must be transactional with the ledger, RLS scoping is native, and no new deployable is created.

DataForSEO's async-queue model (Standard queue) posts a task and resolves by poll or postback-triggered fetch; live/sync providers resolve immediately. The interface is capability-based so drivers can be partial:

interface SearchDataProvider {
  key: 'dataforseo' | 'semrush' | 'scraper';
  capabilities: Set<'serp' | 'volume' | 'suggestions' | 'difficulty'
                  | 'backlinks' | 'competitors' | 'ai_visibility'>;
  postSerpTasks(reqs: SerpRequest[]): Promise<TaskRef[]>;
  fetchSerpResults(refs: TaskRef[]): Promise<SerpResult[]>;
  getKeywordMetrics(kws: KeywordQuery[]): Promise<KeywordMetrics[]>;
  getBacklinkSummary(target: string): Promise<BacklinkSummary>;
  getAiVisibility(q: AiVisibilityQuery): Promise<AiVisibilityResult[]>;
  estimateCostUsd(op: ProviderOp): number;   // consulted BEFORE dispatch (stop-loss)
}

Selection order per call: engagement tool_scope.provider override → tenant default → platform default (dataforseo, Standard queue). Semrush serves premium engagements; the scraper driver (free autocomplete/PAA) is a capability-limited fallback for suggestions only.

Caching-in-Postgres

search_data_cache is shared, no-RLS (like companies): market data is public-world data, and the whole cost win is cross-tenant reuse — the same keyword volume serves N clients. Only the provider layer reads/writes it; it never serializes raw to tenant APIs; single-flight dispatch (advisory lock per cache key) prevents stampedes.

KindTTL
volume30 days
serp24 hours (tracked ranks bypass cache)
suggestions14 days
backlinks7 days
ai_visibility7 days
D-4 · Ratified 2026-07-23This is a deliberate, documented RLS exemption. It contains no client identifiers or client-private data — results are copied onto tenant rows, never returned raw.

The usage/cost ledger

Scope + budget stop-loss, checked in one place before dispatch: (0) the capability must be enabled in the engagement's tool_scope — a disabled tool is refused with the toggle named, regardless of budget; then month-to-date SUM(cost_usd) vs. engagement budget → tenant monthly cap → global platform cap (env, default $150/mo until the deposit model is proven). Any breach: the call is refused, a search.provider.budget_threshold event fires (also at 80%), and the console shows the blocked state.

The ledger powers the per-engagement usage panel, tenant admin rollup, the search.provider_cost.month rollup metric (feeds billing), and the §01 "blended $/client" truth — spend = Σ each engagement's enabled tools. The scope panel (SM-29) shows a projected monthly cost per toggle so the human sees the price of each switch before flipping it.

§12

Trust & Security

Nothing new to invent — every control reuses an existing platform mechanism, applied to a new set of resources.

Key custody

DataForSEO/Semrush keys: platform-nest env → OpenBao target-state; never in platform-ui, n8n credential stores, or per-tenant rows. Client OAuth tokens (P4) ride the integration_connections vault only.

RLS

All search_* tenant tables: FORCE-RLS, third-wall predicate, fail-closed empty-set semantics. The single exemption is search_data_cache — ratified, D-4.

Cerbos resources

New policy files: resource_search_property/engagement/keyword/audit/campaign/report/ledger. resource_search_engagement carries a set_scope action — the tool-scope decision is itself permission-gated.

Crawler egress (SSRF)

Resolve-then-check against registered+verified property domains; deny private/link-local/metadata ranges; robots.txt respect; rate caps; identified UA. Property verified_at is a prerequisite to first crawl.

Inbound webhooks

Notification-only (task ids), HMAC/secret-path validated at n8n; authoritative data always re-fetched over the authenticated provider API.

Money safety

Single dispatch choke-point (estimate → ledger check → advisory-lock → dispatch → true-up); one-shot approvalId consumption is replay-proof.

Module permissions declared in the contract: search:engagement:read|write, search:scope:write, search:keyword:write, search:rank:read, search:audit:run, search:brief:write, search:campaign:write, search:campaign:launch (covers manual mark-applied and api execution), search:content:publish, search:report:write|approve, search:ledger:read, search:provider:admin.

Audit: every provider call (ledger), every Cerbos decision (existing), every hub tool call (existing JSONL), every approval decision (existing) — nothing new to invent.
