§00

Executive Summary

What we are building, why the AGPL boundary is the whole architecture, and the shape of the decision already made.

Social-media becomes a platform-nest module vertical (ModuleContract key social, tables social_*) plus a department console on the dept-interface-template — the already-reserved "Publish" craft group (Calendar · Composer · Inbox · Analytics). The professional moat is approved platform-app access + brand-fit judgment, not scheduling plumbing, so the architecture keeps every byte of judgment, tenancy, and approval logic on our side of a hard license line.

The shape, in one paragraph

Postiz is the publishing engine, run AGPL-CONTAINED — an isolated container reached only over its REST API (mere aggregation; our NestJS/Go/Next.js stay uninfected). All domain state, tenancy, RBAC, approvals, and judgment live outside Postiz in platform-nest. Postiz holds exactly two things: network OAuth tokens (it must, to publish and refresh) and the approved-and-scheduled execution queue — drafts never enter Postiz. There is no universal post object: a social_posts master carries the idea/brief/approval state, and social_post_variants carry per-network content validated against each network's media rules and quota before anything is queued. A first-class connector registry (social_accounts + the platform-app fleet) is surfaced exactly like the IT device registry. AI is local-first via ai-gateway-go — Hermes for bulk work, Claude only for client-facing polish, brand-voice RAG riding WS8 knowledge, images from the Creative Image Studio, credits-gated. Human-in-the-loop is mandatory and stricter than SEO: every outbound public action — publish, reply, delete — is a WS4 impact:'high' suspension, and execution consumes a one-shot approvalId with payload-hash match. There is no auto-publish path, for humans or agents. Money — X per-post fees and generative-image/video credits — flows through one social_usage_ledger with the SEO-proven stop-loss chain, fail-closed, checked before dispatch.

Build order is risk-honest: P0 contracts + containment spike → P1 organic publish/calendar/composer on our own accounts ($0, own-risk) → P2 engagement inbox → P3 AI copy/assets + analytics/reports (+ X metering) → P4 agent-proposed drafts. 27 tickets P0–P4 plus 2 decision-gated, /army-ready, in §12.

Decision stateAll architecture-level decisions in this document are locked (see §14 Decision Log) and conform to prior foundation-research locks (publisher choice, Chatwoot drop, human-in-the-loop). What remains open are the six owner-decision items in §13. Registration in MODULES.md as social-media · 0.0.0 · PLANNED happens on approval of this doc.

Architectural pillars

P1 · Postiz contained

The publishing engine runs at arm's length behind one REST adapter. No shared code, no shared DB, no linking — the fork stays thin-to-zero.

P2 · Two-level content

No universal post object. A master idea/brief/approval row; per-network variants carry content, media, and settings, validated before anything is queued.

P3 · Connector registry

Per client × network — app-review status, token health, quota counters, last error — surfaced exactly like the IT device registry.

P4 · Local-first AI

Hermes for bulk drafting, Claude for client-facing polish only, brand-voice RAG over WS8 knowledge, images via the Creative Image Studio.

P5 · Human-in-the-loop, always

Every outbound public action is a WS4 suspension; execution consumes a one-shot approvalId with payload-hash match. No exceptions for agents.

P6 · One metered ledger

X per-post fees and generative credits flow through a single ledger with fail-closed stop-loss — engagement budget → tenant cap → global cap.

§02

System Overview

The whole subsystem on one plate: the private platform, the license zone at arm's length, and every seam between them.

Reading the diagram

  • Zone A holds all state and judgment: the module, its RLS-scoped Postgres, the AI routing, the brand-voice RAG, the MCP tool surface, and the event backbone.
  • The license zone is Postiz — reached exclusively over REST, no shared code, no shared schema, no in-process embedding. Its own Postgres and Redis are opaque to us; we never query them.
  • Two arrows cross to the internet: Postiz's publish/refresh egress to the networks (where the network tokens live), and a narrow path-allowlisted ingress (edge proxy → Postiz's OAuth-callback and platform-webhook paths only).
  • Status webhooks toward us are notification-only (post/integration ids) — the authoritative state is always re-fetched over the authenticated Postiz API, never trusted from the webhook body.

Domain Model & Schema

The core entities, the two-level content model, and the FORCE-RLS third wall every table inherits.

Design rules (inherited, not optional)

  • Every tenant table: tenant_id uuid NOT NULL REFERENCES companies(id), origin_site, created_at/updated_at, soft-delete deleted_at where user-facing.
  • FORCE-RLS with the WSD-3 third wall — policy predicate tenant_id = ANY(app_current_tenants()) AND app_module_allowed('social') on both USING and WITH CHECK, byte-identical to 0028_module_hr.sql. App side reaches these tables only via withTenants(tenants, { modules: ['social'] }).
  • Migrations take the next unused number (0034+ as of 2026-07-23 — coordinate with any in-flight SEO tickets drawing from the same sequence); no in-migration GRANTs; no sync_app grants (social tables do not sync in v1).
  • Money: metered cost is numeric(12,6) USD (same rationale as the SEO ledger). No client-facing money in v1 — no ad spend.
  • The single non-tenant table is social_platform_apps — our own app fleet, no client data, admin-endpoint-only. Unlike SEO there is no shared market-data cache: every other byte in this module is client-private.

Publisher Boundary & Cost Ledger

One adapter is the entire AGPL containment line; one ledger is the entire money-safety line.

C-01

Publisher Port — SocialPublisher

Zone A
Purpose
The single, capability-based interface every publishing operation goes through. Keeping every call at arm's length behind one adapter is the AGPL containment line.
Technology
platform-nest, src/modules/social/publisher/. One driver ships in v1 (Postiz); the port exists so the Mixpost-Pro fallback (or a direct-API driver) is a driver swap, not a redesign.
Responsibilities
  • Org lifecycle: createOrg, connectUrl (OAuth entry), listIntegrations (registry sync source) — tenant mapping stays ours; the driver carries only the opaque org ref.
  • Publishing: schedulePost, cancelPost, getPostStatus — accepts only approved work; the caller enforces §07, the driver asserts approvalId present.
  • Engagement: listComments, sendReply.
  • Analytics: getAccountMetrics, getPostMetrics.
  • Money: estimateCostUsd(op) — consulted before dispatch (X pay-per-post).
Interfaces
in: module call sites (dispatch choke-point, registry sync, inbox pull) · out: HTTP+JSON to Postiz's public API only
Data owned
None — stateless per call; org-scoped API key resolved from api_key_ref at call time
Security
Every request/response OTel-annotated (network, org, op, cost_usd); no Postiz type or code imported — containment is enforceable by lint (zero postiz package deps)
Operations
Driver swap (Mixpost fallback) = new driver + deploy change, not a redesign

The usage/cost ledger

X is a metered cost center (~$0.015/post, ~$0.20 with link — reverify at build time) and generative image/video is the highest-cost AI class. Both flow through one ledger, mirroring search_provider_calls: social_usage_ledger (kind in x_post/ai_image/ai_video/ai_cloud_text, cost_usd numeric(12,6), status, requested_by, correlation_id — indexed (tenant_id, engagement_id, created_at DESC)).

Scope + budget stop-loss (fail-closed, one choke-point before dispatch)

Byte-for-byte the SEO pattern:

  1. The capability must be enabled in the engagement's tool_scope (networks.x, ai.imageGen) — a disabled toggle refuses with the toggle named, regardless of budget.
  2. Month-to-date SUM(cost_usd) vs — engagement usage_budget_usd → tenant monthly cap → global platform cap (env, default $100/mo until X usage is proven).
  3. Breach: refuse + emit social.usage.budget_threshold (also at 80%); console shows the blocked state; override = social:credits:admin + audit.
Price of the clickThe composer surfaces estimateCostUsd on every X variant before approval is requested, so the approver sees the price of the click. Ledger powers the per-engagement usage panel, tenant rollup, and the social.usage_cost.month rollup metric. Gateway-side AI cost caps remain enforced upstream independently (defence in depth).

AI-drafts → human-approves → publish (the WS4 spine)

  1. AI (or a human, or a WS8 agent) produces draft rows — always persisted, never dispatched. Drafts live in our DB only; nothing enters Postiz at draft time.
  2. Low-impact artifacts (reports, campaign plans) approve in-console via module permissions. Anything outbound-public — publish, reply, cancel-published, delete — goes through WS4: the MCP tool is declared write:true, impact:'high', the hub write-gate suspends it into automation_approvals, with a full preview (rendered variant, media, target account, scheduled time, estimated X cost).
  3. Execute — one-shot, single-mode: approval produces an approvalId bound to the variant's payload_hash. The dispatch choke-point consumes it (status approved, hash match, unconsumed) in the same transaction that calls schedulePost and stamps postiz_post_id — exactly once, replay-refused. Any edit after approval nulls the approval and the variant re-enters review.
  4. Scheduling semantics: approval covers content + target + time window. Postiz executes the queue; a reconcile flow re-fetches authoritative status. A variant stuck queued past its slot + grace raises social.post.failed for human action — never auto-retry a publish that may have half-succeeded.

Control layers

Key custody (three-way split)

App creds (OpenBao → Postiz env) · Postiz org keys (server-side alias) · network tokens (inside Postiz only, never copied). Disjoint blast radii by construction.

AGPL containment

No shared code/DB/process, REST-only, lint-enforced zero Postiz deps, fork-touchpoint budget with review. License boundary = security boundary.

RLS & tenancy

FORCE-RLS, third-wall predicate, fail-closed empty-set semantics on every social_* table except the client-data-free social_platform_apps.

Wrong-account defense

FK chain variant→account→publisher_org→(tenant,client) validated at composer time AND re-validated at the dispatch choke-point.

Publish safety

Single dispatch choke-point: scope check → media/quota re-validate → one-shot approvalId + hash match → schedulePost → stamp → true-up. No auto-retry of ambiguous failures.

Cerbos resources

Seven new resource policies (engagement, account, post, inbox, report, ledger, platform_app) with derived-roles reuse; UI mirrors in lib/rbac.ts.

Inbound surfaces

Edge exposes only exact-path OAuth callbacks/webhooks to Postiz; Postiz→us webhooks notification-only, HMAC/secret-path validated.

Money safety

Estimate → tool-scope → ledger stop-loss → dispatch → true-up. X spend visible on the approval card before the human clicks.

Publish safety — the non-obvious oneThe AI ingests brand corpus and past-post content, which is untrusted input. Defense against prompt injection is not in the prompt — it is that every outbound-public tool structurally suspends to WS4 regardless of what the model decided, and execution requires a one-shot approval bound to an exact payload hash. The model can propose; only an authorized, gated, hash-matched command executes — for humans and agents alike.

Audit

Every ledger row, every Cerbos decision (existing), every hub tool call (existing JSONL), every approval decision (existing), every publisher-adapter call (OTel + module log with org/network/op) — nothing new to invent.
