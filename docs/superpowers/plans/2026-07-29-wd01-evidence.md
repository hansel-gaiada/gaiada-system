## Findings (filed, not fixed — QA doctrine)

### F-1 · ⚠️ Dispatcher drops client context → ingested runs are invisible to the client portal

`pipeline_runs.client_id` is **NULL** on the ingested run, so the portal (which scopes on
`run.client_id → clients.portal_user_id`) cannot list it. Root cause:

- `meeting_recordings` **does** carry `client_id` + `project_id` (FKs present).
- `pipeline.createRun` **does** accept `clientId` ("drives client-portal scoping").
- **`automation/workflows/mtg-dispatcher.json` never passes it** — zero occurrences of
  `clientId`/`client_id` in the workflow JSON; the "Assemble createRun args" node omits it.

So the context exists at both ends and is dropped in the middle. The design's WD-07 line
("client/project context plumbed … start already accepts it — **verify end-to-end**") assumed this
worked; it does not. **Owner: WD-07**, and it should be promoted from "polish" to a required fix —
the portal is a Phase-1 deliverable and WD-08's gate walks a client staging review.

### F-2 · `stale-approval-chaser` errored 04:00–07:00, recovered 08:00+

Four consecutive CRON errors ending exactly when the stack was redeployed, then two clean runs.
Almost certainly redeploy fallout, not a latent bug. Not webdev's ticket — flagged for whoever owns
the search/SEO redeploy session.

### F-3 · Migration-number assumption is stale (affects three programs)

Design D-12 assumes the ledger ends at `0040` and claims **`0041_module_webdev.sql`**. **`0041` is
consumed.** Actual disk + DB state:

- `0041`–`0044` → PM (templates, progress snapshots, followers/reactions, doc versions)
- `0045`–`0048` → search/SEO (audit ingest, AI drafts, provider simulation, capability provenance)

**The webdev module migration must take `0049`** (next-unused at merge, per migrations README rule
5), coordinating with SMM-01 and Creative CR-01 — which are *also* aimed at consumed numbers.
Creative D-13's `0036+` was already flagged stale; it is now stale by 13.
