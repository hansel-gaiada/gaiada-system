## 1. The signature, and the central ruling

Two exported names, not one function that branches on its arguments:

```ts
// THE default. Always asks Cerbos (wraps check()). Correct for everything, including
// condition-dependent grants and the wildcard bypass.
async function can(principal: Principal, permissionKey: string, resource: PermissionResourceAttrs): Promise<boolean>

// The narrow, opt-in fast path. Answers strictly from principal.perms — zero round trip,
// zero awareness of any resource-level condition.
can.scopeOnly(principal: Principal, permissionKey: string, scope: ScopeRef): boolean
```

`PermissionResourceAttrs` is `Omit<Resource, "kind">` — callers never name a raw Cerbos kind;
`can()` derives it from the catalog entry for the permission key
(`permission-catalog.json`'s `cerbosKind`/`cerbosAction`, e.g. `"pm.task.update"` →
`{kind: "pm_task", action: "update"}`), which is exactly what IAM-01a's catalog exists to hide
from callers. `ScopeRef` is `{scopeType, scopeId}`, the same union `RoleGrant`/`PermissionGrant`
already use.

### The ruling: Cerbos is the default; `perms` is a declared, narrow opt-in

**They are not equivalent, and the API makes the caller say which one they mean by making
them call a differently-named function — not by branching on argument shape.**

- **`can()` always asks Cerbos.** Cerbos evaluates conditions a flat `perms` list cannot
  express — `ownerId`, `subjectUserId` (HR self-service), `teamId`, assurance floors
  (`notLow`/`high`) — and it is the only place the platform_admin/group_executive wildcard
  bypass lives (IAM-04c: the bypass stays a per-kind Cerbos rule, never a `*` permission).
  `can()` therefore resolves the bypass correctly for free, with no special-casing, because it
  always goes through the exact mechanism the bypass is implemented in.
- **`can.scopeOnly()` answers from `principalHasPermission()` (IAM-03a) alone.** No network
  round trip, but it literally cannot see a condition. It is safe ONLY for genuinely
  scope-only questions — nav visibility, whether to render a "New X" button, pre-filtering a
  list before the real per-row check — never for gating access to one specific resource.

Reproducing the IAM-04b pilot's own 403→200 regression at the API layer would look exactly
like a `can()` that silently picked the cheap `perms`-only path when it guessed a question was
"probably scope-only." Two differently-named exports make that mistake something a code
reviewer sees in the diff (`can.scopeOnly(...)` reads differently from `can(...)`), not
something an implicit branch decides invisibly.

## 2. Relationship permissions and the wildcard bypass

- **The 15 relationship-class permissions never answer `true` off a bundle.** They
  structurally cannot: 0093's `role_permissions_reject_relationship` trigger and
  `assemblePrincipal()`'s own `class = 'grantable'` filter both already make it impossible for
  one to appear in `perms` at all (pre-existing, IAM-03a/IAM-01c — not this ticket's
  mechanism). `can.scopeOnly()` adds a THIRD, louder layer on top: it checks the catalog's
  `class` field and **throws** for any relationship key, rather than returning the `false` the
  data would produce anyway. A thrown, named error ("relationship-class... use can() instead")
  is safer than a silent `false`, which would read as "checked, correctly denied" when the
  honest answer is "wrong tool for this question." `can()` answers relationship permissions
  correctly by asking Cerbos directly — proven live against `assistant.agent_run.read`: the
  owning user + matching `origin` attribute allows, a mismatched owner denies, and
  `platform_admin` (role-arm wildcard, zero perms) is correctly DENIED too, because that kind
  carries no wildcard rule at all (catalog Ruling 3: "no wildcard, no superadmin... may reach
  these").
- **The wildcard bypass resolves correctly through `can()` with zero perms.** Tested directly:
  a `platform_admin` principal with an EMPTY `perms` array still gets `true` from
  `can(p, "pm.task.delete", ...)` and `can(p, "hr.case.export", ...)` — the role-arm wildcard
  rule is what answers, unaffected by whether `perms` is populated, because `can()` always
  goes through Cerbos and Cerbos's wildcard rule lives entirely on the role-name axis.
  `can.scopeOnly()` has no wildcard concept at all (correctly — IAM-04c: no `*` permission
  exists) and would only agree with `can()` for `platform_admin` on the 215 grantable keys
  because migration 0094 happens to bundle all 215 of them explicitly onto that role; it
  disagrees (throws) for the exempt 15, which is the correct behavior, not a gap.

## 3. Tests — both arms, both directions, and the disagreements (`can.test.ts`, 21 tests)

Split into two tiers deliberately: pure catalog/scope-logic tests need no Cerbos and run
unconditionally; `can()` itself needs live Cerbos (`describe.skipIf(!live)`, same convention as
every other `src/rbac/*.test.ts`).

**Tier 1 — pure (8 tests, always run):**
- `can()` throws on an uncatalogued key; `can.scopeOnly()` throws on an uncatalogued key.
- `can.scopeOnly()` throws for 4 different relationship-class keys (assistant thread/memory/
  agent_run, `core.mcp_tool.call`), asserting both the "relationship-class" and "Use can("
  substrings, so the error is actionable, not just present.
- `can.scopeOnly()` ALLOW (holds key at exact scope), DENY (key not held), DENY (right key,
  wrong company), ALLOW (global grant covers every company asked about) — the same scope
  cascade `principalHasPermission()` already guarantees, exercised through the new name.
- One test asserts `can.scopeOnly()` needs no `CERBOS_URL` at all (it is synchronous).

**Tier 2 — live Cerbos, `can()` both arms both directions (9 tests):**
- ALLOW/DENY via the permission arm alone (no role); ALLOW/DENY via the role arm alone (empty
  perms) — proves `can()` is a correct drop-in for both of IAM-04b's existing arms, not just
  one.
- DENY with no role and no perms at all; DENY cross-tenant despite a matching company-scope
  permission grant (no leak).
- The wildcard-bypass-through-zero-perms case and the two relationship-permission cases
  described in §2.

**Tier 2 — the disagreements the ruling exists to name (3 tests):**
- **Finding 2 reproduced as a `can()`-vs-`scopeOnly()` disagreement:** `team_lead`'s dead
  `pm.task.*` bundle entry — `can.scopeOnly()` says `true` (it only sees the flat grant),
  `can()` says `false` (Cerbos's real condition, provably unreachable per
  `pm-adversarial-authz.test.ts`, correctly denies). This is the exact hazard named in the
  ticket brief, pinned as an assertion rather than left implicit.
- **Finding 1 reproduced the same way:** a `member`'s self-scoped `hr.case.read` bundle entry,
  asked about *someone else's* case — `can.scopeOnly()` says `true` (indistinguishable from an
  unconditional hold once flattened), `can()` says `false` (the real `subjectUserId` check
  denies). A contrasting agreement case (the caller's own case) is asserted alongside so the
  test proves the disagreement is specifically about the *condition*, not about the key being
  wrong.
- **The relationship-class disagreement is a refusal, not an allow/deny split:**
  `can.scopeOnly()` throws outright; `can()` answers via Cerbos. Included to make explicit that
  "disagreement" here has two shapes — a wrong answer, and a refusal to answer at all — and
  the API's job is to make the second shape loud rather than let it decay into the first.

## 5. Blockers / follow-ups (not this ticket's remit)

- **D9/D14 write-approval semantics are NOT respected by `can()`.** It is a pure question
  (like `check()`), not a guard — it does not audit the decision and does not re-check D11
  `sessionVersion` on mutations. `authorize()` (`core/http.ts`) remains the throw-and-audit
  call site for routes and is unchanged. IAM-03's report flagged that a future `can()` "will
  need to respect" D9/D14 semantics; this ticket did not implement that, because the ticket
  brief scopes `can()` to wrapping `check()` and nothing in IAM-04's landed work gives `can()`
  an approval-routing contract to wrap yet. Whoever builds D9/D10 approval-gated writes should
  decide whether that belongs inside `can()` or stays a separate layer above it — flagged, not
  assumed either way.
- **IAM-05c (the BFF "my effective permissions" endpoint)** is the natural next consumer of
  `can.scopeOnly()` specifically — it needs to answer "what can this caller do in this scope"
  in bulk without N Cerbos round trips, which is exactly the fast path's intended shape. Not
  built here.
- **`can()`'s per-call Cerbos round trip is not batched.** A caller needing several permission
  answers for one request (e.g. rendering several gated buttons) will make several HTTP calls
  to Cerbos today, same as `check()` already does today for every existing caller — this
  ticket did not change that cost profile in either direction. `planResources` (D16) remains
  the existing answer for set-returning questions; `can()` does not attempt to replace it.
- **Migrating existing `authorize()`/`check()` call sites to `can()` is explicitly out of
  scope** and was not done — the ticket's own instruction is additive-only, and every existing
  call site keeps working unchanged.
