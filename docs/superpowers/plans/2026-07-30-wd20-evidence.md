## 4. Token non-exposure sweep

Code invariant (`platform-nest/src/core/integrations.service.ts`): `toConnectionResponse()` is the
**only** exported response shape and structurally has no `access_token_enc`/`refresh_token_enc`
fields — `hasToken`/`hasRefreshToken` booleans only.

Test evidence (`integrations.test.ts`, all green):

```ts
// creation: no token fields leak
expect(body.access_token_enc).toBeUndefined();
expect(body.refresh_token_enc).toBeUndefined();
expect(JSON.stringify(body)).not.toMatch(/token_enc/);

// after a real token is sealed via setConnectionTokens():
expect(row).toMatchObject({ hasToken: true, hasRefreshToken: true, tokenKeyVersion: "v1", status: "linked" });
expect(asText).not.toMatch(/token_enc/);           // full response body text-scanned
expect(db.rows[0].access_token_enc.startsWith("enc:v1:")).toBe(true);   // DB has ciphertext
expect(db.rows[0].access_token_enc).not.toContain(PLAINTEXT);            // never the plaintext

// fail-closed: token write refused (503) with no INTEGRATION_TOKEN_KEY, DB stays NULL
```

No live `integration_connections` rows exist yet on the dev stack (`select count(*) ... → 0`) — no
one has linked a provider — so there is nothing to sweep live-response-wise beyond the test
evidence above; the test suite already covers the sealed-token case end-to-end.

### Finding WD-20-R1 — `work_activity` has no `exec`/`group_executive` Cerbos carve-out (regression, filed not fixed)

- **Severity:** Medium (authz gap — a real capability is missing, not a leak)
- **Where:** `platform-nest/cerbos/policies/resource_work_activity.yaml` — only `platform_admin`
  (actions `*`) and `company_admin`/`manager`/`member`/`viewer`/`team_lead` (action `read`, all
  scoped `inTenant`) have rules. There is **no `group_executive` rule at all.**
- **Contrast:** `resource_integration_connection.yaml` (same ticket family, same author) DOES give
  `group_executive` an explicit global read/create/update/delete rule. The ticket's own AC line
  ("Cerbos matrix (member/manager/company_admin/exec × own/other/company rows)") implies exec should
  be in the grid for both resources; it's asymmetric today.
- **Repro:** `cerbos-webdev-matrix.test.ts`, test `"exec (group_executive, global scope): NOT in the
  work_activity allow list — no rule matches"` — asserts (and confirms) `allow(execPrincipal,
  {kind:"work_activity",tenantId:T1}, "read") === false`.
- **Impact:** an exec (`group_executive`) — who per the design doc has cross-company oversight —
  cannot read the work-activity/evidence feed for ANY company, including via the department Home
  KPI/Activity tab, which is a Phase-1 UI surface they'd reasonably expect to see.
- **Owner / fix tier:** senior-be — add a `group_executive` read rule to
  `resource_work_activity.yaml` mirroring the `resource_integration_connection.yaml` pattern
  (`condition: { match: { expr: "variables.notLow" } }`, no `inTenant` since exec is cross-company).
  One-line policy change + a parity test; low risk, no schema change.
