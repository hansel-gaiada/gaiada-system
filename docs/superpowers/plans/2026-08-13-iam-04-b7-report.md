# IAM-04-B7 — retrying `portal`'s permission arm, after the closure mechanism landed

**Status:** PROTOTYPED / DEV-VERIFIED (targeted suites, `cerbos compile`, `npm run typecheck`, live
probes against a freshly-restarted `gaiada-test-cerbos`; NOT deployed to the live estate — no
commit, no push, no tag, per this ticket's own constraint). Tree left dirty for review.

**Ticket:** IAM-04-B7. IAM-04-B6 found `portal` structurally BLOCKED and named the precondition for
re-attempting it: IAM-SEC-06 (or a Cerbos-side exclusion) landing, and IAM-SEC-05 being fixed. Both
have since landed. This ticket's entire first job was to **establish, not assume**, that the block
is genuinely lifted before changing anything — the ticket brief explicitly called out a prior
instance of arguing a gate was stale on an incomplete premise, refuted by the architect finding an
unguarded writer. This time the premise was checked from source and by experiment before any policy
file was touched.

**Verdict: the block IS genuinely lifted for `portal`+`client`.** Wired all 7 actions,
company-scope-only (faithfully mirroring `client`'s own reach, never the generic
"global-or-company" shape). Updated the hazard gate to derive its mitigation from
`scope-constrained-roles.json` rather than a hand-written exemption. Zero decisions changed for
anyone who is not a `client` grant holder; the `client` role-arm rule itself is byte-unchanged.

## 1. Step 1 verdict — establishing the block was lifted, with evidence

### 1.1 Does IAM-SEC-06's filter actually neutralise the `:722`/`:735` hazard for `client`?

**Yes — confirmed from source, then proved by test, both static and live.**

- `platform-nest/src/rbac/scope-constrained-roles.json` (read-only; not edited by this ticket) has
  `"client": ["company"]`. This is machine-derived from `derived_roles.yaml`'s own `client`
  condition by `scripts/generate-scope-constrained-roles.mjs` — the identical source
  `permission-arm-hazard-scan.test.ts`'s own Pattern-C classifier parses, so the two cannot
  silently disagree about what `client`'s own condition allows.
- `platform-nest/src/rbac/scope-constrained-roles.ts`'s `isGrantScopeReachable("client",
  "company")` → `true`; `isGrantScopeReachable("client", "global")` → `false`. `principal.ts`'s
  `assemblePrincipal()` applies this per-row, before a permission ever survives into
  `Principal.perms`.
- **Proved by a NEW test** (`iam-04-b7-portal.db.test.ts`, "ACCEPTANCE" block): a real
  `user_roles` row — `client @ global` (via `grantRole(user, clientRoleId, "global", null)`, a real
  DB insert, not a mock) — resolved through the REAL `assemblePrincipal()` yields
  `roles: [{role:"client", scopeType:"global", scopeId:null}]` (the grant itself is untouched) and
  `perms: []` (every permission this grant would otherwise have resolved is dropped). A second test
  in the same file drives that principal through the REAL `check()` → REAL Cerbos and gets `DENY`
  on all 7 `portal` actions. Ran green against `gaiada-test-pg` + a restarted `gaiada-test-cerbos`
  (see §5).
- If it had NOT been lifted, that first test would show `perms` non-empty at global scope, and the
  second would show `ALLOW` somewhere — neither happened.

a scope `client`'s own role-arm rule would refuse. Every path that could produce such a payload was
traced:

neither constructs a `portal`/`client`-shaped Cerbos payload at all. The only bypass that exists is
confined to test-file mocks, which cannot fire from a real request.

## 2. What changed, and exactly how the gate now derives its mitigation

### 2.1 The gate (`permission-arm-hazard-scan.test.ts`)

The "REACHABILITY (other-narrow direction, IAM-SEC-04)" test used to be unconditional: ANY
co-occurrence of an other-narrow Pattern-C role with a wired `perm_*` arm on the same kind was a
hard failure, full stop — matching the exact wording IAM-04-B6 quoted ("STOP wiring that kind's
permission arm and report this, do not tune the predicate to make it pass"). It is now:

```ts
const sec06ProtectedRoles = loadSec06ProtectedRoles(); // reads scope-constrained-roles.json
const coOccurring = otherNarrowHits.filter((h) => permArmKindsForC.has(h.kind));
const offenders = coOccurring.filter((h) => !sec06ProtectedRoles.has(h.role));
expect(offenders).toEqual([]);
```

`loadSec06ProtectedRoles()` does one thing: reads the `roles` object out of
`scope-constrained-roles.json` and returns its key set. **Nothing hand-written** — this is the same
artifact IAM-SEC-06 built specifically so the write-path guard and the resolution-layer filter
could both be re-derived from `derived_roles.yaml` without drifting from it or from each other. If
`client` (or any future other-narrow role) is ever removed from that JSON — by hand, or because
`derived_roles.yaml` changed and nobody regenerated it — this offenders check goes red the moment
someone tries to wire a mirror on that role's kind, and a SEPARATE new completeness test (added
alongside it, mirroring the existing `:763`-region check that does the same for
`ROLE_SCOPE_CONSTRAINTS`) goes red immediately regardless of whether any mirror exists yet:

```ts
for (const role of rolesFound) {
  expect(sec06ProtectedRoles.has(role)).toBe(true);
}
expect(sec06ProtectedRoles.has("client")).toBe(true);
expect(sec06ProtectedRoles.has("org_unit_lead")).toBe(true);
```

This is deliberately a DIFFERENT artifact from `loadOtherNarrowRolesFromController()` (which reads
`admin-identity.controller.ts`'s `ROLE_SCOPE_CONSTRAINTS`, the write-path guard) — the ruling
explicitly rejected relying on that layer alone for closure (IAM-04c §8: seeds/migrations bypass it
by design; IAM-SEC-05 found it incomplete besides, via the unguarded `inviteUser` writer). The
existing `:763`-region completeness test against `ROLE_SCOPE_CONSTRAINTS` is untouched — it still
serves its own purpose (write-path completeness, invariant 3 of the ruling's §8) — this ticket adds
a second, independent completeness check against the resolution-layer artifact, it does not replace
the first.

`permission-arm-hazard-scan.test.ts` went from 129 tests (B6's count) to 132: +1 for the new
completeness test, +1 net from restructuring the reachability test's body (it now logs an
informational "excused by IAM-SEC-06" line), and the pre-existing suite's other counts are
unaffected by portal's addition (Pattern A/B never fire on `portal` — it has exactly one role per
rule, never mixed — confirmed by PART 3's two regression-guard `it.each` blocks running vacuously
for `portal`, see §5).

### 2.2 The policy files

- `derived_roles.yaml`: 7 new `perm_portal_*` roles, each checking
  `request.principal.attr.perms.exists(g, g.key == "portal.<action>" && g.scopeType == "company" &&
  g.scopeId == request.resource.attr.tenantId)` — **no global branch**, unlike every other kind's
  perm arm in this file. This is the hand-crafted, scope-faithful mirror IAM-04-B6 §5 built and
  probed in isolation before reverting it; the shape is deliberate, not a shortcut.
- `resource_portal.yaml`: 7 new single-action rules, each `derivedRoles: ["perm_portal_<action>"]`,
  `condition: variables.inTenant` — the SAME condition the pre-existing `client` rule already
  carries. The `client` rule itself is byte-unchanged (confirmed by
  `iam-04-b7-portal.test.ts`'s dedicated assertion). The comment block explaining the prior BLOCKED
  finding was rewritten to explain the closure; no rule text in that block changed.

All 7 catalog keys (`portal.read`/`decide`/`sign`/`pay`/`update_profile`/`request_change`/
`approve_post`) pre-existed as `class: "grantable"` rows (confirmed before wiring) — no key was
invented.

### 2.3 The client-boundary check (⚠ constraint)

**No staff permission-holder can act through the `client` rule, and no client can reach a
staff-only action.** Concretely:

- No other role's bundle holds any `portal.*` key today (`role-permission-bundles.json`, confirmed
  — only `client` and the exempt `platform_admin` wildcard superset do). `role_permissions` is
  seed/migration-only data (grepped every writer — `INSERT`/`UPDATE`/`DELETE` on that table exist
  only inside `migrations/*.sql`, no controller or service writes it at request time), so no live
  admin action can hand a staff role this key today.
- A **realistic** staff principal (a real `company_admin` grant, real membership, its REAL resolved
  bundle from `assemblePrincipal()`) is denied all 7 actions — proved live, DB-backed, in
  `iam-04-b7-portal.db.test.ts`'s "REGRESSION CONTROL" block (§5).
- One adversarial variant WAS explored and is worth naming plainly rather than glossing over: a
  hand-crafted Cerbos payload giving a `company_admin` ROLE grant an artificially-injected
  `portal.read` PERM entry (the same "simulate what a future mirror would do" technique IAM-04-B6's
  own probe 6 used, back when no mirror existed) now returns **ALLOW**, because the wired mirror
  checks the flat `attr.perms` array by design, exactly like every other permission arm in this
  program — it does not, and structurally cannot, check which role produced the entry. This is NOT
  a portal-specific defect: it is the accepted, documented semantics of the whole IAM-04
  permission-arm mechanism (REG3's own report: "anyone whose ROLE carries enough PERMISSION should
  reach an action, not only named roles"), and it is not reachable via any real write path today
  (see the `role_permissions` finding above). It is flagged here, not silently discovered later.
- No client can reach a staff-only action: `portal` carries no staff-only action at all (the DR-12
  staff-read rule was already deleted; there is no other staff action on this kind), so the
  question is vacuously satisfied.

## 7. Blockers / follow-ups for the owner

1. **`docs/PERMISSION-CONTRACT.md` §2** still describes `portal` as blocked/deferred behind an
   architect decision — stale after this ticket, same flag IAM-04-B6 raised and left for whoever
   next touches that doc (not in this ticket's ownership list).
2. **The adversarial finding in §2.3** (a hand-injected `portal.read` perm on a `company_admin` role
   grant is honoured by the new mirror) is not a live hazard today — `role_permissions` is
   migration-only data with no admin-editable write path — but it is worth naming as a standing
   property of the whole permission-arm mechanism, not just `portal`: any future migration that
   grants a `portal.*` key to a non-`client` role would immediately create a real staff-through-
   client-rule crossing, with nothing in this ticket's own tests positioned to catch it (they pin
   TODAY's bundle contents, not a structural invariant against it). If the "roles become DATA"
   program (memory `iam-rbac-program`) ever lets an admin grant arbitrary permission keys to
   arbitrary roles, `portal.*` keys should probably be excluded from what's grantable to non-client
   roles at that layer — flagged for whoever builds that feature, not something to solve here.
3. **`org_unit_lead`+`appraisal`/`report_document`** could now, mechanically, pass the same
   "REACHABILITY (other-narrow direction)" gate if a future ticket wired a mirror there — the
   closure mechanism (IAM-SEC-06) covers `org_unit_lead` exactly as it covers `client`. The owner's
   ruling to keep those two kinds permanently unwired (IAM-04c §9, option C) is independent of the
   gate and was not revisited or touched by this ticket; naming this so nobody mistakes "the gate
   would now allow it" for "the owner decision changed."
