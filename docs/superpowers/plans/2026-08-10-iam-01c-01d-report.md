Schema extension (all `ADD COLUMN IF NOT EXISTS`, idempotent):
`module_key`, `resource`, `action`, `cerbos_kind`, `cerbos_action`, `class text NOT NULL DEFAULT
'grantable'`, `sensitive boolean NOT NULL DEFAULT false`, `deprecated_at timestamptz`. (`module_key`

FK to a registered `ModuleContract.key`, since `core`/`portal` are catalog domains with no
compiled-in module of that name.)

**Row counts — asserted three ways, not assumed:**

1. **In the migration itself** — a closing `DO $$ ... END $$` block queries `count(*)` overall and
   per `class`/`sensitive` and `RAISE EXCEPTION`s (aborting the whole transaction) if any of
   total=230, grantable=215, relationship=15, sensitive=79 doesn't match exactly. This is the
   "assert affected row counts, never assume" instruction applied literally — if the INSERT ever
   silently narrowed (it structurally cannot here; see §1a), the migration itself fails loudly
   rather than reporting success.
2. **In `permission-catalog.db.test.ts`** — re-derives the same four expected numbers straight from
   `permission-catalog.json` (so the test can't drift from the source either) and asserts the live
   DB matches exactly, plus a 6-key spot-check across every domain (core/hr/search/portal/mcp_tool/
   assistant) comparing every column (`module_key`, `resource`, `action`, `cerbos_kind`,
   `cerbos_action`, `class`, `sensitive`) against the JSON, not just the key.
3. **Idempotency, proven not asserted** — the same test re-executes 0093's own SQL text a second
   time against the already-seeded database (bypassing the ledger on purpose) and asserts the total
   is still exactly 230 and that `core.client.read`'s row `id` is byte-identical before and after
   (the `ON CONFLICT (key) DO UPDATE` never touches `id`, so a second run re-syncs columns onto the

**Result, this run:** 230 total / 215 grantable / 15 relationship / 79 sensitive. Exact match, both
inside the migration's own guard and in the standalone test's independent re-derivation.

**§1a — why the RLS backfill trap categorically cannot apply here (asserted, not assumed either):**
`permissions` has no `tenant_id` column and has never had `FORCE ROW LEVEL SECURITY` applied — it
is one of `0001_core.sql`'s own "Global tables (no tenant_id; app-layer guarded)", alongside
`companies`/`users`/`roles`. I did not just take that on faith: `npm run lint:migration-rls` (which
tracks exactly the tables that have ever had `FORCE ROW LEVEL SECURITY` applied, per that script's
own header) scanned 93 migrations and reported **0093 clean** — my file is not and cannot be in the
set that lint even looks at, because the table it touches is never in the FORCE-RLS set. Separately,
the specific failure mode the trap describes — an UPDATE/DELETE/INSERT…SELECT whose row-set is
filtered by a FORCE-RLS USING policy reading an unset `app.current_tenant_ids` GUC — cannot occur
here for a second, independent reason: 0093's only DML is a literal-VALUES `INSERT … ON CONFLICT DO
UPDATE`, whose row-set is the literal VALUES list, not a SELECT filtered by any RLS policy. There is
no GUC in this file's path to forget, and no row-set for a missing GUC to silently narrow to zero.
**Conclusion for the FORCE-RLS sweep: `permissions` is correctly treated as global reference data,
not tenant data, and needs no RLS at all.**

## How the 15 relationship entries are distinguished so they can never be seeded role-grantable

Two independent layers, deliberately not one:

1. **Schema:** `class text NOT NULL DEFAULT 'grantable'` with `CHECK (class IN ('grantable',
   'relationship'))` (`permissions_class_check`, DROP-then-ADD idempotent). Verified: an attempted
   insert with `class = 'nonsense'` is rejected by the constraint (test: "the class CHECK constraint
   rejects anything outside grantable/relationship").
2. **DB-level enforcement, the part that actually answers "must never be seeded role-grantable":** a
   `BEFORE INSERT OR UPDATE` trigger on `role_permissions` (`role_permissions_reject_relationship` /
   `permissions_reject_relationship_grant()`) looks up the target permission's `class` and
   `RAISE EXCEPTION`s if it is `'relationship'`. This is defense-in-depth **beneath** the app-layer
   IAM-01d check — it fires even for a direct SQL insert that never goes through
   `validateModulePermissions()` at all (an admin tool, a future migration, a bad manual grant).
   Proven, not asserted, five ways in `permission-catalog.db.test.ts`:
   - a single relationship permission (`core.mcp_tool.call`) is rejected on INSERT;
   - **every one of the 15** relationship rows individually rejects a grant attempt (a loop over the
     real 15, not a sample — this is the test that would catch a 16th exempt pair added later
     without the trigger being told about it, since the trigger reads `class` off the row, not a
     hardcoded list);
   - the control case — a `class='grantable'` permission — **succeeds**, proving the trigger
     discriminates on class rather than blocking everything;
   - an UPDATE that repoints an *existing* grant's `permission_id` onto a relationship row is also
     rejected (not just INSERT — a grant that started legitimate and gets silently repointed later
     is the same hazard).
   The concurrent IAM-02a migration (`0094`) explicitly depends on this and says so in its own
   header ("`0093`'s `role_permissions_reject_relationship` trigger enforces that at the DB layer
   even if this file's own SELECT ever tried to — it does not"), which is independent confirmation
   the naming and mechanism line up with what the rest of the IAM work expects.

## 2. Fail-closed validation — exact behavior, and how I proved it

**File:** `platform-nest/src/modules/registry.ts`, `validateModulePermissions()`. Wired into
`platform-nest/src/main.ts`'s `bootstrap()`, called once, **after every `registerModule()` call**
(needs the full registered set) and **after `migrate()`** (already run at the top of `bootstrap()`,
so `0093`'s seed is guaranteed in place before validation runs).

**Exact mechanism:** one query — `SELECT key FROM permissions WHERE class = 'grantable' AND
deprecated_at IS NULL` — builds a `Set<string>`. Then it walks `allModules()` and every module's
`permissions[]`; any declared `key` not in the set is collected as `"<module.key>: \"<perm.key>\""`.
If the collected list is non-empty, it throws a single `Error` naming **every** offending
module+key at once (not just the first), with the full list in the message body. It deliberately
filters on `class = 'grantable'` rather than mere row existence — a module declaring one of the 15
relationship keys fails exactly the same way an uncatalogued key does, because that key's row exists
in `permissions` but isn't in the queried set.

**What happens at boot on a throw:** `bootstrap()` has no try/catch around this call, and it's
`await`ed strictly before `wireSearchProviderModeAndAdsWriteMode()`, `buildApp()`, and
`app.listen()`. A throw here means **the HTTP server never binds a port** — there is no code path
between the throw and any request-serving code. At the process level, `main.ts`'s entry point is a
bare `if (require.main === module) void bootstrap();` with no rejection handler anywhere in this
file or `telemetry.ts`. Node (v24 here, default since v15) terminates a process on an unhandled
promise rejection with a non-zero exit code, printing the rejection — so in production this is a
hard crash naming the exact module+key, not a hang and not a silent continue.

**⚠ Honesty check on verification depth:** I proved the throwing behavior itself directly and
thoroughly (6 dedicated tests below, all against the real `getPool()`/`withGlobal` path the
production code uses). I traced, but did **not literally execute**, a full `node dist/main.js` boot
with a deliberately-bad module compiled in to watch the process actually exit non-zero — that would
need a throwaway build and felt like more blast radius than this ticket's scope justified. Treat
"the process hard-crashes in prod" as **traced from Node's documented default**, not
end-to-end-executed; the "does the validator itself throw with the right message, given the real
production module set" half is fully executed and green.

**Tests (`src/modules/registry-permission-validation.db.test.ts`, 7 tests, all green):**
- the **real production 12-module set** (the exact objects `main.ts` registers, same order)
  validates clean against the seeded catalog — this is the concrete proof that 0093's migration map
  and the 01d module-declaration rewrite landed together correctly, not just that they look
  consistent on paper;
- a module declaring a made-up uncatalogued key fails closed, naming both the module and the key;
- a module declaring the **old pre-migration colon-style key** (`hr:case:read`) also fails closed —
  proof this is a real fail-closed check and not a no-op that happens to pass today;
- a module declaring a **relationship-class** key (`assistant.thread.read` — a real row in
  `permissions`) fails closed too, proving the check is `class`-aware, not row-existence-aware;
  static assertion that neither `automation:workflow:read`/`automation.workflow.read` nor
  `search:content:publish`/`search.content.publish` (colon or dotted) is declared by any production
  module (would boot-block on re-introduction);
- one bad module mixed in among the 12 real ones still sinks the whole boot (fails for the process,
  not per-module);
- an empty `permissions: []` array always validates clean (no false positive on modules that declare
  nothing, e.g. `assistant`/`automation-console`/`reports` after this rewrite).

## 3. Ruling on the 2 true orphans

**Both DECLARATIONS REMOVED, not catalogued.**

- **`automation:workflow:read`** (automation-console module) — no Cerbos enforcement exists. The
  module's own file header already documented the deviation before I touched it:
  `AdminSystemsController` is global/`platform-admin`-scoped by an in-code check, has no `:tenantId`
  route param, and was never Cerbos-authorized. Declaring it as a catalog permission would
  misrepresent an in-code admin check as a role-grantable Cerbos permission — the exact kind of
  false signal the catalog exists to prevent.
- **`search:content:publish`** (search module) — no Cerbos enforcement exists; `ai-drafts.ts` has
  zero `authorize()` calls. It was declared ahead of an unbuilt feature.

**Why removal over catalog-as-is:** cataloguing either would require either (a) inventing a Cerbos
action with no real enforcement behind it — lying to the catalog — or (b) leaving it uncatalogued,
which is exactly what fails IAM-01d's validator, i.e. the boot-block the ticket told me to resolve,
not leave standing. Both module files carry an inline comment recording the ruling and the correct
forward path: mint the real Cerbos action + catalog entry first (additive, Phase 2+) when either
feature actually ships, then re-add the declaration — never the other order.
