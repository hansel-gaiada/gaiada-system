## 2. Table shape + indexes

```sql
CREATE TABLE org_unit_closure (
  tenant_id      uuid NOT NULL REFERENCES companies(id),
  ancestor_id    text NOT NULL,
  descendant_id  text NOT NULL,
  depth          int  NOT NULL CHECK (depth >= 0),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, ancestor_id, descendant_id)
);
CREATE INDEX ix_org_unit_closure_ancestors ON org_unit_closure (tenant_id, descendant_id, depth);
```

- One row per `(tenant, ancestor node id, descendant node id)`, with `depth` = tree distance.
- **Text node ids** (not uuid) — carries the same free-form id vocabulary as `user_roles.scope_id`
  (0100), `org_unit_memberships.unit_node_id` (0055), and `company_org_structure`'s own blob. No
  text↔uuid translation seam anywhere in the chain.
- **Self-inclusive at depth 0** — a node is its own ancestor. Deliberate, not a default: HIER-2's
  sketched Cerbos condition (`g.scopeId in request.resource.attr.unitAncestors`) needs to match a
  grant scoped directly AT the resource's own unit, not only at a strict ancestor above it.
  Documented in both the migration header and `org-unit-closure.ts`'s header.
- **Scope of the closure is the WHOLE tree**, not filtered to `department`/`division` kind. This
  was a deliberate design call, not an oversight — flagged explicitly for HIER-2 to confirm (§7
  below).
- **Two hot queries, both indexed:**
  - "all ancestors of node N" (what a resource carries for grant matching) — `WHERE tenant_id = $1
    AND descendant_id = $2`, served by the dedicated `ix_org_unit_closure_ancestors`.
  - "all descendants of node N" (the subtree a grant at N covers) — `WHERE tenant_id = $1 AND
    ancestor_id = $2`, served by the PRIMARY KEY's own leftmost prefix (`tenant_id, ancestor_id,
    descendant_id`) — no separate index needed.
- **RLS:** `FORCE ROW LEVEL SECURITY` + the standard `tenant_isolation` policy off the 0025
  `app_current_tenants()` helper — the same wall as `org_units` (0026) / `org_unit_memberships`
  (0055). Every column, index, and the PK itself lead with `tenant_id`.

## 3. The transactional PUT hook

New pure+I/O module: `platform-nest/src/core/org-unit-closure.ts`.

- `computeOrgUnitClosure(root: OrgNodeForWalk): ClosureRow[]` — PURE. Reuses `OrgNodeForWalk` from
  `dept-resolution.ts` (imported, not redefined) rather than writing a second tree-node type. Walks
  the tree once, emitting the full self-inclusive ancestor/descendant/depth set, with a
  deterministic nearest-wins tie-break for a malformed tree that repeats an id (mirrors
  `deriveBlobPlacements`'s own tie-break posture).
- `rebuildOrgUnitClosure(c, tenantId, root)` — I/O. `DELETE FROM org_unit_closure WHERE tenant_id =
  $1` then a single `unnest()`-based bulk `INSERT`, on the CALLER's client/transaction. Wholesale
  rebuild, not a diff — this is what makes "node moved" and "node deleted" trivially correct: there
  is no incremental-update branch that can miss an affected path or leave an orphan.
- `loadUnitAncestors` / `loadUnitDescendants` — thin read helpers for the two hot queries, provided
  for HIER-2 and exercised by this ticket's own tests; not wired into any Cerbos-facing code path
  (that wiring is HIER-2's).

Hook: `platform-nest/src/admin/company-admin.controller.ts::putOrg` now calls
`rebuildOrgUnitClosure(c, tenantId, structure.root)` immediately after the existing
`sweepMemberships(c, tenantId, structure.root)` call, inside the SAME `withTenants([tenantId],
...)` transaction as the blob write and the membership sweep. A closure-write failure rolls back
the blob write too — the closure can never disagree with the tree it describes, by construction
(same transaction, not "usually consistent").

Diff:
```
+ import { rebuildOrgUnitClosure } from "../core/org-unit-closure";
  ...
  await sweepMemberships(c, tenantId, structure.root);
+ await rebuildOrgUnitClosure(c, tenantId, structure.root);
  await emitEvent(c, tenantId, "org_structure", tenantId, "org_structure.updated", { ... });
```

per-tenant `set_config('app.current_tenant_ids', co.id::text, true)` guard 0055 uses, because

the same nearest-wins `MIN(depth)` dedup — documented in the migration header as intentionally
mirroring the TS function, same convention 0055/`dept-resolution.ts` already use for their own
backfill/runtime pair.

ambient tenant context") that:

   ambient tenant GUC set — exactly the production privilege model;
2. asserts the resulting row count is `> 0` and matches the row count produced when the same

## 5. Cross-tenant `node_id` collision — test result

Two independent tests, at two different layers, both green:

1. **`src/db/org-unit-closure.test.ts`** — seeds tenant A with node id `'shared-id'` carrying a
   real child (`'div-1-1'`), and tenant B with the SAME text id `'shared-id'` carrying NO children.
   Asserts: tenant A's `'shared-id'` has `'div-1-1'` as a descendant; tenant B's `'shared-id'` does
   NOT (tenant B's closure contains zero rows mentioning `'div-1-1'` at all); every row involving
   `'div-1-1'`, across both tenants' full closures, carries tenant A's id. **PASSED.**
2. **`src/admin/company-admin.test.ts`** — same collision, but driven through the REAL HTTP `PUT`
   handler against two different companies created via the normal fixtures (not hand-inserted
   rows), with two different admin users. **PASSED.**

Verdict: the ticket brief flagged this as "the most likely real bug" — it is not present. Isolation
holds because every query, every index, and the PRIMARY KEY itself lead with `tenant_id`, and
`FORCE ROW LEVEL SECURITY` makes a missing tenant context fail to zero rows rather than to another
tenant's rows.

## 7. Design decision flagged for HIER-2 to confirm

The closure covers **every node in the org-blob tree** (holding/company/department/division/
role/person), not filtered to `department`/`division` "unit" kind. Rationale (also in both the
migration header and `org-unit-closure.ts`'s header): a kind-filtered closure would need its own
copy of the unit-kind vocabulary, and that copy could drift from `person-scope.ts`'s own
`UNIT_KINDS` (untouched by this ticket, and explicitly not to be duplicated) or from the
`org_unit` scope shape CHECK (0100), which itself imposes no kind restriction. A full-tree closure
cannot disagree with either. Practical consequence: an ancestor/descendant list CAN contain a
`role`/`person` node id if one happens to sit on the path — harmless, because nothing in this
codebase ever mints a grant at a role/person node id, so those entries are never the left side of a
real comparison. **HIER-2 should read this before writing its Cerbos condition** — if it ever wants
"ancestors filtered to department/division only," that filter belongs in HIER-2's read helper (or a
`kind` column added to this table later), not retrofitted here without HIER-2's sign-off.

## 8. Rollout notes

- **Additive only.** New table, new module, one new call inside an existing transaction. No column
  changed, no existing table altered, no existing behavior changed for any caller other than
  `putOrg` (which now also writes closure rows — it already wrote membership-sweep rows in the same
  transaction, so this is the same risk shape as the existing TR-04 hook, not a new one).
- **No backward-incompatible deploy ordering required.** The table can be created and backfilled
  before, during, or after a `platform-nest` deploy that includes the `putOrg` hook change — an
  older running instance simply never reads/writes it; a newer instance reads/writes it from its
  first PUT after the migration lands. No cutover step, no flag.
- **Cost bound:** `company-admin.controller.ts`'s own `MAX_NODES = 300` bounds each tenant's
  closure to at most a few tens of thousands of rows, recomputed wholesale on every PUT (not a hot
  read path). Not a performance concern at this scale; flagged only so a future MAX_NODES increase
  re-checks this.
