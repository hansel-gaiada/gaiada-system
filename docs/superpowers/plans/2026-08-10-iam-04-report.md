## 1. The attribute shape passed to Cerbos

`cerbos.ts::principalPayload()` gained one additive field, `attr.perms`, alongside the pre-existing
`attr.grants`:

```ts
attr: {
  assurance: p.assurance,
  companies: p.companies,
  grants: p.roles.map((g) => ({ role: g.role, scopeType: g.scopeType, scopeId: g.scopeId ?? "" })),
  perms: (p.perms ?? []).map((g) => ({ key: g.key, scopeType: g.scopeType, scopeId: g.scopeId ?? "" })),
}
```

`p.perms` is IAM-03a's optional `PermissionGrant[]` — `{key, scopeType, scopeId}`, isomorphic to
`RoleGrant`. Defaulting to `[]` when absent means a mocked/synthetic `Principal` without `perms`
produces a valid, empty `attr.perms` (every `.exists()` in `derived_roles.yaml` evaluates false —
fail-closed, matching how `grants` already degrades for a roleless principal). Nothing else in
`principalPayload`/`resourcePayload`/`check`/`planResources` changed.

## 2. How the permission derived roles express scope

`derived_roles.yaml` gained an "IAM-04a" section, beside (not replacing) the role-name derived roles.
Baseline shape, one derived role per catalog permission key:

```yaml
- name: perm_pm_task_read
  parentRoles: ["user"]
  condition:
    match:
      expr: >-
        request.principal.attr.perms.exists(g, g.key == "pm.task.read" && (
          g.scopeType == "global" ||
          (g.scopeType == "company" && g.scopeId == request.resource.attr.tenantId)))
```

**Global covers everything; company covers exactly the company it was granted at.** Nothing
narrower or broader, per the ticket's own instruction — and deliberately matching
`principal.ts::principalHasPermission()`'s already-documented boundary: project/team cascades
(manager/member's project scope, team_lead's team scope) are **not** reproduced in the permission
arm. This is safe, not a coverage gap: every pre-existing role-name rule is untouched, so a decision
that depends on project/team scope is still made, just by the unmodified role arm rather than by a
new permission-arm path. Cerbos derived-role conditions have no access to the action under
evaluation (the same reason `module_staff`/`module_manager` string-compose from `resource.attr.module`
rather than from the action), so each permission key needs its own concretely-named derived role —
there is no single generic parameterized alternative.

One derived role got a **second, load-bearing clause**, discussed in §4: the five `perm_pm_task_*`
roles each exclude the exact `(scopeType, scopeId)` a `team_lead` grant occupies, by cross-checking
the pre-existing `attr.grants` array (already sent, unchanged) rather than trusting `attr.perms`
alone.

## 3. The two pilot policies — purely additive

Both `resource_pm_task.yaml` and `resource_hr_case.yaml` have **zero existing lines changed**. Every
new rule is an appended block; the original role-name rules (including both kinds' untouched
`platform_admin` wildcards) are byte-identical to before this ticket.

- **`resource_pm_task.yaml`**: five new single-action rules (`read`, `update`, `create`, `delete`,
  `manage`), each `derivedRoles: ["perm_pm_task_<action>"]`, condition `inTenant && notLow` —
  structurally identical to the two existing role-arm rules' own condition, just split one-action-
  per-rule so a principal holding only `pm.task.read` can never ride `pm.task.update` through a
  combined rule.
- **`resource_hr_case.yaml`**: eight new single-action rules, split into two tiers:
  - **Unconditional tier** (`update`, `delete`, `export`) — safe because no other role in this file
    reaches those three specific actions under a narrower condition.
  - **Self-scoped tier** (`read`, `create`, `cancel`) — mirrors the pre-existing member-self rule
    exactly, including its own `subjectUserId == principal.id` condition, carried on the new rule
    (not folded into the derived role, matching how `member` itself carries no self-check of its
    own).
  - **Deliberately NOT built**: an unconditional `read`/`create` mirror. Reason in §4.

## 4. The isolation proof, and the two real findings the pilot surfaced

**Positive, live probes** (against `gaiada-test-cerbos`, restarted after every edit, verified via
`docker inspect --format '{{.State.StartedAt}}'` postdating each edit):

```
principal: {roles: [], perms: [{key:"pm.task.read", scopeType:"company", scopeId:"T1"}]}
  -> read: EFFECT_ALLOW, update: EFFECT_DENY   (fires with ZERO role held; correctly scoped to
                                                 exactly the action its key grants, no bleed)
same principal, resource.tenantId = "T2"        -> EFFECT_DENY (no cross-tenant leak)
perms=[{key:"hr.case.update", scope:"company:T1"}], no roles -> update: ALLOW, delete/export: DENY
perms=[{key:"hr.case.read", scope:"company:T1"}], no roles, subjectUserId == principal.id
                                                 -> ALLOW
same, subjectUserId == "someone-else"           -> DENY (self-check enforced, not bypassed)
```

These are backed by 16 automated tests in `cerbos-permission-dual-match.test.ts`, every one of which
grants the permission **without** the corresponding role (`roles: []`) — so the role arm cannot
possibly be the one answering. A second block re-asserts the role arm decides identically to its
pre-existing behavior with **empty** `perms`, proving the additions are additive, not replacements.

**Finding 1 — hr_case's flat `perms` cannot distinguish self-scoped from unconditional reach for the
same key.** `member`'s `role_permissions` bundle (migration 0094, unrelated to this ticket, already
seeded) contains `hr.case.read`/`create`/`cancel` — copied in from **member's own self-only rule** in
this same file, because 0094/the parity suite's bundling methodology treats a resource-instance
condition (self-ownership) as "satisfied" when computing reach. That bundle entry is
indistinguishable, once flattened into `perms`, from `company_admin`/`module_staff`/`module_manager`
holding the identical key **unconditionally**. Building a blanket unconditional mirror for
`read`/`create` would have silently let any `member` read or create *any* hr_case in the tenant, not
just their own — a real widening. **Resolution:** those two actions get only the self-scoped mirror
(which re-imposes the exact same restrictive condition rule6 already uses), never an unconditional
one. `update`/`delete`/`export` have no such ambiguity (no other role reaches them under a narrower
condition) and got the unconditional mirror safely.

**Finding 2 — a REAL regression, caught and fixed before landing, not theoretical.** `team_lead`
appears in `resource_pm_task.yaml`'s role list alongside `company_admin`/`manager`/`member`/`viewer`,
so migration 0094 bundled it `pm.task.*` too (verified empirically against the live DB: `SELECT ...
FROM role_permissions WHERE role='team_lead' AND key LIKE 'pm.task%'` returns all five keys). But
`team_lead`'s own derived role matches **only** `scopeType == "team" && scopeId ==
resource.attr.teamId`, and a pre-existing adversarial test
(`src/modules/pm/pm-adversarial-authz.test.ts`, its own "REAL FINDING") already pins that
`pm.controller.ts` **never sets** `resource.attr.teamId` — so `team_lead` is provably unreachable on
`pm_task` at *any* grant scope, yet its bundle row exists regardless. A `team_lead` grant made at
**company** scope (the schema permits granting any role at any `scope_type`) produced a `perms`
entry indistinguishable from a legitimate `company_admin`/`manager`/`member`/`viewer` grant at that
same scope. My first cut of the `perm_pm_task_*` derived roles (plain global-or-company cascade)
initially **flipped that exact pinned test from 403 to 200** — a real decision change, caught by
running the existing suite, not invented for this report.

**Fix, entirely within owned files, no schema/migration change:** each `perm_pm_task_*` derived role
now also excludes the exact `(scopeType, scopeId)` a `team_lead` grant occupies, by checking the
pre-existing `attr.grants` array:

```yaml
request.principal.attr.perms.exists(g, g.key == "pm.task.read" && (
  (g.scopeType == "global" &&
    !request.principal.attr.grants.exists(x, x.role == "team_lead" && x.scopeType == "global")) ||
  (g.scopeType == "company" && g.scopeId == request.resource.attr.tenantId &&
    !request.principal.attr.grants.exists(x, x.role == "team_lead" && x.scopeType == "company" && x.scopeId == g.scopeId))))
```

This can never cause a real access **loss**: if the same principal also holds a genuinely qualifying
role at that scope, the unmodified role-arm rules grant it directly regardless of what this derived
role decides — the exclusion only removes a permission-arm path that was never backed by real
reachability. `hr_case` has no analogous hazard: `module_staff`/`module_manager`'s attribute
dependency is `resource.attr.module`, which every real HR handler sets to the literal `"hr"` (grepped
across `hr.controller.ts`/`loans.controller.ts` — confirmed, no exceptions), so those bundle entries
are trustworthy, unlike `team_lead`'s `teamId` on `pm_task`, which is never populated.

After the fix: `pm-adversarial-authz.test.ts`'s pinned test is green again, and a new test in
`cerbos-permission-dual-match.test.ts` pins the exact scenario (company-scope AND global-scope
`team_lead` grants both correctly denied; a principal holding `team_lead` **plus** a genuinely
qualifying role is correctly still allowed via the untouched role arm).

## 5. The two files touched outside the primary ownership list

`role-permission-parity.db.test.ts` (IAM-02b's file) and `scripts/generate-role-bundles.mjs`
(IAM-05b-1's file) both statically re-parse every policy file's `derivedRoles` lists and **throw** on
any name they don't recognize (by design — fail loud on drift). Adding `perm_*` derived roles to
`derived_roles.yaml` made both throw immediately, turning IAM-02b's 22-test gate red on its very
first run against the edited policies. Neither file is in my owned list, but my ticket's own
verification bar is "parity suite green... at every step," so leaving it red was not an option.

**Fix (one line + comment, in each file):** skip `perm_*`-prefixed derived roles when building
per-role coverage — they match on `attr.perms`, not `attr.grants`, so they are not attributable to
any of the 18/20 named roles either file measures. This is semantically inert (never changes what
either file concludes about role-name reachability) and is proven so: `role-permission-parity.db.test.ts`
is 22/22 green after the change, and `generate-role-bundles.mjs --check` reports byte-identical
regeneration. Both edits were applied carefully around a live concurrent edit to the same files (a
different session landed IAM-04c-1's `role-permission-parity.db.test.ts` rewrite and IAM-02g's
`generate-role-bundles.mjs` extension to 20 roles mid-session) — re-verified after each collision that
my one-line skip survived and the file's own gate still passed.

## 8. Blockers / follow-ups (not this ticket's remit)

- **IAM-04-ROLLOUT must budget for Finding 2's pattern, not just Finding 1's.** Any kind whose
  role-name rule list mixes a "pure scope" derived role (company_admin/manager/member/viewer — scope
  only) with an "attribute-dependent" one (team_lead/module_staff/module_manager/module_approver/
  client — scope **plus** a resource attribute the flat `perms` array cannot corroborate) needs the
  same treatment: either confirm the dependent attribute is reliably populated for that kind (as
  verified here for `hr_case`'s `module`), or add the `attr.grants`-based exclusion demonstrated here
  for `team_lead`/`pm_task`. This is a real, previously-latent gap in the `role_permissions`
  bundling methodology (0094/0098, not this ticket's files) — harmless until IAM-04 made `perms` a
  live decision input, now the first thing any future migration to permission-matching must check
  per kind. Recommend IAM-04-ROLLOUT's kickoff include a scripted pass: for every kind, does its
  role list mix scope-only and attribute-dependent derived roles, and if so, is the attribute
  reliably populated by every real handler for that kind?
