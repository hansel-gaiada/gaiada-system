## Headline finding

**Zero net-new assistant write tools exist to register.** The assistant broker's (ASST-17) real

read-only in its entirety. The ticket's own escape hatch applies: *"If the broker's proposable

that makes it a checked fact rather than a claim.

## Evidence chain (all read directly from the current checkout, cited by file:line)

1. `platform-nest/src/modules/assistant/broker.ts:408-411` — `ASSISTANT_AGENT_TOOLS` is the
   broker's **entire** tool universe. `runToolTurn` (same file, ~line 592-601) refuses any `agent`
   argument that isn't a key of that map, returning `errorKind: "unknown_agent"`, **before contacting
   the runner at all**. Today the map has exactly two entries, both read-only:
   ```
   "status-reporter": ["projects.list", "tasks.list"],
   "approvals-chaser": ["agency.pendingApprovals"],
   ```
   Neither AgentDef the broker can drive holds any write tool, high or low.

2. `ai-agents/src/specialists.ts:29-65` — the repo's ONLY write-capable AgentDef, `taskTriager`
   (`tasks.update`, `low_write`), lives in `writeSpecialists`, not `specialists`. `ASSISTANT_AGENT_TOOLS`
   names neither map — the broker cannot reach it. So even the one write ai-agents can do anywhere is
   structurally unreachable from a chat turn.

3. `ai-agents/src/agent-write-guard.test.ts:92,108` — `RERUN_CAPABLE_HIGH_WRITES` (the CI-enforced
   allowlist of tool names **any** AgentDef anywhere may declare `high_write`) is `[]`. The guard test
   (same file, "declares `high_write` only for tools on RERUN_CAPABLE_HIGH_WRITES") structurally fails
   the ai-agents build the moment any AgentDef declares a `high_write` outside that empty allowlist. A
   `high_write` is the **only** thing that files an `origin='agent'` proposal
   (`ai-agents/src/agent.ts`'s write gate) — a `low_write` executes immediately and never reaches
   `automation_approvals`/this registry at all.

Chained: broker → only 2 read-only AgentDefs reachable → CI guard forbids any AgentDef anywhere from
holding an ungated `high_write` → no `origin='agent'` proposal can exist today, from the assistant or
otherwise. The assistant-proposed write surface is empty by construction, and by a **different
project's** CI guard this ticket correctly does not touch.

## What "reuse D14-15's PM entries" means, concretely

`pm.createTask` / `pm.createDoc` are already registered in
`platform-nest/src/core/approval-executables.ts` (D14-15) and needed **zero changes**. New in this
ticket: proof that they work for an `origin='agent'` proposal specifically (D14-15's own test file
only exercises `origin='automation'`), since that is the origin every assistant-filed write would
carry. See test evidence (C) below — the entries are origin-agnostic, so the moment some future
AgentDef the broker can drive proposes one of these two tools, no registry change is needed.

## Why `resource_mcp_tool.yaml` is unchanged (the two-list discipline, applied correctly)

The ticket instructs extending "D14-13's policy-side executable list in the same change." Extended:
**by zero entries**, and that omission is itself verified correct, not merely asserted:

- The grant-aware impact conjunct in `resource_mcp_tool.yaml` only matters for
  `request.principal.attr.isAutomation` (n8n) principals — for any other principal (including every
  `origin='agent'` re-drive, which is OBO for the platform user, never n8n) the `!isAutomation`
  disjunct is `true` and the whole impact term is already satisfied. **No assistant-proposed write can
  ever need this list**, because assistant proposals are never `origin='automation'`.
- Separately and independently: `pm.createTask`/`pm.createDoc` are `impact:"low"` at the hub
  (`mcp-hub/src/pm-tools.ts`), so even for an automation caller the `impact == "low"` disjunct already
  satisfies the conjunct without reaching the grant term — this is why D14-15 itself correctly never
  touched the Cerbos list either (confirmed: `resource_mcp_tool.yaml`'s executable list is still
  `["deploy.staging", "deploy.production"]` only, unchanged since D14-13).

A dated note recording this evaluation was added to `resource_mcp_tool.yaml`'s header (see Files
touched) so a future reader doesn't have to re-derive it.
