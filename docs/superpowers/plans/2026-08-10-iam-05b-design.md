# IAM-05b design ruling — what the UI mirror generates, and what it must never generate

**Status:** PLANNED (design ruling; no code changed). Measured from source 2026-08-10.
**Parents:** `2026-08-10-iam-phase1-tickets.md` (IAM-05b, §1a DR-1/DR-2, FIX-2) ·
`2026-08-10-iam-01a-02a-analysis.md` (Ruling 1) · `2026-08-10-permission-catalog.md` (the 215) ·
`2026-08-10-permission-groups.md` (the 75) · `2026-08-10-identity-rbac-program.md` (D-1..D-11).
**Question resolved:** the original IAM-05b said "generate `platform-ui/src/lib/rbac.ts` from the
catalog" without saying which of THREE vocabularies (215 permissions / 75 groups / 34 capabilities)
the UI should speak. This doc rules it, from call-site evidence, and rewrites the ticket.

---

## 0. Verdict, in one paragraph

**`can()` keeps speaking capabilities. `rbac.ts` stays hand-authored. What gets generated is the
proof, not the file:** a hand-authored, type-pinned **capability→permission map** (each of the 34
capabilities declared as a named set of catalog permissions with explicit check semantics), a
machine-generated, checked-in **role→permission-bundles export** from the catalog parse, and a
generated **capability-axis parity test** that asserts, for every `(role, capability)` pair, that
`ROLE_CAPS` agrees with the Cerbos-derived bundles — with a documented-exception register in the
exact pattern `rbac-cerbos-parity.test.ts` already proved on the role axis. This kills the drift
class (the actual goal) with **zero changes to any of the ~188 capability-asking call sites**, and —
the decisive strategic point — the map is not scaffolding: it is the table that later lets `can()`
evaluate **custom roles** (D-1) from resolved permissions (IAM-05c's payload), which role-keyed
`ROLE_CAPS` can structurally never do. Naive regeneration of `rbac.ts` from the catalog is
**rejected**: it renames the API under 149 literal call sites, and it would discard the file's
comment record — which is the institutional memory of every judgment call DR-1/DR-2/FIX-2 just paid
for. The phase exit criterion #4 ("rbac.ts generated from the catalog, not hand-written") is
**amended accordingly** (§6).

## 2. Q1 — what vocabulary should `can()` speak? Capabilities. Here is why the alternatives lose.

### 2.1 Fine-grained permissions (the 215) — rejected as the call-site vocabulary

- **The rename is ~188 sites of per-site policy archaeology.** 93 of the 149 literal sites (62%)
  sit on the four biggest capabilities (`search.manage`/`pm.manage`/`hr.manage`/`company.manage`),
  each of which names a **multi-permission tier** (e.g. `search.manage` ≈ the 21-permission draft
  tier the groups doc measured). Each site would need a judgment call about *which* fine-grained
  permission it "really" means. That is a high-regression migration purchasing nothing the parity
  chain (§3) doesn't already purchase.
- **Many sites gate surfaces, not actions.** Nav items, page sections, "render the edit UI at
  all" — the honest question is "does this user sit in the tier this surface serves", and a single
  `(kind, action)` is a lie at those sites. The engagements page shows keyword+audit+campaign
  affordances behind one question; forcing it to ask `search.keyword.create` would under-ask.
- **The server and the UI are answering different questions.** IAM-05a's server-side
  `can(permission, scope)` is per-endpoint, where one call site *is* one `(kind, action)` — there,
  fine-grained is correct. The UI asks "should this surface offer this family of affordances".
  Same word, different granularity, by design — exactly Ruling 1's reasoning, applied to gating
  instead of authoring.
- **Convergence happens anyway, without a rename.** Several capabilities already have singleton
  permission sets (`org.edit` → `core.org_structure.update`; `approvals.retry`;
  `search.scope.write`; `search.ledger.admin`; `checkin.excuse`). Where a duty is naturally one
  action, the capability *is* the permission under a stable name.

### 2.2 Permission groups (the 75) — rejected in two sentences

Groups are the **authoring** UX for composing roles; they are not part of the grant chain (a role
persists as a permission set — a custom role can hold 8 of a group's 9 permissions via advanced
picks, making "does the user have the group?" unanswerable). Gating a button on `Everyday
Collaboration` is a category error, and 75 names optimized for HR readability are the wrong shape
for 188 code sites.

### 2.3 Capabilities — kept, with the definition FIX-2 already discovered

FIX-2's correction criterion is the formal definition this file needed all along: **a capability is
a named set of catalog permissions whose backing policies grant the same role tier** ("all three
policies carry the IDENTICAL role list" was the stated evidence for `pipeline.write`). DR-1's
collateral happened because `approvals.decide` violated that invariant invisibly — nothing checked
it. The fix is to make the invariant *declared and checked* (§3), not to abandon the vocabulary.

## 3. Q2 — what pins capabilities to the catalog: hand-authored map, machine-checked, per-capability semantics

### 3.1 Why pure derivation fails — three worked counter-examples

Could `ROLE_CAPS` be *generated* as `{c : bundle(role) ⊇ P(c)}` from the catalog + bundles? No —
tested against the corrections this program just made:

| Case | Under strict `⊇` (ALL) derivation | Verdict |
|---|---|---|
| `agency_approver` × `approvals.decide` | Its bundle holds 1 of the 3 decide pairs (`agency.approval.approve` only) → derivation **strips its only capability**, reverting DR-2b | derivation wrong |
| `manager` × `company.manage` | Manager holds the `integration_connection` company tier but not `company.update`/`billing.invoice.*` → derivation strips it, reverting the documented Gap-3 judgment ("show it, the server still refuses" — the safe direction, chosen deliberately) | derivation wrong |
| `group_executive` × everything | `ALL` in the mirror vs 118/230 in Cerbos — pinned inert by Ruling 4 (sole holder is a test seed), deleted by D-7 in Phase 3 | derivation "fixes" something the owner already ruled on |

And the mirror direction (ANY semantics, `bundle ∩ P ≠ ∅`) breaks differently: it would re-grant
nothing wrong above but cannot express `pipeline.manage`'s member-exclusion honestly. **No single
derivation rule reproduces the hand-authored table** — because the table encodes decisions, not
data. Ruling 1 said the same thing about authoring; this is its gating-side echo.

### 3.2 The design: declared sets + declared semantics + a checked register

Three artifacts (full ticket spec in §5):

1. **`platform-ui/src/lib/rbac-capability-map.ts`** — hand-authored, type-pinned:
   ```ts
   export const CAPABILITY_MAP = {
     "pipeline.write": {
       permissions: ["core.pipeline_run.create", "core.pipeline_run.update",
                     "core.pipeline_stage.create", "core.pipeline_gate.create"],
       semantics: "all",   // role must hold EVERY member permission (the FIX-2 tier invariant)
     },
     "approvals.decide": {
       permissions: ["core.automation_approval.decide", "agency.approval.approve",
                     "core.pipeline_gate.decide"],
       semantics: "any",   // "may decide SOMETHING here" — rationale + DR-2b ref in a comment
     },
     // … all 34 …
   } as const satisfies Record<Capability, CapabilityDef>;
   ```
   `Record<Capability, …>` + `satisfies` makes **both** directions a compile error (a capability
   without a map entry; a map entry for a non-capability) — construction-level, no codegen, no new
   dependency, exactly the Gap-1 lesson ("one list, by construction"). The permission *sets* are
   design judgment and stay hand-authored — but they are seeded almost mechanically, because
   `rbac.ts`'s own capability comments already cite the exact backing policies for every entry
   added since the 2026-08 audits.
   - Default semantics is `all`. `any` requires a written rationale in the entry; today exactly
     two earn it: `approvals.decide` (DR-2b's deliberate partial coverage) and `company.manage`
     (the Gap-3 safe-direction judgment). An `any` capability deliberately trades per-surface
     precision for "visible refusal, never silent hiding" — the tie-break rule the codebase
     already adopted; anyone wanting precision splits the capability (the FIX-2 playbook).

2. **`platform-nest/src/rbac/role-permission-bundles.json`** — machine-generated by the same parse
   pipeline that produced `permission-catalog.json` and fed migration `0094`: role → sorted
   catalog keys (18 roles, 925 pairs, wildcard-expanded). Checked in, diff-reviewed, and pinned by
   two platform-nest tests: *regeneration produces no diff*, and *JSON ≡ the DB `role_permissions`
   seeded by 0094* (join on `permissions.key`). Chain anchor: IAM-02b's parity suite already
   proves those bundles ≡ live Cerbos decisions, with demonstrated teeth.
   **This is where the review surface the original ticket wanted actually lands:** a policy change
   regenerates the bundles, and the diff shows exactly which role gained/lost which permission —
   far more reviewable than a diff of a generated UI file.

3. **`platform-ui/src/lib/rbac-capability-parity.test.ts`** — the generated proof (sibling and
   structural twin of the existing role-axis test, which already reads platform-nest files by
   relative path — established precedent, no new mechanism). Asserts, from data, never hand-lists:
   - **Map well-formedness:** `Object.keys(CAPABILITY_MAP)` ≡ `CAPABILITIES` (belt to the type
     system's braces); every referenced key ∈ the catalog's 215 grantable; **zero** intersection
     with the 15 relationship-class keys (the same check the groups doc ran).
   - **The core assertion — for every `(role, capability)`:**
     `ROLE_CAPS[role] ∋ capability ⟺ semanticsEval(bundles[role], MAP[capability])`,
     except entries in the exception register. A failure names the pair and the direction
     (OVER-claim: dead button; UNDER-claim: hidden working feature — the dangerous one).
   - **Exception register, guarded:** each entry = `{role, capability, direction, reason,
     decisionRef}`; a register entry that is no longer a real divergence **fails** (the
     guard-the-guard pattern from `DELIBERATELY_OUTSIDE_ROLE_CAPS`). Known-today content:
     `group_executive` excluded wholesale (Ruling 4 / D-7; drop the exclusion when Phase 3 deletes
     the role) — everything else is expected to pass under its declared semantics or go to the
     owner (§3.3).

### 3.3 First-run adjudication — the register findings become mechanical verdicts

The first green run *pins* today's judgment calls (as DR-1's own pin test did). Reds expected on
first run, each already documented in the drift register and each routed to a **decision**, never a
silent fix (the phase's standing rule):

- `it_admin` × `company.manage` (drift finding #7 — over-claim, 1 live holder): under `any`
  semantics it stays red → owner decides remove-or-register.
- `company_admin` × `appraisal.read` (finding #6): the map + bundles adjudicate it precisely.
- `hr_staff` family (finding #2, 0 holders): mechanically resolved by whatever
  `P(hr.manage)`/`P(hr.view)` contain — the test turns a prose register into a verdict.

### 3.4 Why the map is load-bearing, not scaffolding — the Phase-4 argument

D-1's whole point is roles-as-data. A company_admin composes "Marketing Coordinator" in IAM-20;
**`ROLE_CAPS` cannot know it exists** — role-keyed capability tables are structurally incompatible
with custom roles. The end-state `can()` is:

```
can(me, cap, company) = semanticsEval(effectivePermissions(me, company), CAPABILITY_MAP[cap])
```

where `effectivePermissions` is IAM-05c's payload (server truth, cached, session-version
invalidated). That swap happens **inside `can()` once**, and the ~188 call sites never change.
The capability map authored by this ticket is the exact evaluation table that swap consumes. So
IAM-05b is not "make the mirror honest" only — it is the first half of making the mirror
**custom-role-capable**, which nothing else in Phase 1 provides.

## 4. Q4 — the IAM-07b drift test: "three-way" is the wrong shape; it is a pinned chain

With three vocabularies at three granularities there is no single three-way diff. The honest shape
is a **chain of pairwise pins**, each mechanical, each already proven or specified above:

```
Cerbos policies ⟷(1) permission-catalog.json ⟷(2) DB permissions (0093)
      ⟷(3, IAM-02b live parity) role_permissions (0094) ⟷(4) role-permission-bundles.json
      ⟷(5, NEW 05b test) CAPABILITY_MAP + ROLE_CAPS ⟷(6, tsc) Capability type ⟷ 188 call sites
      (role axis: derived_roles.yaml ⟷ Role union — exists, rbac-cerbos-parity.test.ts)
```

| Link | Pin | Status |
|---|---|---|
| 1 | policy parse ≡ catalog JSON (230=230, both directions) | run manually in the wave-3 alignment audit — **IAM-07b makes it CI** (platform-nest test) |
| 2 | catalog JSON ≡ DB rows | 0093's three-way asserts exist — IAM-07b keeps them in CI |
| 3 | bundles ≡ live Cerbos decisions | **exists** — IAM-02b, teeth proven |
| 4 | bundles JSON ≡ DB `role_permissions`, regen no-diff | NEW — IAM-05b-1 |
| 5 | map+`ROLE_CAPS` ≡ bundles under declared semantics | NEW — IAM-05b-3 |
| 6 | every call site's string ∈ `Capability`; map exhaustive over it | tsc, by construction |
| role axis | raw Cerbos roles ≡ `Role` union | **exists** |

IAM-07b's rewritten job: promote link 1 to a CI test, verify links 2–5 are green in CI on one
commit, assert the chain has **no unpinned link** (a meta-test enumerating the six), and document
the chain in the IAM-07a contract doc. Module-declaration validation (IAM-01d's boot-time
fail-closed check) already guards the module axis and stays as-is. One deliberate non-goal: no pin
from capabilities to *groups* — groups sit above the catalog for authoring and already carry their
own validation (`build-groups.mjs` checks + the planned groups drift test); tying them to the UI
mirror would couple two layers Ruling 1 explicitly separated.

## 6. Q5 — migration path: the corrections are preserved by construction

DR-1 (manager without `approvals.decide`), DR-2a (`member`/`viewer` + `people.directory`), DR-2b
(`agency_approver`'s one capability), FIX-2 (`pipeline.write`/`pipeline.manage`/`webdev.provision`
splits, `viewer` excluded from `pipeline.write`), Gap-2 (`team_lead` sweep) — **none of these are
regenerated, because nothing regenerates `ROLE_CAPS`.** The map is authored *to make today's
mirror pass* under declared semantics; spot-proofs done for this ruling: `pipeline.write` under
`all` reproduces member ✓ / viewer ✗ / team_lead ✗ exactly; `approvals.decide` under `any`
reproduces manager ✗ (DR-1) and `agency_approver` ✓ (DR-2b); `platform_admin: ALL` becomes
*consistent* rather than an over-claim, since every map set ⊆ the 215 ⊆ its reach — Finding A's
mirror concern dissolves once the map can only reference grantable keys. Where the mirror genuinely
cannot pass (§3.3's three known findings), the test forces an owner-sighted decision — which is the
program's stated policy for drift, now mechanized. The first green run pins everything, exactly as
DR-1's regression test pinned that single decision.

**Amendment required to the phase doc** (`2026-08-10-iam-phase1-tickets.md` §4, exit criterion 4):
replace "`rbac.ts` generated from the catalog, not hand-written" with "`rbac.ts`'s capability model
is **pinned to the catalog by a generated parity chain** (capability map + bundles export + parity
tests); the file itself stays hand-authored, and every future divergence either fails CI or appears
as an explicit register entry in the same diff." The original wording's *motive* (kill
hand-maintained-parallel-list drift) is fully served; its *mechanism* was named before anyone
counted the call sites.
