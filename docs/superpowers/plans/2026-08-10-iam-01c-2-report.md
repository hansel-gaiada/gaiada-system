## 3. Migration — `platform-nest/migrations/0092_user_roles_global_scope_unique.sql`

Ledger check at authoring time: `ls migrations | sort | tail` showed head `0090_webdev_provisioned_
sites.sql` with `0091` reserved for a concurrent agent (per the coordinator's instruction) and `0092`
genuinely free — confirmed again after the concurrent agent's `0091_iam_02d_ungrantable_roles.sql`
landed mid-session (it only seeds `roles` rows — `team_lead`/`viewer`/`it_manager`/`it`/
`search_staff`/`search_manager` — and touches nothing this ticket owns; no interaction, re-verified
by re-running the test suite after it landed). `0092` was and remains free.

**What it does, in order, inside one transaction:**
1. Maps every duplicate GLOBAL-scope grant (`scope_id IS NULL`, same `user_id`+`role_id`+
   `scope_type`) to its canonical survivor — the **oldest row, by id** (UUIDv7 ids are
   creation-ordered, same convention 0073 used for the analogous `roles` dedupe).
2. **Fails loudly** (`RAISE EXCEPTION`) if a duplicate carries a `managed_by` that conflicts with an
   already-non-null, different `managed_by` on its survivor — a genuine data conflict that needs a
   human decision, not a silent pick-a-side. (Not expected to fire: today's 4 live duplicates all
   have `managed_by IS NULL`.)
3. Promotes a duplicate's `managed_by` onto the survivor when the survivor doesn't already have one
   (preserves the reconciler-owned marker per 0026 §D, per the ticket's instruction).
4. Deletes the losers — and **asserts the affected row count via `GET DIAGNOSTICS`** against the
   expected count from the dedupe map, raising and rolling back the whole transaction on any
   mismatch, rather than assuming the DELETE did what the map implied.
5. Adds `CREATE UNIQUE INDEX user_roles_global_scope_uniq ON user_roles (user_id, role_id,
   scope_type) WHERE scope_id IS NULL` — closes the recurrence gap.
6. Final assertion: zero duplicate `(user_id, role_id, scope_type)` groups remain among
   `scope_id IS NULL` rows.

No repoint step for `service_grant_claims.user_role_id` (a plain, non-cascading FK): confirmed live
that zero claims reference any `scope_id IS NULL` `user_roles` row, and structurally impossible under
the current write path (`service-reconciler.ts` only ever inserts `user_roles` with `scope_type =
'company'` and a real `scope_id` — grepped and read directly, never `'global'`). If this ever became
nonzero, the DELETE would fail loudly with a foreign-key violation — the correct outcome, not
something to migrate around silently.

The pre-existing 4-column `UNIQUE (user_id, role_id, scope_type, scope_id)` constraint is **left in
place**, matching 0026's own A2 ruling ("don't widen uniqueness") — the new index only closes the
slice that constraint was never able to enforce; it does not add or change columns.

## 5. Risk flagged — NOT fixed here (outside this ticket's file-ownership scope)

`admin-identity.controller.ts`'s `assignRole` handler (`POST /:tenantId/users/:userId/roles`) inserts
with a **targeted** `ON CONFLICT (user_id, role_id, scope_type, scope_id) DO NOTHING`. A targeted
arbiter only suppresses a violation detected via *that exact index*. After 0092, a repeat grant of an
already-held **global** role still never trips the named 4-column arbiter (same NULL reason as
always) — so the INSERT now hits the **new** partial index instead, which is not the named arbiter,
and Postgres raises a real, unhandled `23505` instead of the endpoint's current graceful
"already-granted, adopt-if-reconciler-managed" flow (lines ~282-299 of that file).

- `testing/fixtures.ts`'s `grantRole()` (used by `seed:agency` and most test fixtures) is
  **unaffected** — confirmed by test (b)(2) above — because its `ON CONFLICT DO NOTHING` has no
  target, which Postgres treats as a catch-all over every unique constraint on the table.
- The one affected call site is the HTTP `assignRole` endpoint's **global-scope branch
  specifically**. Non-global grants (company/team/project/record, all with a real `scope_id`) are
  untouched by the new partial index and keep working exactly as before.
- This is precisely the endpoint a forthcoming role-assignment UI (IAM-05b/06) would drive to
  re-grant an existing global role. **Recommend a same-wave follow-up**, mirroring how 0073 was
  paired with `createRole()`'s `ON CONFLICT (name) WHERE company_id IS NULL` update: branch the
  `assignRole` `ON CONFLICT` target on `scopeType === 'global'` (target the new partial index
  explicitly, or drop to an untargeted `DO NOTHING` for that branch), before this migration ships to
  a database driving a live role-assignment surface. Not touched here — `admin-identity.controller.ts`
  is outside this ticket's owned files, and three other agents are working in this checkout.

## 6. Rollout notes

- **Additive-only, no data-shape change** for any consumer: the migration only removes exact
  duplicate rows (never a row an app path is relying on individually) and adds an index. No column
  changes, no widened grants, no weakened RLS (the table has none).
- **Deploy order**: no special sequencing needed beyond the normal migration runner — `0092` runs
  once, in ledger order, as part of the next `platform-nest` boot/deploy. It is idempotent
  (`CREATE UNIQUE INDEX IF NOT EXISTS`, `NOT EXISTS`-shaped dedupe map) and safe to re-run/no-op if
  ever re-applied to an already-deduped database (the ledger mechanism prevents that in practice,
  but the SQL itself is also safe under a manual re-run).
- **Backfill**: none required beyond what the migration itself performs — the "backfill" here IS the
  one-off dedupe, executed transactionally with the index creation, in the same file, per the
  ticket's own framing.
- Once deployed, re-running the exact live query in §1 against `gaiada_platform` should show exactly
  2 rows (one per elevated account) instead of 4 — worth a manual live SELECT-only spot-check after
  the next deploy, since this migration was never run against that database here.
