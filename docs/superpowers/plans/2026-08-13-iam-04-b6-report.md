## 2. Why `portal` and 5 of 8 social kinds could not be mirrored today — read this before re-attempting either

### 2.1 `portal` — the client-boundary STOP, hazard #3 exactly

The ticket's own hazard #3 says: *"`portal` is the CLIENT-facing surface... If `portal`'s rules
cannot be mirrored without changing a client-side decision, STOP and report."* That is exactly
what happened, discovered by running the gates the ticket named, not by inspection:

`permission-arm-hazard-scan.test.ts`'s Pattern C (IAM-SEC-03, widened IAM-SEC-04) scans **every**
`EFFECT_ALLOW` rule (wildcard or not) for a role whose own derived-role condition is
scope-narrower-than-"global-or-company". Run UNSCOPED, BEFORE any edit, it already reports:

```
{ "kind": "portal", "role": "client", "reason": "missing-scope-branch" }
```

`client`'s condition (`derived_roles.yaml`) matches `scopeType == "company" && scopeId ==
tenantId` **only** — no global branch — structurally identical to the `platform_admin` wildcard-
bleed shape IAM-SEC-02/03 closed, just in the OPPOSITE scope direction (narrower than implied,
not wider). The test's own "REACHABILITY (other-narrow direction, IAM-SEC-04)" assertion is:

> "no company/org-unit/attr-narrower-than-global role is named in a kind that ALREADY has a wired
> `perm_*` permission arm ... STOP wiring that kind's permission arm and report this, do not tune
> the predicate to make it pass."

Today this passes ONLY because `kindsWithPermissionArm()` doesn't yet include `"portal"` (no
`perm_*` rule exists there). **Verified empirically, not just reasoned:** a candidate
`perm_portal_read` rule (company-scope-only condition, faithfully mirroring `client`'s own reach)
was added to a scratch copy, the test suite was re-run, and this exact assertion flipped red.
Reverted before anything shipped. This is the **identical mechanism** that blocked
`report_document`/`appraisal`+`org_unit_lead` in IAM-04-B5 — that ticket's own report already
named the shape as unfixable without inventing a new mitigation mechanism, out of remit for a
rollout ticket. The same holds for `client`+`portal` here.

**What this means concretely:** even a hand-crafted, scope-faithful mirror (company-scope-only,
matching `client`'s own condition exactly, which I built and probed successfully in isolation — see
§5) is invisible to this static gate's coarse, kind-scoped check. The gate does not distinguish "a
faithful mirror" from "a naive one" — it flags the mere co-existence of a scope-narrower role and
ANY permission arm on the same kind, because a **future** edit to the mirror could silently widen
it and nothing would catch that regression without this rule. Loosening the gate to let `portal`
through would remove exactly the protection IAM-SEC-04 was built to add, for the one kind where the
narrower role is the client-facing boundary itself — the highest-stakes place to loosen it. **I did
not weaken the gate, invent a workaround, or wire a mirror anyway.** `resource_portal.yaml` gets a
comment-only change documenting this; the file's own rules are byte-unchanged.

**This needs an owner/architect decision, not an engineering workaround**: either (a) design a
`GLOBAL_ONLY_ROLES`-shaped guard for the OTHER-narrow direction (an action-scoped, not kind-scoped,
version of the check — non-trivial, since it requires proving the SPECIFIC mirrored action isn't
one the narrower role also holds, which the DB bundle doesn't record provenance for), or (b)
decide `portal` stays role-name-only permanently. Recommend filing this as its own ticket rather
than re-attempting it inside a rollout batch.

### 2.2 The 5 fully-unmirrored social kinds — no code to confirm against

`resource_social_account.yaml`/`resource_social_client_review.yaml`/`resource_social_inbox.yaml`/
`resource_social_report.yaml` all share the identical structure: every action is ALSO held by
`social_manager`/`social_staff` via `module_manager`/`module_staff` (a `resource.attr.module`
attribute gate). The "confirm-reliable" mitigation IAM-04-REG2 established for this exact shape
(`hr_case`/`hr_record`/`agency_approval`/9×`search_*`/`webdev_change_request`/
`webdev_provisioned_site`) requires grepping every REAL `authorize()` call site and confirming the
module literal is hardcoded, never caller-supplied. For these 4 kinds, **there is no call site to
grep** — tree-wide search for `kind: "social_account"` / `"social_client_review"` /
`"social_inbox"` / `"social_report"` inside any `.controller.ts` returns zero hits. Only
`social_engagement` and `social_post` have a real, wired handler
(`src/modules/social/social.controller.ts`, `registerModule(socialModule)` in `main.ts`,
`SocialController` in `app.module.ts`).

`social_platform_app` is a different shape: `admin` is platform_admin-wildcard-only (nothing else
to mirror), and `read` is `group_executive`-only besides the wildcard — a group_executive-only
rule is never mirrored (established IAM-04c/B4/B5 precedent: it would hand a company-scoped
permission holder cross-tenant reach the role arm never gave them). There is no company_admin/
manager/module-tier rule on this kind at all (deliberate — the underlying table has no `tenant_id`
and no RLS). Nothing survives after excluding the wildcard and the exec-only rule.

**This is not the same finding as `portal`'s.** These 5 kinds are not structurally blocked by a
hard gate — they are blocked by an absence of evidence. The moment any of them gets a real
handler, a REG2-style audit can confirm or refute reliability and the mirror can land. Flagged for
the next ticket that builds one of these 5 kinds' endpoints, not something this ticket invented a
workaround for.

## 5. Client-boundary analysis for `portal`

No mirror was wired, so there is no NEW client-boundary surface to analyze — but the boundary was
probed to make sure the comment-only edit changed nothing:

- A real `client` principal (grant recorded at company scope, matching `ROLE_SCOPE_CONSTRAINTS`'s

  removal is untouched, verified live (§6, probe 6). No staff permission-holder can act through the
  `client` rule, because there is no mirror for any staff role to ride through, and the `client`
  rule's own condition never matches a `company_admin` grant (`client`'s derived role only matches
  `g.role == "client"`).
- No client permission-holder can reach a staff-only action, because no permission arm exists on
  this kind at all for ANY action — the flat `attr.perms` mechanism is entirely absent from this
  kind's evaluation today, exactly as before this ticket touched it.
