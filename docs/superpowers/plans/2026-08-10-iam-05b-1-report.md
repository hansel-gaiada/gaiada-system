## 1. What was built

**`platform-nest/scripts/generate-role-bundles.mjs`** — a self-contained Node ESM script (matching
the existing `lint-migration-rls.mjs`/`lint-withtenants.mjs` idiom: plain `node scripts/*.mjs`,
`readFileSync`/`readdirSync`, no build step) that re-parses the ACTUAL Cerbos policies
(`cerbos/policies/resource_*.yaml` + `derived_roles.yaml`) with a real YAML parser (`js-yaml`,
already a transitive dependency this package's own test suite imports the same way), wildcard-
expands `*` actions against each kind's own action universe (`permission-catalog.json`'s 230
concrete pairs), and resolves the `module_staff`/`module_manager`/`module_approver` derived-role
string-composition to the same 18 real, nameable roles that `0094_iam_02a_role_permission_bundles.sql`
seeds and `role-permission-parity.db.test.ts`'s `computeCerbosCoverage()` independently re-derives.
This is a **third** independent expression of the identical derivation algorithm (SQL migration,
DB-parity test, this generator) — deliberately not a cross-import from the sibling `.test.ts` file
(which the ticket forbids editing and which a generator script should not depend on for a plain
`node scripts/...` invocation to work).

Invoked as:
```
cd platform-nest
npm run gen:role-bundles              # regenerate the checked-in JSON in place
node scripts/generate-role-bundles.mjs --check    # exit 1 if regeneration would differ (no write)
node scripts/generate-role-bundles.mjs --stdout   # print JSON without writing any file
```

**`platform-nest/src/rbac/role-permission-bundles.json`** — the generated artifact. `_meta` block
(title/status/source/generatedBy/regenerate-instructions/rulings/companionDocs/keyOrder/note/counts,
in the same spirit as `permission-catalog.json`'s own `_meta`), then `roles: { <roleName>: [<sorted
permission keys>] }` for all 18 roles, **roles sorted alphabetically, each role's keys sorted
lexically** — so a future policy change's diff shows exactly which role gained/lost which
permission, which is the exact review surface the design ruling says this artifact exists to
provide (§3.2 item 2 of `2026-08-10-iam-05b-design.md`).

**`platform-nest/src/rbac/role-permission-bundles.db.test.ts`** — 7 tests:
1. sanity: the artifact declares exactly the 18 roles.
2. **regen-no-diff**: `generate()` + `serialize()` (imported from the generator script) reproduces
   the checked-in file byte-for-byte.
3. every referenced key exists in the catalog's 215 grantable permissions.
4. zero `class='relationship'` keys appear in any bundle (mirrors the 0093 DB trigger, checked a
   third time on the artifact specifically — catches a hand-edit that bypassed the generator).
5. every role's keys are sorted lexically (the diff-reviewability property itself, checked).
6. **DB parity**: the artifact's per-role permission sets equal live `role_permissions` (seeded by
   0094) for all 18 roles, joined on `permissions.key` — failure names the exact role + key +
   direction, preferring neither side.
7. DB parity on counts: per-role and total-pair counts match the artifact's own `_meta.counts` and
   the expected 925 total.

**`platform-nest/package.json`**: added `"gen:role-bundles": "node scripts/generate-role-bundles.mjs"`.

## 4. How the generator is invoked

```
cd platform-nest
npm run gen:role-bundles                          # regenerate src/rbac/role-permission-bundles.json in place
node scripts/generate-role-bundles.mjs --check    # CI-friendly: exit 1 on any diff, no write
node scripts/generate-role-bundles.mjs --stdout   # print JSON without touching the filesystem
```

The regen-no-diff test (`role-permission-bundles.db.test.ts`, test (a)) imports `generate`/`serialize`
directly from the script and asserts the same invariant `--check` enforces from the CLI — both
paths exist because CI test runs exercise the former and a pre-commit/manual regen workflow would
use the latter.
