# IAM-02h report — the parity suite's role list, derived not hand-maintained

**Status: DEV-VERIFIED** (green against `gaiada-test-pg` + `gaiada-test-cerbos`, live re-derivation
from the checked-out Cerbos policies, 2026-08-10).

## What changed

`platform-nest/src/rbac/role-permission-parity.db.test.ts` no longer declares its own literal
`REAL_ROLES` array. It now imports `REAL_ROLES` from `scripts/generate-role-bundles.mjs` — the
same single source of truth `role-permission-bundles.db.test.ts` already imports it from. This
closes the fifth instance of the "provisioned at one layer, invisible at the next" defect shape
found in this program on 2026-08-10 (see the "⚠ OPEN" section of
`docs/superpowers/plans/2026-08-10-iam-phase1-tickets.md`).

Because the literal list also carried the module_staff/module_manager → real-role resolver
(`moduleStaffTargets`/`moduleManagerTargets`), and that resolver is this file's own **independent**
re-derivation of Cerbos coverage (not imported from the generator — the generator's header is
explicit that it is "the THIRD independent expression of the same algorithm," deliberately not
cross-imported), the resolver itself also needed the two new module-composed mappings the generator
already carries:

- `webdev_change_request` / `webdev_provisioned_site` → `webdev_staff` (module_staff) /
  `webdev_manager` (module_manager), matching `generate-role-bundles.mjs`'s own
  `moduleStaffTargets`/`moduleManagerTargets`.
- The generic `service_assignment`/`member` fan-out (module_staff) and `service_assignment`
  (module_manager) rules now include `webdev_staff`/`webdev_manager` in their target lists, again
  matching the generator.
- `NO_ROLE_SEEDED_KINDS` — emptied (it held exactly those two kinds before). Kept as a named,
  currently-empty set rather than deleted, so a *future* module found in the same
  unseeded-role shape has an established place to land pending its own role-seeding ticket — the
  same convention the generator itself uses.

Two more hardcoded counts were removed as part of the same fix, since they are exactly the shape
that caused this defect in the first place (a literal frozen the day it was written, then silently
stale):
- The header claims of "18 real roles" throughout the file's prose comments were rewritten to not
  name a count.
- The trailing sanity test, which asserted `REAL_ROLES.length === 18`, now asserts only that the
  imported list has no duplicates and is non-empty — the "is the SET of roles what we expect"
  question is answered elsewhere (see "Derivation choice" below), not by a count pinned in this file.

## What the two never-before-compared roles revealed

**No mismatch. `webdev_staff` and `webdev_manager` bundle == this file's own live-Cerbos-derived
coverage, exactly, on the first run they were ever included.**

Before the fix: 22 tests (18 per-role + 4 fixed assertions), `webdev_staff`/`webdev_manager`
invisible. After: **24 tests, all green** — `role "webdev_staff": ... reachability` and
`role "webdev_manager": ... reachability` both pass with `{ missingFromBundle: [], extraInBundle: [] }`,
and the full 20-role × 230-pair matrix test also reports zero mismatches.

This is a real, non-trivial finding, not a tautology: IAM-02g's bundle (0098, generated by
`generate-role-bundles.mjs`) and this file's `computeCerbosCoverage()` are **two independently
written implementations** of the same module_staff/module_manager → concrete-role resolution
(the generator's own header calls itself "the THIRD independent expression of the same
algorithm" alongside 0094's SQL and this test file). Getting the same resolver logic right twice,
independently, without ever having compared the two roles before today, and having them agree
byte-for-byte across all 215 grantable pairs on the first comparison, is evidence the IAM-02g
derivation was correct — not evidence manufactured by making the two sides copy each other (they
don't: this file re-parses `cerbos/policies/*.yaml` itself and re-implements the resolver from
scratch; it never calls into the generator's `computeCoverage()`).

**No adjustment was made to either side to force agreement.** Per the ticket's instruction, if
they had disagreed the fix would have stopped there and reported which derivation looked wrong,
not silently patched one to match the other.

## Derivation choice: generator, not DB — and why

`role-bundle-completeness.db.test.ts` derives the **role-name set** live from the `roles` table
(`SELECT ... FROM roles WHERE company_id IS NULL`) and is right to do so for its own job: catching
a `roles` row that exists but has zero permission bundle backing it, no matter what created that
row. That guard has no resolver logic in it at all — it just counts, so anything richer than "does
this name have ≥1 permission" would be out of scope for it.

This suite's job is different: it needs, for each role, an *independently computed Cerbos-side
reachability set* to diff against the bundle. That requires knowing **which module_staff /
module_manager / module_approver rule resolves to which concrete role**, which is not something any
query over `roles` or `role_permissions` can tell you — it is knowledge about how Cerbos's
derived-role abstraction maps onto real role names, and that mapping is authored by a human each
time a new module is on-boarded (as IAM-02g did for `webdev_staff`/`webdev_manager`, and as this
ticket had to replicate in `moduleStaffTargets`/`moduleManagerTargets` above).

If this suite derived its role *set* from the DB instead of the generator, a newly-seeded role
would be picked up as a name, but `computeCerbosCoverage()` would have no idea what module_staff
rule (if any) is supposed to resolve to it — it would either throw (the existing fail-fast for an
"unhandled kind" some other rule already exercises) or silently compute an empty Cerbos-side
coverage for it, which would then show every one of its bundled permissions as `extraInBundle` — a
**false positive**, not a real finding, on every future module rollout, purely because the DB
doesn't carry resolver semantics. Deriving the *role list* from the generator instead keeps this
suite's role set exactly in lockstep with the one place that also has to encode the resolver
mapping (the generator) — whoever adds a role to the generator's `REAL_ROLES` already has to teach
its `moduleStaffTargets`/`moduleManagerTargets` about it, so this file inherits a role list whose
resolver companion-work is guaranteed to exist somewhere reviewable, even though this file's own
resolver still has to be updated by hand (as this ticket did) because it is a deliberately separate
implementation, not an import.

**Where they could disagree:** the generator's `REAL_ROLES` and the live `roles` table can drift in
exactly the shape IAM-02g's own header documents as variant #4 — a `roles` row seeded (e.g. by a
migration or `seed:agency`) with no corresponding entry ever added to the generator's `REAL_ROLES`.
That drift is real and already has its own dedicated guard (`role-bundle-completeness.db.test.ts`,
empty exemption allowlist, DB-derived) and its role-*name*-existence sibling
(`role-catalog-drift.db.test.ts`). This suite is not the right place to duplicate that check —
doing so here would require this file to also independently re-derive the resolver mapping for any
DB-discovered role, which is exactly the "hand-maintained resolver, easy to leave incomplete"
problem this whole program has been closing all day, just moved one file over.

## Proof: a newly-added role is now auto-detected, not silently skipped

Two levels of evidence:

**1. The already-real case.** `webdev_staff`/`webdev_manager` were added to
`generate-role-bundles.mjs`'s `REAL_ROLES` by IAM-02g, on the same day, with **zero corresponding
edit** to `role-permission-parity.db.test.ts` needed for the import to pick them up — the two new
`it.each` cases (`role "webdev_staff": ...` / `role "webdev_manager": ...`) appear in this run's
output purely because the array they're generated from grew. That is the property this ticket
exists to establish, demonstrated with the real production data, not a synthetic stand-in.

**2. A synthetic new-role probe (temporary, not committed).** To prove the *mismatch-detection*
half (not just "the role appears in the list" but "a genuine drift on that role would be caught"),
a throwaway test was written, run, and then deleted (never part of the git working tree; confirmed
absent afterward):

- Extended `REAL_ROLES` **in memory only** with a synthetic `iam02h_probe_role` that appears in no
  Cerbos policy anywhere (checked by scanning every parsed policy file's rules for the literal
  string — confirmed zero mentions).
- Seeded a real `roles` row and a real `role_permissions` row for `iam02h_probe_role` directly in
  the disposable test database (the exact shape of "a role got a bundle, but Cerbos was never
  taught about it" — the inverse of IAM-02g's variant #4).
- Ran the identical `loadBundle()`-style query the owned file runs, over the extended list, and
  computed the identical `extraInBundle` diff the real `it.each` assertion computes.
- Result: `extraInBundle` immediately equalled `[the seeded permission key]` — the probe role's
  drift was caught the moment it entered the (in-memory-extended) list, with no further code change.

```
✓ REAL_ROLES extended in-memory with a probe role now flows through the exact query the owned
  file runs, with zero edits to that file
✓ probe_role has zero Cerbos-derived reach (no policy names it) but a seeded bundle row ->
  mismatch is caught, not silently dropped
```

Both proof tests passed. The probe file
(`platform-nest/src/rbac/_iam02h-probe-DELETE-ME.db.test.ts`) was deleted immediately after the run
and is not present in the working tree.
