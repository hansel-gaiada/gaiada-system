**No `owner` persona was created.** D-8's `owner` role does not exist in Cerbos or `roles` today

### IAM-06a — the durable seed

`src/seed/personas.ts`, run via `npm run seed:personas` (new script line in `package.json`,
alongside `seed:agency`). Plants one real user per persona, email
`persona.<key>@iam-personas.test`, in a dedicated "IAM Persona Sandbox" company with every module
a persona's role might need enabled (`agency, hr, reports, search, assistant, webdev, pm, it`) —
without this, a correctly-authorized persona can still get a fail-closed 404 from an unrelated
module gate, which looks exactly like a permission denial and would mislead whoever runs this by
hand.

**Idempotency — verified, not assumed.** Ran the script twice against a live test database and
queried `user_roles` directly:

```
persona.agency_approver@iam-personas.test  grants: 2   (agency_approver + member — correct)
persona.<every other key>@iam-personas.test grants: 1   (unchanged across both runs)
persona.client_contact@iam-personas.test    grants: 0   (correct — no user_roles row at all)
client_contacts rows for that user: 1        (not 2)
team_memberships rows for team_lead: 1       (not 2)
```

Identical UUIDs on both runs — the second run adopted every existing row, created nothing new.

### IAM-06b — the per-test fixture (the consumed API)

`src/testing/personas.ts::seedPersonaTenant(which?, label?)` seeds a **brand-new, disposable**
tenant + team + client on every call — deliberately NOT the same rows IAM-06a plants, so tests
never depend on that script having been run and never collide with each other. Returns
`{ tenantId, teamId, clientId, users, as(persona) }`; `.as(persona)` is the one-line header
builder (`{ authorization, "x-user-id" }`) that plugs directly into the `app.inject()` pattern
every existing adversarial-authz suite already uses.

`platform-ui/e2e/personas.ts::loginAsPersona(page, key, opts?)` is the frontend equivalent — signs
in via the real `/login` form and waits for the post-login redirect (works for both the staff `"/"`
landing and the client's `"/portal"` landing).

## 3. Both directions — proven, not just designed

`src/testing/personas.test.ts`, 8 tests, real `app.inject()` round-trips against live Postgres +
Cerbos (not internal function calls). Green:

```
✓ src/testing/personas.test.ts (8 tests) 3.4s
```

Deliberately picked `resource_device.yaml` as the demonstration boundary — a small, sharply
written policy (`create`/`update`/`delete` -> `company_admin, it_staff` only; baseline `read` ->
everyone company-scoped) that gives a clean ALLOW and a clean DENY without needing any
module-attribute plumbing:

- **ALLOW** — `it_admin` registers a device (201).
- **DENY** — `viewer` and `member` are both refused (403) on the identical write.
- **ALLOW** — `manager`/`member`/`viewer`/`company_admin` all read the device registry (the
  baseline rule).
- A persona not in the seeded set (`p.as("team_lead")` when only `["manager"]` was seeded) throws
  a named error immediately, not a confusing 401 two lines later.
- `client_contact` is refused the staff device registry outright (portal-only, structurally no
  `company_memberships` row).
- `group_executive` still passes through the platform_admin/group_executive wildcard.

**A real finding surfaced by writing this, not assumed going in:** the first draft of the "every
staff tier can read the device registry" test included `team_lead` and failed. `team_lead`'s
Cerbos derived role only activates when `request.resource.attr.teamId` matches the grant's scope
— the device resource carries no `teamId` attribute at all, so the derived role never fires even
though `resource_device.yaml`'s read rule lists `team_lead` by name. The honest answer for
`team_lead` on a company-wide, team-less resource is DENY, and the test now asserts exactly that
(with the mechanism explained inline) instead of a wrong ALLOW that would have quietly hidden the
scope-cascade boundary `rbac.ts`'s own `scopeCovers` comment already documents on the UI side. This
is precisely the kind of thing IAM-06b's ergonomics are supposed to make easy to catch.

Frontend equivalent: `platform-ui/e2e/iam-personas-fixture.spec.ts`, 3 tests, run via
`npx playwright test --project=personas` — green:

```
ok  ALLOW — superadmin sees the Settings nav item (admin.access)
ok  DENY  — member does NOT see the Settings nav item (admin.access)
ok  a DEMO_MODE-unsupported persona fails loudly, not silently as the wrong identity
```

## 4. DEMO_MODE — covered honestly, not silently

Checked before writing anything: `src/lib/demoIdentity.ts` resolves exactly 4 coarse tiers
(`demo-hansel` / `gede-ic` / `seo-staff` / `demo-client`). This ticket deliberately left that file
and `demoFixtures.ts` unmodified — they are shared UI-program surface with their own owners and
their own e2e suites depending on the current 4-tier shape; rewriting them was out of scope and
riskier than the ticket's ergonomics goal justified.

**Result: 5 of 14 personas work under `DEMO_MODE=1`** (`superadmin`, `group_executive` — same
`demo-hansel` identity carries both roles — `member`, `search_staff`, `client_contact`), each
mapped to the *exact* existing demo identity that already holds that real role, not an
approximation. The other 9 (`company_admin`, `manager`, `team_lead`, `viewer`, `hr_staff`,
`hr_manager`, `it_admin`, `search_manager`, `agency_approver`) have no demo equivalent.
`loginAsPersona` makes this a loud, named error thrown before the page is even touched —

```
DEMO_MODE has no identity for persona "team_lead". src/lib/demoIdentity.ts only resolves 4 coarse
tiers today ... Run this spec against a real backend instead ...
```

— rather than silently substituting `demo-hansel` (superadmin) for an unsupported persona, which
would make a DENY assertion pass for the wrong reason. That failure mode is exactly the
under-claim/over-claim class this whole IAM program exists to eliminate, so the fixture refuses to
reintroduce a version of it. Full table + the real-backend escape hatch (`{ demoMode: false }` +
`npm run seed:personas`) are in `platform-nest/README-PERSONAS.md`.

One correctness bug caught while proving this: the first draft checked
`process.env.DEMO_MODE === "1"` inside the Playwright **test-runner** process. `playwright.config.ts`
only sets `DEMO_MODE=1` on the spawned `next dev`/`next start` **child** process (the `webServer`
block) — the test runner's own env never has it, so under the standard `npm run e2e` invocation
that check always evaluated false and silently took the "real backend" branch against a server that
was actually running in demo mode. Fixed by making `demoMode` an explicit option defaulting to
`true` (matching the project's actual default), never an env-var read — verified by rerunning the
spec both before (2 of 3 tests failed, for exactly this reason) and after (3/3 green) the fix.

## 5. What a consuming team still has to figure out for themselves

(also written into `README-PERSONAS.md`'s closing section, so it travels with the code)

- **Multi-team scenarios.** `seedPersonaTenant()` gives `team_lead` exactly one team. "Lead of team
  A, denied on team B" needs a second team inserted by hand.
- **New module-gated surfaces.** Both seed paths hardcode the module list they enable
  (`agency, hr, reports, search, assistant, webdev, pm, it`). A new module needs adding to both
  files or its personas will look wrongly "denied" (actually a 404 module gate, not a 403 role
  denial — the status code alone won't tell you which).
- **No `owner` persona, on purpose** — do not write a test assuming one exists.
- **Cerbos staleness** — this ticket restarted `gaiada-test-cerbos` before trusting any result
  (`StartedAt` 2026-08-10T03:36:09Z was only 44s after the most recent policy edit in the repo,
  `resource_agent_run.yaml`, which is close enough to a live concurrent edit to be worth not
  trusting — restarted to 06:11:20Z before running anything against it). Anyone using these
  fixtures against their own long-running local Cerbos should check the same thing first.
- **A full `tsc -p tsconfig.json` build currently fails** — but on pre-existing errors in
  `src/rbac/principal-permissions.db.test.ts` and a missing `@types/js-yaml` declaration, both
  inside files this ticket does not own and both belonging to concurrent sessions' in-flight
  IAM-03a-shaped work. Verified by name that none of the reported errors reference any file this
  ticket touches (`grep -i personas` over the `tsc` output returns nothing).
