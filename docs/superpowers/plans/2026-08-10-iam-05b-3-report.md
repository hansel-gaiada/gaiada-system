## 0. The honest headline

This guard is designed, per the ticket's own instruction, to surface real findings on first run —
not to be silently green. It **is** green everywhere except the one section whose entire job is to
report divergence: the core `(role, capability)` biconditional. That section fails exactly 7 named
cases. Two were predicted in advance (drift register #6/#7); **five are new**, found only by
actually building and running this guard against the real catalog + bundles + map, not by manual
re-reading. All 7 are reported below for owner/architect adjudication — none were fixed, and none
were silently absorbed into the exception register without a citable reason.

## 2. Why 24 raw mismatches, not 2 — and how they resolve to 7 real findings + 17 excepted

A first pass computed the biconditional over **all** 17×34 pairs with no exceptions at all and
found **24** raw disagreements — a useful diagnostic, not the final answer. Sorting them:

**9 — `group_executive`, wholesale.** `ROLE_CAPS.group_executive = ALL`; Cerbos denies it on
`admin.access`, `people.directory`, `rollups.view`, `pipeline.write`, `hr.view`, `hr.manage`,
`reports.ops.poll`, `appraisal.score`, `appraisal.cycle.admin` — exactly the pattern drift register

and bare `member`-kind exclusions). Disposed of by Ruling 4 / D-7: sole holder is a seed/test
account (`exec@gaiada.test`); corrected in Phase 3 when the role is deleted, not here. **Seeded into
the register wholesale, per the ticket's own instruction.**

**7 — self-service (`owns`-conditioned) reach that `role-permission-bundles.json`'s bundling
methodology cannot distinguish from an unconditional grant.** This is a genuinely new piece of
diagnosis this ticket produced: `resource_hr_case.yaml`'s own IAM-04b comment (lines ~79–92) states
outright that migration 0094's bundling methodology "treats a resource-instance condition
(self-ownership) as 'satisfied' when computing reach... a real granularity gap in the current
215-permission catalog... not something fixable from [the policy layer]." Confirmed directly
against `resource_integration_connection.yaml` (lines 44–49) too: `member`/`viewer`/`team_lead` hold
full integration-connection CRUD **only** under `variables.owns` — a completely different Cerbos
rule and role list from the unconditioned `company_admin`/`manager` "company.manage tier" rule two
lines above it in the same file — yet the bundle export cannot tell them apart, so it credits
`member`/`viewer`/`team_lead` with the same four permission keys `company.manage`'s set needs. Same
root cause, same shape, as the four `member`-self entries IAM-02a's drift register §3 already ruled
"not drift" (`reports.person.view`/`reports.project.view`/`checkin.read`/`appraisal.read`, all
reached via `owns`/`subjectUserId==principal.id`). All 7 entered the exception register with the
exact citation.

**1 — a call-site double-gate.** `hr_manager × approvals.decide`: `hr_manager` genuinely holds
`core.automation_approval.decide` (module-scoped to `hr`), so the biconditional flags it. But
IAM-02a's drift register §3 already ruled this "no live gap": the one real call site,
`hrActions.ts`'s `decideHrLeave`, gates on `can(...,"approvals.decide",...) || can(...,"hr.manage",...)`,
and `hr_manager` holds `hr.manage`. Registered with that exact citation.

## 4. The exception register, guarded — mechanics and teeth

Two escape hatches, both mechanically checked against staleness:

1. **`WHOLESALE_EXCEPTED_ROLES = {"group_executive"}`** — guarded by a test that recomputes
   `group_executive`'s mismatches against **all 34** capabilities (bypassing the wholesale skip)
   and asserts the result is non-empty. If `group_executive`'s `ROLE_CAPS` entry is ever narrowed
   to match Cerbos (or the role is deleted per D-7), this guard fails, forcing the wholesale
   exception's removal instead of letting it silently outlive its reason.
2. **`KNOWN_NON_DRIFT`** (8 entries, each with `role`, `capability`, `direction`, `reason`,
   `decisionRef`) — guarded by a test that recomputes each entry's real mismatch and asserts it
   still matches the registered direction exactly. A register entry that stops diverging (or
   starts diverging in a different direction) fails this guard by name.
