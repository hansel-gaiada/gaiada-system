## 3. Four defects/gaps found by BUILDING and DRIVING it (none were assumed going in)

### 3.1 `targetUserId` was an attribute no handler could send

`resource_position.yaml`'s self-assign DENY and `resource_role_grant.yaml`'s self-target DENY both
read `request.resource.attr.targetUserId`; the `Resource` type had no such field and
`resourcePayload()` never sent one, so **both DENY rules were structurally unreachable**. Fixed by
adding the attribute. This is the same shape as `team_lead`'s `teamId` and `report_document`'s
`scope_id` — the third distinct instance of "a rule reads something nothing can carry".

### 3.2 HR cannot place, move, or terminate — and design §5.1 says it can

Established by running the suite, not by reading: `assign`/`unassign` are `company_admin` +
`org_unit_lead` only. An `hr_manager` gets 403 the moment `positionId` is present, and on
transfer/terminate. **What shipped honours Cerbos**, and both directions are pinned. This needs an
owner call — recommendation and options in `PERMISSION-CONTRACT.md` §11.2. It is the one thing in this
ticket that is a genuine design contradiction rather than an implementation choice.

### 3.3 The leaver flow would have disabled every leaver's login (RLS zero-row trap)

§5.3 says: disable `users.status` only if **no other company's active membership remains**. The first
implementation counted memberships under `withGlobal` — which sets no tenant GUC, so
`company_memberships`' RLS returned **0 rows for everyone, with no error**, and the flow concluded "no
other employment" for every single leaver. Someone still employed at another group company would have
had their platform login disabled by a termination at one company.

Caught by the `"does NOT disable a login when the person still works at another group company"` case
(observed RED: `expected true to be false`), then fixed by using the sanctioned `principal_lookup`
policy (0072 §7b) — the same transaction-local, single-user read `assemblePrincipal()` uses for this
exact question. The red→green transition IS the teeth proof.

### 3.4 `0109`'s uniqueness did not cover the joiner's own natural key

Design §5.1's idempotency key is `(tenant_id, work_email)`; `0109` shipped
`(tenant_id, user_id) WHERE user_id IS NOT NULL`. A `pending_start` candidate has no `user_id`, so two
retries before the principal exists would have produced two employee rows for one person with nothing
at the DB layer to stop it. `0111` adds the partial unique (`work_email IS NOT NULL AND deleted_at IS
NULL`); the controller's find-then-write covers both axes so neither index's violation can escape as
an unhandled 23505 → 500 (the failure mode `0092`'s partial index caused in `assignRole`).

## 4. Deliberate refusals (each one a typed 400, not a silent approximation)

| Refusal | Why |
|---|---|
| Future `startDate`/`effectiveDate`/`lastDay` | `collectDesired()` resolves on `pa.valid_to IS NULL` — no as-of axis. A future date would apply *now* while the record claimed otherwise. **Scheduled JML is deferred**, and needs an as-of reconciler pass. |
| `positionId` without `workEmail` | A seat confers roles; roles need a principal. |
| `PATCH {employmentStatus:"terminated"}` | Termination is a flow (close seats, revoke, disable, bump). As a field edit it would produce a "terminated" employee holding every grant. |
| `DELETE` while a seat is open | Deleting the people file under live grants leaves managed grants with nothing explaining them. |
| A candidate with no position gets **no** `users` row | 0109's own comment. Minting a principal per CV grows the population `assemblePrincipal()` resolves, for people not hired. |

## 5. Idempotency, per flow (§5's requirement)

- **Hire** — natural key `(tenant_id, work_email)`; the retry test asserts ONE employee and ONE seat.
- **Transfer** — already-in-seat returns `{ok:true, unchanged:true}` with no churn/session bump; a
  double transfer leaves exactly one open seat.
- **Terminate** — the second call is a no-op (no open seats left to close); asserted.

Every seat write is guarded rather than `ON CONFLICT`, because a GiST `EXCLUDE` cannot be an
`ON CONFLICT` arbiter.
