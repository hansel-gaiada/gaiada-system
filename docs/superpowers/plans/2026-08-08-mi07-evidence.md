### MI-07-R1 — Local compose port collisions on `up -d` (infra, not webdev code)

- **Severity:** Low (dev-environment only; no server, no committed file, touched).
- Two collisions surfaced recreating `postgres`/`cerbos` with `docker-compose.local.yml` layered in:
  (1) `docker-compose.vps.yml`'s own `postgres` service publishes `127.0.0.1:55433:5432`, which is the
  SAME host port `gaiada-test-pg` already owns — the previously-running dev postgres had been manually
  remapped to `55436` by some earlier, undocumented local action, so a plain `up -d` silently tried to
  revert to the file's `55433` and collided. (2) `docker-compose.local.yml` publishes `cerbos` on
  `127.0.0.1:3592/3593` for host-run test suites — but that is the SAME port `gaiada-test-cerbos` (the
  canonical port-owner per this estate's own documented rule) already holds, and the dev
  `gaiada-cerbos-1` had previously been running with NO published ports at all.
- **Repro:** `docker compose -f vps.yml -f local.yml -f build.yml up -d postgres platform cerbos` on a
  clean recreate, no further overrides.
- **Impact:** a routine rebuild-and-recreate (exactly what this ticket's own runbook calls for) silently
  destroys the previously-working dev postgres/cerbos containers with a port-bind error, and the two
  committed compose files disagree with each other and with the box's actual prior state about who owns
  `55433`/`3592`.
- **Fix applied for this session only:** a local, uncommitted compose override pinning postgres back to
  `127.0.0.1:55436:5432` and resetting cerbos's port list to empty (`ports: !override []`), so the dev
  stack coexists with the always-on test containers. Not committed anywhere.
- **Owner / fix tier:** devops. Recommend either documenting the dev-postgres/cerbos port convention in
  `docker-compose.local.yml`'s own comments (it already documents the test-container-port collision for
  cerbos in one sentence but does not resolve it), or giving the dev stack's postgres/cerbos their own
  non-conflicting host ports in the committed file so a routine rebuild is not a footgun.

### MI-07-R2 — `automation/.env` and `infra/compose/.env` disagree on `N8N_DB_PASSWORD`; neither matches the live role (infra, blocks n8n locally)

- **Severity:** Medium (blocks local verification of a real, shipped automation surface; no data
  exposure — n8n simply cannot boot, it does not run with wrong/stale credentials).
- Both files are gitignored (`.gitignore:9`), confirmed via `git check-ignore -v` on both — this is a
  **local secret-file drift**, not a committed-code issue, and not the "value pasted into a transcript"
  class of incident.
- **Repro:** `automation/.env`'s `N8N_DB_PASSWORD` did not match `infra/compose/.env`'s value (direct
  byte comparison, values not reproduced here per the no-secrets-in-evidence rule). After editing
  `automation/.env` to match `infra/compose/.env` (the value the `postgres` container itself was
  actually booted with, confirmed via `docker inspect gaiada-postgres-1`'s env list), `n8n` **still**
  failed with `password authentication failed for user "n8n"` — meaning the live Postgres role's actual
  password matches **neither** committed local `.env` file. This was not remediated further: altering
  the `n8n` role's password directly (`ALTER ROLE ... WITH PASSWORD`) was correctly refused by this
  session's own permission guard as a credential-modifying action requiring explicit human sign-off, and
  no attempt was made to work around that refusal.
- **Impact:** `automation/docker-compose.yml`'s `n8n` service cannot boot locally in its current state,
  which blocks live verification of the shipped `pipeline-fanout` workflow (design §3.1 step 5) —
  see §3.6 below for exactly what this leaves UNVERIFIED and what was checked as a substitute.
- **Owner / fix tier:** devops. The fix is either to `ALTER ROLE n8n` to match one of the two `.env`
  files (a human decision on which value is authoritative) or re-provision the role from
  `infra/db/init-cluster.sh` against the current `.env`. Left the `automation/.env` edit in place (now
  matching `infra/compose/.env`, at least removing one axis of drift) — n8n itself was left **stopped**
  (`docker compose stop n8n`) rather than crash-looping.

### 3.4 `prd_sign` — signer succeeds, viewer denied (positive control), notification is signers-ONLY

```sql
select id, user_id, type from notifications where created_at > now() - interval '20 minutes' order by created_at;
--  … | SIGNER  | webdev.change_request.converted   (both viewer+signer got this — the general kind)
--  … | VIEWER  | webdev.change_request.converted   ← the POSITIVE CONTROL: notify genuinely ran for
```

The viewer received the `converted` notification but **not** the `pipeline.gate.opened` one — the

missing-field-reads-as-null trap this program has hit before).

### 3.5 Double-convert race — a real HTTP double-fire against the live dev backend

The repo's deterministic race test (§2.1) already proves the mechanism under a forced collision. As
the closest available proxy for "a real double-click through the UI" (the browser-driven walk itself
is UNVERIFIED — see §7), two concurrent `curl` POSTs were fired at the SAME live `:3004` process with
NO advisory-lock pre-hold — an honest network race, not a manufactured one:

```
POST …/triage {"action":"convert","route":"mini_run"}   ×2, launched together via `&`/`wait`
→ A: HTTP 200 {"id":"…","status":"in_progress","route":"mini_run","pipelineRunId":"019fe1cf-0a9b-…"}
→ B: HTTP 409 {"error":"change request already triaged (status in_progress)",
               "existing":{"status":"in_progress","route":"mini_run","pipelineRunId":"019fe1cf-0a9b-…"}}
select count(*) from pipeline_runs where title='MI07 live double-click race';  -- 1
```

**Caveat, stated plainly:** this is a curl-driven concurrent HTTP race against the real server process,
not a literal Playwright browser double-click on the triage button. It is real evidence the mechanism
holds outside the deterministic test harness, on the actual runtime; it is not a substitute for a
browser-level UI walk, which is UNVERIFIED (§7).
