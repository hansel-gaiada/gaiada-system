## 1. The gap, confirmed exactly as briefed

`0097_webdev_module_roles.sql` seeded `webdev_staff`/`webdev_manager` as global `roles` rows but
inserted **zero** `role_permissions` rows. `0094`'s own header already flagged this as "finding
(b)" and pinned the exact math in advance: 7 `(kind,action)` pairs (2 for `webdev_staff`, 5 for
`webdev_manager`) from the two webdev-specific policies. This is the **fourth variant of one
defect class** found in this program today (role named in Cerbos+rbac.ts with no `roles` row ->
0091; baseline roles seed-script-only -> 0095; `agency_approver` same shape -> 0096; `roles` row
exists but no bundle -> this ticket).

## 6. Part 2 — the completeness guard: `src/rbac/role-bundle-completeness.db.test.ts`

**Derives, does not hand-maintain.** Unlike the generator/migration/parity-test trio (which all key
off a hand-listed `REAL_ROLES`), this guard queries the live `roles` table directly
(`WHERE company_id IS NULL`) via a `LEFT JOIN` to `role_permissions`, so a role with **zero**
bundle rows still appears in the result (count 0) instead of vanishing — the exact shape that made
this defect invisible to a naive `INNER JOIN` check in the first place. A future migration that
seeds a 21st global role and forgets its bundle fails this guard immediately, by name, with **no
code change required in this file** — the same "derive, don't hand-maintain" discipline
`role-catalog-drift.db.test.ts` (IAM-02d/IAM-02f) established for role *names*; this is that
guard's sibling for role *bundles*.

### Exemption-allowlist conclusion: **empty, deliberately**

Considered and rejected before writing the guard:

- `client` (portal-only, the obvious first guess) holds 6 real permissions
  (`portal.read`/`sign`/`pay`/`decide`/`request_change`/`update_profile`) — not a plausible
  exemption; confirmed by inspecting `resource_portal.yaml` and the live bundle.
- Enumerated all 20 currently-seeded global roles (via the migrations that create them — 0026,
  0069, 0072, 0091, 0094, 0095, 0096, 0097 — and cross-checked against the live `roles` table in
  the test DB): every one exists specifically *because* some Cerbos policy names it. None is a
  deliberate no-op placeholder.
- A role that grants literally nothing through the permission layer is, the moment IAM-03a/04 make
  `role_permissions` load-bearing, indistinguishable from the exact silent-nothing failure this
  entire ticket chain exists to close.
- The one plausible **future** exemption is Phase 3's `owner` role (D-8), explicitly still
  undefined elsewhere in this program — but it does not exist as a seeded `roles` row today, so a
  guard that only inspects what is actually seeded has nothing to exempt yet. Noted in the test's
  own header so whoever seeds it doesn't let it slip through by omission.

**Conclusion: the allowlist is empty.** Per the ticket's own framing, this is a **stronger**
guarantee (every seeded global role must resolve to at least one grantable permission, no
exceptions) than a populated one — not a missing feature.
