# WD-23A — RE-SPEC: Drive OAuth rides SEO's Google OAuth core (promote, don't rebuild)

**Status:** RE-SPEC — supersedes the WD-23A row + LD-13 in
[`2026-07-30-webdev-phase3-tickets.md`](./2026-07-30-webdev-phase3-tickets.md) ·
**Date:** 2026-08-01 · **Trigger:** the SEO/search-marketing programme closed (`search-marketing
0.5.0 DEV-VERIFIED`) and shipped a complete, adversarially-verified Google OAuth implementation
**after** the Phase-3 plan was written on 2026-07-30.

**One-line verdict:** WD-23A as written would build the estate's **second** Google OAuth state
machine. It must instead **promote SEO's into core and extend it**. The security machinery is done;
what remains is a wall-placement problem.

---

## 0 · Why this re-spec exists

The Phase-3 plan (2026-07-30) specced WD-23A as a from-scratch build:

> `src/core/google-drive.service.ts` … mint a 128-bit nonce, store server-side in Redis
> `oauth:state:<nonce>` … exchange the code … refresh single-flight

Every one of those clauses is **already implemented, hardened, and test-proven** in
`platform-nest/src/modules/search/google/` (SM-25a), with a threat model published in the source.
The plan simply predates it. Building WD-23A as written would produce two divergent OAuth state
machines over the *same* credential vault — and the two would drift, because only one of them would
be under adversarial test.

**This is a wall problem, not a code problem.** SEO's implementation sits **inside a module**, which
is the wrong side of design decision **D-2** (core-vs-module walls) for a core concern like Drive.

## 2 · What SEO built that WD-23A must REUSE, not re-derive

`src/modules/search/google/oauth-state.ts` publishes a named attack list with a refusal mechanism
and a proving test for each. **This is the deliverable WD-23A was going to spend an Opus seat
re-creating:**

| | Attack | Refused by |
|---|---|---|
| A1 | Login-CSRF on the callback (binds the *attacker's* Google account into the victim's tenant) | state must be a server-created row **and** `created_by == calling principal` (`principal_mismatch`) |
| A2 | State forgery / tenant pivot | tenant travels **inside** the HMAC: `gs1.<stateId>.<tenantId>.<HMAC>`, `timingSafeEqual` before any DB read; the signed tenant is the only tenant opened |
| A3 | Authorization-code replay | single atomic `UPDATE … WHERE consumed_at IS NULL RETURNING` — DB-enforced, not check-then-act |
| A4 | PKCE downgrade / verifier theft | `S256` CHECK-constrained in the migration (no `plain`); verifier stored **sealed** |
| A5 | Redirect-URI substitution | row records its own issued `redirect_uri`, re-compared at callback |
| A6 | Provider confusion | caller states expected provider, must match the row |
| A7 | Cross-tenant state read | FORCE RLS on the state table + signed tenant is the sole `withTenants` entry |
| A8 | Stale in-flight requests with live verifiers | TTL enforced **in the consume predicate**, not merely by a sweep |

Plus, in `oauth.ts`: refresh-token **rotation persistence** (the classic rotation bug — a new refresh
token must be stored or the *next* refresh dies); `invalid_grant` → `status='error'` **without
destroying stored tokens** (a read path must not be able to shred a credential); RFC-7009 revocation
**issuer-first, local-revoke-always** (an unreachable issuer must not stop us forgetting a
credential); and `meta.googleIssuerHost` / `googleIssuerIsGoogle` provenance so a dev-issuer link is
readable as one at a glance.

**Drive inherits all of the above for free** — including the provenance stamp, which means a
sandbox-issued Drive connection can never silently read as a real Google one.

> Note the standard SEO set for itself, which carries over verbatim: *a green sandbox/Keycloak run is
> a validated client of our own model of Google, not a validated Google integration.* WD-23A's ACs
> must not claim otherwise; real-Google behaviour stays deferred (SEO's SM-41G, webdev's equivalent).

## 3 · The three genuine blockers to reuse

**B1 — the state table is search-owned AND forbids Drive.**
`0060_search_google_oauth_states.sql:64` has
`CHECK (provider IN ('google_search_console','google_analytics','google_ads'))` — `google_drive` is
rejected. Worse, **every** access goes through `withTenants(…, { modules: ["search"] })`, so a tenant
without the `search` module enabled **cannot run a Drive link at all**. A Web Dev department that
happens not to sell SEO would find Drive silently unlinkable. This is the D-2 violation.

**B2 — search concerns are welded into the flow functions.**
`GoogleProvider` is a closed 3-member union; `DEFAULT_SCOPES` is a `Record` over it (so adding Drive
is a type error at every exhaustive site); and `startAuthorization`/`completeAuthorization` carry
`propertyId` + a `bindPropertyConnection` call — `search_properties` concepts with no Drive meaning.

**B3 — one callback route, one configured redirect URI.**
The callback is `GET /api/search/google/oauth/callback` (`search-google-oauth.controller.ts:61`) and
`GOOGLE_OAUTH_REDIRECT_URI` is a single scalar. Drive cannot mount a second callback without either
a second registered URI + a second config var, or a shared route.

---

## 4 · Ruling — promote to core, register surfaces

### 4.1 One shared callback, dispatched from the signed state

**Decision:** `GET /api/integrations/google/callback` becomes the single callback for **all** Google
surfaces. The provider is already carried inside the signed state (that is exactly why SEO put the
tenant in the HMAC — Google forbids wildcard redirect URIs), so one exactly-registered URI serves
every surface and every company.

**Do this now, because it is currently free.** OQ-9 has not landed — I verified `infra/compose/.env`
holds no Google credential — so **no redirect URI is registered with Google yet**. Choosing the core
path costs nothing today and would cost a coordinated re-registration later. Keep
`api/search/google/oauth/callback` as a thin permanent alias so SEO's own tests and any local
bookmarks keep working.

### 4.2 The state table is REPLACED, not migrated

**The key enabling observation:** `search_google_oauth_states` rows have a **10-minute TTL**
(`GOOGLE_OAUTH_STATE_TTL_SECONDS`, default 600s) and represent only *in-flight* authorization
requests. There is **no durable data to migrate** — a deploy at any moment can lose at most a few
half-finished link attempts, whose correct remedy is already "start again" (the `unknown_or_expired`
branch users hit today on any expiry).

So: create a core `google_oauth_states` table (next-unused migration number, re-verified at merge per
LD-1), carrying forward **unchanged** FORCE RLS, the `S256` CHECK, `origin_site`, the sealed
verifier, and the `simulated`/`issuer_host` provenance columns — with the provider CHECK widened to
include `google_drive`. Drop the search table in the same migration. No backfill, no dual-write, no
data-migration risk. State this reasoning in the migration header so a reviewer does not go looking
for the missing backfill.

### 4.3 Provider union → surface registry

Replace the closed union with a registry keyed by provider string, each entry declaring its default
scopes and an optional `onLinked` hook:

- **search** registers `google_search_console` / `google_analytics` / `google_ads` and supplies the
  property-binding hook — so `propertyId` and `bindPropertyConnection` move *out* of the core flow
  and *into* search's own hook, where they belong.
- **webdev** registers `google_drive` with scopes `drive.readonly` + `drive.file`, no hook.

Search's existing public API (`startAuthorization`, `completeAuthorization`, `getAccessToken`,
`refreshConnection`, `revokeGoogleConnection`, `resolvePropertyConnection`,
`bindPropertyConnection`, `DEFAULT_SCOPES`, `GoogleConnectionView`) is preserved as re-export shims
from the module path, so **no in-flight SM ticket has to churn** and the diff stays reviewable.

### 4.4 Config namespace

`config.search.google` → `config.google` (core), with `config.search.google` kept as an alias
property. The env var **names do not change** (`GOOGLE_OAUTH_CLIENT_ID` / `_SECRET` / `_REDIRECT_URI`
are already generic and already in `.env.example`) — only `GOOGLE_OAUTH_REDIRECT_URI`'s *value*
changes to the §4.1 path. `GOOGLE_OAUTH_STATE_TTL_SECONDS` and the refresh-skew var move with it.

### 4.5 Fold `readConnectionSecrets` into core, as its own TODO asks

`oauth.ts:14-19` carries an explicit deferral:

> `core/integrations.service.ts` exports `readAccessToken` but no refresh-token sibling … **TODO
> (follow-up): fold it into `core/integrations.service.ts` next to `readAccessToken` when that file's
> ownership frees up — the two are the same concern and should not stay in two places.**

This ticket is that follow-up. Discharge it.

### 4.6 `INTEGRATION_TOKEN_KEY` — now load-bearing for OAuth

Stale-claim #5 of the Phase-3 plan (`.env.example` documents neither `INTEGRATION_TOKEN_KEY` nor any
Phase-3 credential) is **still open** — I verified the row is absent. It now matters more than when
it was filed: the **state-token HMAC key is derived from it** (`oauth-state.ts:84-88`), so on a fresh
box the OAuth flow fails at state-mint, not merely at token-seal. Add the row here.

## 5 · Ticket split + tiering

WD-23A splits in two. This gives a clean bisect point and, more importantly, **moves real work
inside the credential wall**:

| ID | Title | Tier · Model | Credentials | Deps |
|---|---|---|---|---|
| **WD-23A-1** ⚡ | **Promote Google OAuth to core** (§4.1–4.6): core `google-oauth/` + core state table replacing `0060`, surface registry, shared callback + search alias, config move, `readConnectionSecrets` fold, `.env.example` rows. **Behaviour-identical — zero new capability.** | senior-be · **opus·medium** | **NONE** | — (startable today) |
| **WD-23A-2** ⚡ | **Register the Drive surface + read APIs:** `google_drive` registry entry (`drive.readonly` + `drive.file`), `GET /api/:t/integrations/google/files?q=`, connect route for `owner_kind='user'`, Connections-tab wiring | senior-be · Sonnet·high | **OQ-9** | WD-23A-1 |

### Why WD-23A-1 keeps the Opus seat (the justification changes, the flag does not)

The original flag argued *"OAuth CSRF/state-machine bugs pass happy-path tests and are
exploit-grade."* That reasoning is now **inverted but not weakened**: we are no longer writing the
state machine, we are **relocating a live, adversarially-verified one that another department depends
on**. A subtly wrong move silently downgrades guarantees SEO proved — e.g. dropping the
`{ modules: […] }` scoping wrongly, breaking the canonical-re-encoding HMAC recomputation, or losing
the "claim the row *before* checking the binding facts" ordering (deliberate: a state fed into a
failing callback must still be spent). Each of those passes every happy-path test. Refactors of
hardened security code are the *classic* case for start-on-Opus, because the failure is invisible.

### Regression oracle — the AC that matters most

**WD-23A-1's controlling acceptance criterion:** the entire existing search Google suite —
`google-oauth-adversarial-qa.test.ts`, `oauth-state.test.ts`, `google-oauth-keycloak.test.ts`,
`google-oauth.sandbox.test.ts`, `google-oauth-error.filter.test.ts`,
`search-google-oauth.controller.test.ts`, `search-google-gsc-ga4.test.ts` — **passes unmodified**,
with only import paths adjusted. A test that has to be *edited* to pass is a behaviour change and
must be justified line-by-line in the evidence doc or reverted.

Two hard sub-ACs, both learned from this estate's own history:

1. **The `search` module gate must be provably gone for Drive** — a tenant with `search` **disabled**
   completes a `google_drive` link end-to-end. Assert it with a positive control (the same tenant
   still cannot reach search's surfaces). *Correct-but-unwired is indistinguishable from absent* —
   this estate has hit that pattern six times per the SEO tracker.
2. **The Keycloak-gated test must actually run, not "skip by design."** Per the SEO memory,
   `google-oauth-keycloak.test.ts` needs `KEYCLOAK_OAUTH_TEST=1` **plus**
   `GOOGLE_DEV_CLIENT_SECRET` (from
   `GET /admin/realms/gaiada/clients?clientId=google-dev/client-secret`) or it silently skips. A
   silent skip here would let the refactor land with its strongest oracle switched off. Evidence must
   show the test **executed**, with counts.

## 6 · Knock-on amendments to the Phase-3 plan

1. **LD-13 is superseded** by §4 above. In particular the plan's *"mint a 128-bit nonce, store
   server-side in Redis `oauth:state:<nonce>`"* is **rejected** — the shipped design uses a signed,
   RLS-protected, single-use **Postgres** row, which is strictly stronger (survives a Redis flush,
   auditable, and its atomic-consume anti-replay is DB-enforced). Redis is not used for OAuth state.
2. **LD-13's `GET /api/:tenantId/integrations/google/connect`** stays (tenant-scoped, auth'd start),
   but the callback path changes per §4.1.
3. **WD-23B unchanged** — `projects.drive_folder_id` migration, `meta.driveChangesCursor`,
   `startDriveSweepLoop`, and its no-n8n constraint all still hold. It now depends on WD-23A-**2**.
4. **WD-24 unchanged.**
5. **WD-27** gains: a cross-department regression probe that SEO's GSC/GA4 pulls still work after the
   promotion, and an assertion that exactly **one** Google OAuth state machine exists in the tree.
6. **Wave plan:** WD-23A-1 moves **into the credential-free set** — it can run alongside the Phase-3
   leftovers instead of waiting on OQ-9. W3 becomes WD-21 (OQ-2) ∥ WD-23A-2 (OQ-9).

## 7 · What this changes for the owner

- **OQ-9's shape changes.** When registering the Google OAuth client, the authorized redirect URI to
  register is now `https://<erp-host>/api/integrations/google/callback` (+
  `http://localhost:3004/api/integrations/google/callback` for dev) — **not** the search path. Scopes
  become the union across surfaces: `webmasters.readonly`, `analytics.readonly`, `adwords`,
  `drive.readonly`, `drive.file`.
- **One less Opus-seat build, one more Opus-seat refactor** — roughly cost-neutral in tokens, but it
  removes a permanent duplicate-security-surface liability from the estate.
- **Phase 3 regains startable work** while all three OQs remain open.
