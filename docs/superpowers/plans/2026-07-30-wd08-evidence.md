## 5. Regressions filed (not fixed, per doctrine)

### WD-08-R1 — n8n bridge webhook returns HTTP 200 even when the bridge-secret check fails

- **Severity:** Low (no data exposure or bypass — the workflow's own Code node correctly throws
  `bad bridge secret` and refuses to create anything; confirmed 0 rows written for two live
  wrong/missing-secret probes). The gap is purely in the HTTP status code returned to the caller.
- **Where:** `automation/workflows/mtg-dispatcher.json` — the Webhook trigger node is configured
  `responseMode: "responseNode"`; when the "Verify secret + dedupe" Code node throws before
  reaching a "Respond to Webhook" node, n8n's default behavior for this configuration returns
  `200` with an empty body rather than a `401`/`403`.
- **Repro:**
  ```
  curl -X POST http://localhost:5678/webhook/mtg/recording-complete \
    -H "x-gaiada-bridge-secret: wrong" -d '{"v":1,"meetingId":"probe","tenantId":"...","transcript":"x"}'
  → HTTP 200 (empty body)
  ```
  paired with the n8n execution log showing `status='error'`, error `bad bridge secret`
  (`execution_entity` id 283/284 in this session).
- **Impact:** a monitoring/alerting system watching this endpoint's HTTP status codes cannot
  distinguish a rejected (bad-secret) request from a successful one — this could mask a
  brute-force/probing attempt against the bridge secret. No actual data is exposed or created.
- **Owner / fix tier:** senior-integrator (n8n workflow author) — add an explicit
  "Respond to Webhook" error branch (or a workflow-level `onError` setting) that returns 401/403
  with a generic body when the secret-verification Code node throws, mirroring how
  `pipeline-delivery.json`'s other branches already use explicit response nodes.

### WD-08-R2 — Ingest dedupe response omits `runId` (cosmetic; no functional impact observed)

- **Severity:** Very low / informational.
- **Where:** `platform-nest/src/core/meetings.controller.ts` `ingest()` — `dispatch.runId ??
  null`; on the dispatcher's dedupe branch, the n8n workflow's response to the ingest proxy
  apparently doesn't include a `runId` key (only `deduped:true`), so a re-post's response is
  `{"ok":true,"runId":null,"deduped":true}` instead of echoing the original run id.
- **Repro:** see §1.3 above — first ingest returns `runId` populated; the immediate re-post
  (same recording, same `meeting_id`) returns `runId:null,deduped:true`.
- **Impact:** none observed — `meeting_recordings.pipeline_run_id` is set via `COALESCE($2,
  pipeline_run_id)`, so the link established by the FIRST ingest is preserved and the recording
  correctly stays linked to its run (confirmed via `SELECT` in §1.3). This would only matter if a
  recording could reach the dedupe branch WITHOUT ever having been linked first (e.g. a true race
  between two recordings sharing a `meeting_id`, which the `meeting_id` UNIQUE-per-recording model
  makes structurally unlikely).
- **Owner / fix tier:** medior (n8n workflow, `mtg-dispatcher.json`'s dedupe response mapping) —
  low priority, informational only; worth a one-line fix if that workflow is touched again for
  another reason.
