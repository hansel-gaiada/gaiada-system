## Tables added, with their RLS block

| Table | Wall | Predicate |
|---|---|---|
| `employees` | HR module (THIRD wall) | `tenant_id = ANY(app_current_tenants()) AND app_module_allowed('hr')` on both USING and WITH CHECK |
| `positions` | CORE (plain) | `tenant_id = ANY(app_current_tenants())` on both USING and WITH CHECK |
| `position_roles` | CORE (plain) | same as `positions` |
| `position_assignments` | CORE (plain) | same as `positions` |
| `position_grant_claims` | CORE (plain) | same as `positions` |

All five: `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`, one `tenant_isolation` policy
`FOR ALL`. `employees` deliberately gets the **different**, module-gated predicate — design §2
preamble is explicit that the four position-family tables are core/platform-wide-read (the
reconciler, dept-head surface, and admin flows all need to read them without declaring a module
scope), while `employees` sits behind the same third wall as every other `hr_*` table (0028/0081).
Getting this backwards in either direction was the one-line mistake the design doc's own preamble
warns about, so each table's wall is written out explicitly in the migration rather than looped
generically the way 0093's `hr_*` DO-block does.

## The `employees` module-wall proof

Four tests, non-vacuous in both directions (asserts BOTH the zero-row case and the non-zero case
against the identical row, so the test cannot pass by accident):

1. `withHr([A])` (tenant A + `app.scopes='hr'`) sees the row — non-zero, establishes the row exists.
2. Plain `withTenants([A])` (right tenant, **no** module scope declared) — **zero rows**.
3. `withTenants([A])` with `app.scopes='finance'` (right tenant, **wrong** module scope) — **zero
   rows** (catches the "unset vs. wrong" distinction the WD-23A-1 regression class hinges on).
4. `withHr([B])` (**wrong** tenant, **right** module scope) — **zero rows**.
5. `WITH CHECK`: an INSERT under plain `withTenants([A])` (no hr scope) is rejected by RLS, not
   merely filtered on read.

## Cross-tenant isolation proof (core wall)

`positions` (representative of the four core tables — all four share the byte-identical predicate):
a row inserted under tenant A is visible under `withTenants([A])` and invisible (zero rows, no
error) under `withTenants([B])`; an unset GUC (`withGlobal`) also reads zero rows; an INSERT
attempting to smuggle a tenant-B row while authorized only for A is rejected by `WITH CHECK`
(`row-level security` error). The FORCE-RLS sweep (`pg_class.relforcerowsecurity`) confirms all
five new tables in one query, and the exact policy shape (`tenant_isolation`, `FOR ALL`) is
asserted for the four core tables in a second query.

## The §2.3 guard trigger — what's implemented vs. deferred

The design's trigger has three clauses. **(a) denied-role registry** and **(c) scope-shape check**
are implemented in `position_roles_guard()`. **(b) the `ui_grantable` bundle check is DEFERRED to
P2-03**, flagged explicitly in the migration's own header comment and in the trigger function's
body — `permissions.ui_grantable` does not exist yet (P2-03 owns that column per design §7), and
this ticket is explicitly scoped to schema only and forbidden from touching the permission catalog
("those are P2-02/03/04's tickets and would collide"). P2-03 extends the SAME trigger function via
`CREATE OR REPLACE FUNCTION` — no migration renumbering, no new trigger name — the moment the
column exists. This is a real, acknowledged gap in "the trigger rejects ... a non-grantable
bundle" as literally stated in the design doc's own P2-01 acceptance row; I judged it correctly
scoped given the ticket's explicit "do NOT touch the permission catalog" instruction, but flagging
it here rather than silently satisfying the letter of the acceptance criterion while missing its
substance.

The (c) scope-shape check is a **hand-mirrored, hardcoded snapshot** of
`src/rbac/scope-constrained-roles.json` (IAM-SEC-06) as of 2026-08-13, because Postgres cannot
import that generated JSON file. This is flagged in the migration header as a deliberate
duplication seam: if `derived_roles.yaml`'s scope conditions ever change, this CASE block needs a
hand-updated follow-up migration. It is defense-in-depth (the design's own words: "the trigger is
the layer that survives a forgotten guard"), not the primary enforcement point.

## `user_roles.origin_approval_id` — one small addition beyond the literal design text

Design §2.5 describes `origin_approval_id uuid NULL` with no FK. I added
`REFERENCES automation_approvals(id)` because `automation_approvals.id` is a plain `uuid PRIMARY
KEY` (unlike `webdev_provisioned_sites.approval_id`, which stayed FK-less specifically because
`automation_approvals` lacked a composite `(id, tenant_id)` unique at the time — not a concern here
since `user_roles` has no `tenant_id` column to composite against anyway). A real FK is strictly
more correct than a bare uuid with no integrity check, and costs nothing since the target table and
column already exist. Not flagging this as a deviation requiring approval — it is additive
referential integrity, not a behavior or shape change.

Per design §11 (owner decision 2026-08-13: label only, no encryption/scrubbing this wave):

## "One primary per person" — explicit call-out

The ticket's rule 5 says the design calls for "one primary per person, no overlapping active
assignment." I could not find an `is_primary`-shaped constraint anywhere in design §2.4's actual
`position_assignments` table — it lists only the temporal EXCLUDE constraint ("no overlapping
duplicate of the same seat by the same person; plurality across different positions is allowed").
The design's only other mention of "primary" is §1/§12 Q6: `users.title` becoming a **future**
one-way display mirror of "the primary position's title" — explicitly deferred, not built here, and
the ticket's own OWNER DECISIONS section says not to design anything that prevents it later but not
to wire it now. I implemented exactly the EXCLUDE constraint the design's table actually specifies
(no `is_primary` column, no additional uniqueness beyond it) and verified a person CAN hold two
concurrent different positions with no primary designation (owner decision Q3, "plurality is
allowed"). If "one primary per person" was meant as a real additional constraint rather than a
paraphrase of the EXCLUDE constraint's "same seat, same person" semantics, that is a design
ambiguity to resolve with the architect before P2-05/P2-10 build against it — flagging rather than
guessing.

## Fixes made while writing the tests (not schema changes)

Three test-authoring bugs were caught and fixed during this ticket's own verification, none of
which required touching the migration:

1. An assertion compared an alphabetically-sorted DB result against a manually-ordered expected
   array — fixed by sorting both sides.
2. The TEETH test tried to `DROP TRIGGER` through the app pool (`platform_app_test`), which does
   not own `position_roles` — fixed by using `adminPool()` (the migration-owner connection) for the
   DDL toggle, while keeping the INSERT itself on the RLS-bound app pool.
3. A "positive control: unconstrained role" test used `member`, which is actually **constrained**
   in `scope-constrained-roles.json` (reachable: company/global/project — not org_unit) — fixed by
   switching to `agency_approver`, the JSON's own documented example of a role absent from the map.
