### The grain
One **user** in one **tenant**, not one assignment. Design §3.1 defines desired state as the union
over a person's active seats, and that union is only computable per-user. Every entry point
(`reconcileAssignment`, `reconcilePosition`, `reconcileTenant`, `sweepPositionDrift`) resolves to a
user set and drives `reconcileUser`.

## 2. Each carried invariant + its adversarial proof

All proofs are in `position-reconciler-adversarial.test.ts`. Each sets up the collision *first*.

### A2 refcount — two assignments must not double-revoke
**Carried as:** claims are the liveness truth; `managed_by_position` is only a marker. Teardown
drops a claim, re-counts, and deletes the grant only at zero.

**Adversarial proof (VECTOR 1):** two positions *both* conferring `member @ company` to one user →
asserts **one** grant with **two** claims. Closing the first seat asserts `revoked === 0` and the
grant still standing. Only closing the second deletes it.

> **This test caught a real bug in my first implementation.** I keyed the "still desired" check by
> *artifact id*. When seat A closes and seat B still wants the same grant, the artifact is still
> desired — so an artifact-keyed check kept **every** claim on it, including seat A's. The refcount
> never decremented and the closed seat stayed attached to a live grant forever. That is the
> binding criterion ("zero grants tagged to the closed assignment remain") failing outright. Fixed
> by keying on the `(assignmentId, grantId)` **pair**; the comment at `computePlan` records why.

### A2 manual-grant adoption — neither stolen nor duplicated
**Carried as:** `classifyExisting()` returns `skip_manual` when both markers are NULL. No claim is
recorded, no marker is stamped, no second row is minted. Because no claim exists, a later close
structurally cannot decrement it.

**Adversarial proof (VECTOR 2):** a hand-made grant lands *first*, then a position conferring the
identical `(role, scope)`. Asserts `granted === 0`, exactly one row, `managed_by_position` still
NULL, **zero** claims. Then closes the seat and asserts `revoked === 0` and the manual row intact.

The race version is also covered: if a manual row wins the `ON CONFLICT` race, the marker `UPDATE`
is pinned `AND managed_by IS NULL AND managed_by_position IS NULL`, matches zero rows, and the code
takes the leave-alone branch rather than claiming it.

**VECTOR 3** proves the same for a *service*-reconciler-owned row (`managed_by` set, against a real
`service_assignments` row — the FK is live): not claimed, not re-marked, not torn down.

### A16 orphan freeze
**Carried as:** `hasOrphanedSeat()` short-circuits `computePlan` to an empty plan. Grants freeze
standing; nothing is diffed. Deliberately conservative — one orphaned seat freezes the whole user,
because every error in that direction leaves access *unchanged*.

**Adversarial proof (VECTOR 4):** builds a grant, flips the position to `orphaned`, asserts
`orphaned === true`, `revoked === 0`, grant still present.

### FOR UPDATE lock ordering
**Carried as:** verbatim from the service reconciler's QA V3 fix — lock the artifact `FOR UPDATE`
**before** touching its claim, then drop, then re-count. `plan.revokes` is sorted by artifact id in
`computePlan` (so the dry-run shows the real lock order too), giving a stable global order across
all transactions; overlapping teardowns cannot deadlock.

**Adversarial proof (VECTOR 7):** two seats share one artifact, both close, then two
`reconcileUser` calls race via `Promise.allSettled`. Asserts the specific leak — *a live grant with
zero claims backing it* — did not occur: grant gone, both assignments at zero claims.

### A1 in-transaction re-verification
The plan is recomputed **inside** the writing transaction, never carried in from an earlier read.
The batch path's pre-plan is used **only** for the brake; each user is re-planned before applying.

### A14 adoption hook
`adoptPositionGrantAsManual()` clears the marker and drops the claims. Proven: after adoption, a
seat close yields `revoked === 0` and the row survives as manual.

## 3. The flag

**`POSITION_SYNC_ENABLED`** → `config.positionSyncEnabled`. **Dark by default** (`=== "1" || ===
"true"`, same shape as `serviceAssignmentsEnabled`). Every entry point returns `null` before
reading anything when off. Event *handlers* are registered only when the flag is on, and re-check
it internally.

Also added: `POSITION_MASS_REVOKE_THRESHOLD` (default `20`) and
`POSITION_DRIFT_SWEEP_INTERVAL_MS` (default 24h).

---

## 4. The mass-revoke brake, and proof it fires

**Threshold: 20** (design §3.2's "~20"), configurable. It counts grants that would actually be
**deleted** (refcount reaching zero), not claims dropped.

It fails **closed**: the run aborts with `MassRevokeBrakeError` before anything commits, rather
than applying the first N. Two grains:

- **per-user** — checked inside the writing transaction.
- **per-batch** — `reconcileUsers` plans *every* user read-only first, sums the revocations, and
  refuses the whole batch if the total is over. This grain is the one that matters: a per-user
  brake alone cannot catch *"an org edit revoked one grant each from four hundred people"*, because
  every individual plan is under threshold and the damage exists only in the sum.

**Proof (VECTOR 5), at the real default:** 21 users on one seat, seat retired → every holder loses
their grant at once. Asserts `rejects.toThrow(MassRevokeBrakeError)` **and then loops all 21 users
asserting each still has their grant** — a brake that trips after revoking the first twenty is not
a brake. Then `{force: true}` applies all 21. VECTOR 5b proves the per-user grain with the
threshold lowered to 1, likewise asserting both grants survived the refusal.

## 5. Dry-run

`computePlan()` is the single collector. `dryRun` and the real path call **the same function** —
preview and action cannot diverge because there is no second implementation. `revokes` are sorted
in the planner, so the preview even shows the real lock order.

**Proof (VECTOR 6):** dry-run writes nothing, then the real run's plan is compared field-by-field
against the preview's. Also asserts `own_unit` resolves to `scope_type='org_unit'`,
`scope_id='d-dry'` (the position's own node id).

## 6. THE BINDING ACCEPTANCE CRITERION — verbatim

`position-reconciler-mover.test.ts`, run with `CERBOS_URL=http://localhost:3592` against
`gaiada-test-cerbos`, **restarted immediately beforehand** (`docker restart gaiada-test-cerbos`;
`StartedAt=2026-08-14T04:50:53.68841312Z`; `/_cerbos/health → 200`). Cerbos does not hot-reload.

The chain is real end-to-end: **reconciler → `user_roles` → `assemblePrincipal()` → `check()` →
live Cerbos**. Nothing is hand-fed. This probes the **engine**, not a bundle — deliberately:
`role_permission_bundles.json` treats derived-role conditions as satisfied, and `org_unit_lead`'s
entire meaning *is* its condition (is the grant's `scopeId` in the resource's `unitAncestors`?), so
a bundle reports "can read_department" both before and after the transfer and is structurally
incapable of witnessing this.

```

   ✓ P2-05 — the mover criterion, live against running Cerbos > a transfer moves authorization:
     OLD department 403, NEW department 200, closed assignment holds zero grants  350ms

      Tests  1 passed (1)
```

What it asserts, in order:

- Pre-transfer: grants are exactly `[{org_unit, d-web}]`; probe OLD dept → **200**, NEW dept → **403**.
- Transfer (exactly what P2-06 will do): `valid_to = current_date` on the old seat; new position in
  `d-hr`; new assignment. Reconcile → `granted === 1`, `revoked === 1`.
- **(a)** claims on the closed assignment: **0**. Grants: exactly `[{org_unit, d-hr}]`.
- **(b)** probe OLD dept → **403**. Probe NEW dept → **200**.
- **(c)** `session_version` strictly greater than before.

Both resources are probed in **both** directions across the transfer, so a Cerbos returning a
constant answer — or serving stale policy — fails this test rather than passing it.

*Honest scoping:* 403/200 are the platform's documented mapping of `EFFECT_DENY`/`EFFECT_ALLOW`,
asserted through a `httpStatus()` helper. I did **not** drive an HTTP controller, because no
positions HTTP surface exists yet (P2-08/P2-12). The authorization decision itself is the live
engine's.

## 7. Where I sit relative to `sweepMemberships()` — for P2-06

`org_unit_memberships` is DERIVED from the org blob by `sweepMemberships()` on every
`PUT /companies/:id/org-structure`. **This reconciler never reads or writes `org_unit_memberships`
and never reads the org blob.** Its only link to the org chart is `positions.unit_node_id`, which it
treats as an opaque string used to resolve an `own_unit` scope. The two pipelines are therefore
independent projections of the same chart, and **nothing here constrains P2-06**: it can move a
person's blob node through the existing PUT pipeline untouched — `sweepMemberships()` re-derives
memberships exactly as today — while the position side is driven separately by the close/open
assignment pair the transfer also writes. P2-06 closes the old seat (`valid_to = current_date`),
opens the new one, and calls `reconcileUser()` (or emits `position_assignment.closed` /
`.created`). The mover test above performs precisely that sequence, so the seam is already proven.

## 8. Event wiring

`registerPositionEventHandlers()` registers **core** handlers (not a second dedicated consumer
group — this reconciler is single-tenant and needs none of ORG-6's cross-tenant leg accounting) for:

- `position_assignment.{created,closed,updated}` → `reconcileAssignment`
- `position.{updated,retired,orphaned,roles_changed}` → `reconcilePosition`

**The streams `position_assignment` and `position` ARE in `startConsumerLoop([...])`** in
`main.ts`, spread from the exported `POSITION_STREAMS` so there is one list, not two hand-copied
ones. They are listed **unconditionally** (handlers are what the flag gates) so an always-drained
stream can never accumulate a backlog that a flag flip suddenly replays.
`position-consumer.test.ts` statically pins the agreement, including that every trigger's entity
type is covered.

**No feedback loop:** the reconciler emits `position_grants.reconciled` and `iam.drift_detected` on
the `position_assignment` entity type. Handlers are keyed by *event type* and neither is
registered; a test asserts that explicitly so nobody adds a wildcard later.

**Nothing emits the trigger events yet** — P2-06/P2-12 are the producers. This wiring lands dark
and inert on purpose.

## 9. The drift sweep and the RLS trap

`sweepPositionDrift()` reports drift and emits `iam.drift_detected`; it does **not** self-heal
(design §3.4: no silent self-heal while the flag is young). It uses `withGlobal` only to enumerate
tenants, then re-enters `withTenants([tenant])` per tenant, and **asserts the GUC actually took**
(`SELECT $1 = ANY(app_current_tenants())`) before reading — because an unset GUC returns zero rows
and would report a clean bill of health for a tenant it never looked at. An adversarial RLS test
also proves `computePlan` under the wrong tenant's GUC sees zero desired grants and does not leak.

⚠ `sweepPositionDrift()` is **exported but not yet started on a timer** in `bootstrap()`. See
follow-ups.

## 10. Two deviations from the design text — both forced by file ownership

Recorded here so they are decisions, not holes.

1. **The revoke statement.** Design §3.2 specifies a delete pinned by `managed_by_position IS NOT
   NULL`. That belongs in the choke point, which this ticket may not modify, and the writer guard
   correctly reds any bespoke delete elsewhere. The choke point's `revokeManagedGrant()` guards
   `managed_by IS NOT NULL`, which a position-owned row **never** satisfies (0109's exclusivity
   CHECK) — calling it would silently delete nothing. So the file calls `revokeGrantById()` and
   enforces ownership itself, in-transaction, **under the `FOR UPDATE` lock it already holds on
   that exact row**: re-read post-lock, delete only if `managed_by_position IS NOT NULL`. This is
   atomically equivalent — the lock precedes the ownership read, so the A14 adoption path blocks
   behind it and cannot interleave. VECTORs 2 and 3 prove manual and service-owned rows are
   untouchable through it.
   **→ Follow-up for the architect: add `revokeManagedPositionGrant()` to the choke point and
   repoint this one call.** That restores the guard to the statement and is strictly better; it
   only needs an owner for `grant-write.service.ts`.

2. **Stamping the marker.** `GrantSpec` has no `managedByPosition`. The row is inserted through the
   choke point, then marked by a following `UPDATE user_roles SET managed_by_position = …` in the
   same transaction — a provenance-only update the writer guard **explicitly** sanctions ("updates
   (managed_by, managed_by_position, expires_at) are fine and are not flagged"). The intermediate
   marker-less row is never visible outside the uncommitted transaction, and the update is pinned so
   it can never re-stamp a manual or service-owned row.

Two guard suites shaped the final code, which is the guards working:
- `user-roles-writer-guard.test.ts` red-flagged my **header comment** for containing the literal
  delete statement while quoting the design (the sweep is raw text). Reworded.
- `managed-by-invariant.test.ts` red-flagged passing `managedBy:` at all. Correct — `managed_by` is
  the *service* reconciler's marker and the 0109 CHECK forbids both. The field is optional and
  defaults to null, so it is now simply not supplied.

## 12. What I left to P2-06, and other follow-ups

**For P2-06 (transfer capability):**
- Close the old seat with `valid_to = current_date`, open the new one, then call `reconcileUser()`
  or emit `position_assignment.closed` / `.created`. The mover test performs exactly this.
- Move the person's blob node through the **existing** org-structure PUT pipeline — nothing in this
  reconciler blocks that, and `sweepMemberships()` is untouched.
- Both writes (close + open) should be in **one transaction** so a crash can't leave a person
  seatless; the reconciler is idempotent either way, so a redelivered event converges.

**Open follow-ups (none blocking this ticket):**
1. `revokeManagedPositionGrant()` in the choke point — deviation (1) above. Architect call.
2. `sweepPositionDrift()` is not started on a timer in `bootstrap()`. Wire it behind
   `positionSyncEnabled` + `positionDriftSweepIntervalMs`.
3. The expiry half of design §3.4 (revoking `expires_at < now()` override grants) is **not built** —
   it belongs with P2-08, which owns the override-grant surface that creates those rows.
4. Manual `POST /api/:t/positions/reconcile` (+ `?dryRun=1` / `?force=1`) is not built — needs a
   controller and capability. `reconcileTenant`/`reconcileUser` already accept `{dryRun, force}`, so
   it is a thin controller over an existing API.
5. Orphaned-position **auto-retire after TTL** (design §3.3) is not built; freeze works, escalation
   does not.
6. No producer emits the trigger events yet, so the wiring is inert until P2-06/P2-12 land.
