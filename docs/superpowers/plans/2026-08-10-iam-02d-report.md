## Per-role recommendation, with evidence

**All six: SEED. None recommended for deletion.** Deleting any of them would require edits to
Cerbos policy files and/or `rbac.ts` — both explicitly out of this ticket's scope — and I found no
evidence any of the six is a naming mistake rather than a real, deliberately-modeled tier with a
missing seed. Seeding is strictly additive (D-1): it makes a name grantable, confers nothing to
anyone, and changes zero existing authorization decisions.

### `team_lead` — SEED (confirmed live PM blocker, but not a hard-ungrantable defect)

Real, live-relevant raw-grant role: `derived_roles.yaml`'s `team_lead` derived role matches
`g.role == "team_lead" && g.scopeType == "team"`, referenced across ~27 resource policies with PM
read+update parity with `member` (`resource_pm_task.yaml` line 15's rule lists
`company_admin/manager/member/viewer/team_lead` together). `rbac.ts`'s own "Gap 2" comment
documents the full grant sweep it added for this role.

**Correction to the ticket's framing:** `team_lead` is not actually hard-ungrantable today.
`platform-nest/src/core/teams.controller.ts`'s `teamLeadRoleId()` (lines 17–31) already lazily
`INSERT`s this exact global row — guarded by 0073's `roles_global_name_uniq` partial index — the
first time anyone is promoted via `POST /api/:tenantId/teams/:teamId/members {role:"lead"}`. The
zero-row live state means nobody has used that endpoint on gda-aicenter yet, not that the code path
is broken (verified: `src/core/teams.test.ts` exercises this path and passed against the local test
DB, both before and after 0091). Seeding it up front removes the first-call race, makes the role
visible in any admin role-listing UI *before* the first promotion, and unblocks any PM caller that
needs to grant `team_lead` without first creating a Team and promoting someone through it.

### `viewer` — SEED (the "needs a real call" role; call is: seed it, it is not a duplicate of `member`)

Real, distinct raw-grant role (`g.role == "viewer"`, company/global scoped exactly like `member`),
referenced in ~30 resource policies as the read-only baseline, PLUS one genuine oddity confirmed by
reading `resource_pm_task.yaml` directly: line 15's `read`+`update` rule lists
`viewer` beside `member`/`team_lead`/`manager`/`company_admin`, while line 20's
`create`/`delete`/`manage` rule excludes it. So a `viewer` grant is read-only everywhere except
`pm_task`, where it can pass the ball / make execution edits exactly like `member`.
`platform-ui/src/lib/rbac.ts` already models this precisely (`viewer: ["pm.contribute"]`, matching
`member`'s capability set) with an explicit comment trail ("Gap 3"). This capability set matching
`member`'s is intentional documentation of a real, narrower Cerbos tier — not evidence the role is
redundant. `src/modules/pm/pm-adversarial-authz.test.ts` has a dedicated tier-boundary test
(`"viewer: read-only everywhere — denied create/delete/manage, allowed read"`) that passed against
the seeded role after 0091. **Call: seed it.**

### `it_manager` / `it` — SEED (confirmed: exact enforcement synonyms of `it_admin`, but real code checks the names)

`derived_roles.yaml`'s `it_staff` derived role matches `it_admin`/`it_manager`/`it` with the
IDENTICAL OR-condition and scope (lines 74–82); `resource_device.yaml` is the ONLY Cerbos policy
that reads any of the three, and it does not distinguish between them. So in Cerbos enforcement,
`it_manager`/`it` are exact synonyms of the already-seeded `it_admin` — seeding them changes zero
Cerbos decisions. They are not dead names, though: `src/admin/admin-systems.controller.ts` (~line
165) explicitly checks `r.role === "it_admin" || r.role === "it_manager" || r.role === "it"` to
gate the admin systems console, and `rbac.ts` models all three as distinct IT-operator tiers
(`it_admin: ["it.manage","company.manage"]`, `it_manager`/`it`: `["it.manage"]`). Seeding lets that
already-built three-tier UI model actually be assigned.

**Side finding, not fixed (out of scope):** `rbac.ts`'s `it_admin: [..., "company.manage"]` is an
over-claim — `resource_company.yaml` grants `update`/`delete` on `company` to `company_admin` only,
never to `it_staff`/`it_admin`. The UI would show an IT admin a "manage company" affordance the
server refuses. Flagging for the IAM-01/02 catalog work; not touched here (rbac.ts is off-limits
for this ticket, and it's a UI-side over-claim rather than an ungrantable-role defect).

### `search_staff` / `search_manager` — SEED (mandatory: this is the live defect class the ticket asked me to verify)

**Confirmed, live code defect — the pre-0069 reports bug, reproduced for `search`.**
`derived_roles.yaml`'s generic `module_staff`/`module_manager` pair (the same WSD-2 mechanism 0026
seeded for `hr_*` and 0069 seeded for `reports_*`) matches
`g.role == (resource.attr.module + "_staff"/"_manager")`. Every search-module `authorize()` call
passes `module: "search"` literally (verified in `search.controller.ts`,
`search-reports.controller.ts`, `search-google-ads.controller.ts`,
`search-google-oauth.controller.ts`, and all seven `resource_search_*.yaml` policy files), and
`src/modules/search/index.ts:118` registers the module under `key: "search"` — exactly the string
`service-reconciler.ts`'s `moduleRoleId()` composes into `search_staff`/`search_manager`.

`moduleRoleId(c, moduleKey, kind)` (`service-reconciler.ts` line ~89) does
`SELECT id FROM roles WHERE company_id IS NULL AND name = '<key>_<kind>'` and returns `null` on a
miss. Its one caller (line ~264) does:
```ts
const rid = await moduleRoleId(c, row.module_key, kind);
if (!rid) {
  skipped.push(userId); // module role unseeded — cannot grant; reported, never silently dropped
  continue;
}
```
So the failure mode is real but slightly less silent than the ticket brief assumed: the affected
`userId` lands in the `skipped` array of `ReconcileResult`, which the manual `/reconcile` endpoint
and the nightly sweep both return/log — but nothing surfaces it to an operator as an *error*, and
no grant is created. This is byte-for-byte the shape 0069's own header documents for
`reports_staff`/`reports_manager` before that migration landed.

**Not yet a live incident** — verified: `service_assignments` has zero rows for every
`module_key` on gda-aicenter right now, so no real user has silently lost a grant over this *yet*.
It will reproduce the instant a search-department service assignment goes active. **Seed:
mandatory**, exactly as the ticket's expected shape predicted.

## The migration (`0091_iam_02d_ungrantable_roles.sql`)

Seeds all six as global (`company_id IS NULL`) `roles` rows with a `description`. Uses the exact
established idiom from `0026`/`0069`/`0072` (`INSERT ... SELECT ... WHERE NOT EXISTS (SELECT 1 FROM
roles WHERE company_id IS NULL AND name = r.name)`) — idempotent and safely re-runnable, and
compatible with (though not solely reliant on) 0073's `roles_global_name_uniq` partial unique
index. No GRANT statements (migrations run as `platform_owner`; default privileges already cover
`platform_app`, per `migrations/README.md`). No `DELETE`/`UPDATE` DML anywhere. Grants nothing to
any user; touches no other table.

**Rollout:** purely additive, zero-downtime, no backfill, no deploy-order constraint. Safe to apply
to a live database at any time; safe to skip on a database that already has these rows (idempotent
guard). No Cerbos restart needed (no policy file changed).

## The drift test (`src/rbac/role-catalog-drift.db.test.ts`)

Three cases, run against the local disposable `gaiada-test-pg`/`gaiada-test-cerbos` containers
(`DATABASE_URL_TEST`/`CERBOS_URL` from `platform-nest/.env`), via the repo's own `initTestDb`
per-file-database harness:

1. **Every literal Cerbos `g.role == "<name>"` match has a migration-seeded global `roles` row.**
   Fully dynamic — scans every `cerbos/policies/*.yaml` file at test-run time via regex, so a
   *future* literal role name added anywhere in policy is automatically required to be seeded, with
   no test maintenance needed. Excludes six base-tier names (`platform_admin`, `group_executive`,
   `company_admin`, `manager`, `member`, `it_admin`) that are provisioned exclusively by the
   one-time `npm run seed:agency` script (`src/seed/agency.ts`'s `createRole()`), never by any
   migration — confirmed empirically (see "two real bugs" below) and documented in-file as a
   **separate, pre-existing gap**, not this ticket's defect: those six roles have no migration-level
   provisioning guarantee at all, only a manually-run script. Not fixed here (out of scope — fixing
   it means redoing 0073-shaped work for a different table).
2. **Every `module_staff`/`module_manager`-convention module (`hr`, `reports`, `search` — a
   maintained list, documented in-file as to why it can't be derived reliably: the convention is
   string-composed from `resource.attr.module` at request time, not literal in any policy file, and
   a blind scan of controller source for `module: "<x>"` string literals also matches unrelated test
   fixtures like `"not_a_real_module"`) has both `<key>_staff` and `<key>_manager` seeded.
3. **Best-effort cross-check against `platform-ui/src/lib/rbac.ts`'s `Role` union.** Reads the
   sibling project's file as plain text (not a code import — platform-ui is a separate standalone
   project per root `CLAUDE.md`) and skips gracefully with a console warning if that checkout isn't
   present alongside this one, rather than failing.

**Verified with a real positive AND negative control**, not just a green run:
- With `0091` in place: **3/3 pass** against the real test Postgres + Cerbos.
- With `0091` physically removed from `migrations/` and the harness re-run: **all 3 tests fail**,
  reproducing exactly `team_lead, viewer, it_manager, it, search_staff, search_manager` as missing
  (test 1: the non-excluded literal names; test 2: `search_staff`/`search_manager`; test 3: all six
  via the rbac.ts union) — proving the test has real teeth, not a vacuous pass. `0091` was then
  restored and re-verified green.
- `npm run lint:migration-rls`: green, 91 migrations scanned (was 90).
- Adjacent suites re-run against the same live containers to check for collateral regressions from
  adding six new global rows: `src/core/teams.test.ts`, `src/admin/service-reconciler.test.ts`,
  `src/admin/service-reconciler-adversarial.test.ts`, `src/admin/service-assignments-org7.test.ts`,
  `src/admin/org14-preflight-adversarial.test.ts`, `src/rbac/cerbos.test.ts`,
  `src/modules/pm/pm-adversarial-authz.test.ts`, `src/modules/search/search-cerbos.test.ts` —
  **98/98 passed**, including the `viewer`/`team_lead` tier-boundary cases in
  `pm-adversarial-authz.test.ts`.

**Two real bugs found and fixed while building this test** (worth recording since they're the kind
of mistake this exact defect class produces):
- My first draft required EVERY literal Cerbos role name to exist in a bare `initTestDb()`
  (migrations-only, no seed script) database — which is the wrong bar for `manager`/`member`/
  `company_admin`/`platform_admin`/`group_executive`/`it_admin`, none of which any migration seeds
  (only `src/seed/agency.ts` does, on a live deploy). Running it against the real harness surfaced
  this immediately as 6 false-positive failures; fixed with the documented `SEED_SCRIPT_ONLY_ROLES`
  exclusion.
- My `rbac.ts` parser (`text.indexOf(";", start)`) truncated the `Role` union at the FIRST
  semicolon found anywhere after `export type Role =` — which lands inside one of the union's own
  multi-line `//` comments, well before the real end of the block, silently dropping real members
  (`hr_staff`, `search_staff`, ...) while picking up comment noise (`"team"`, `"read"`, `"update"`)
  as false-positive "missing" roles. Fixed by stripping `//` line comments before locating the
  terminating semicolon. Both bugs were only caught because I ran the test against a real database
  instead of reasoning about it statically — exactly the standing lesson in memory
  `scripted-tests-miss-real-inputs`.
