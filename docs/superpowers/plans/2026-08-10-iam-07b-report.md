## 2. Guards added

1. **`platform-nest/src/rbac/cerbos-catalog-alignment.test.ts`** (6 tests, static, no DB/Cerbos
   needed) — link 1. A fourth independent re-parse of `cerbos/policies/*.yaml` (deliberately no
   import from `generate-role-bundles.mjs` or either `.db.test.ts` parity file, matching this repo's
   established convention of independent re-derivation for cross-checks). Proves:
   - every catalog kind has a `resource_*.yaml` (forward — pre-existing coverage, re-derived here
     independently);
   - every `resource_*.yaml` kind has a catalog entry (reverse — genuinely new coverage);
   - every literal (non-`*`) action named in any rule is a catalogued `(kind, action)` pair
     (uncatalogued policy action);
   - on the 5 kinds that carry **no** wildcard rule anywhere (the 4 relationship-exempt kinds +
     `rollup` — pinned count, so a kind silently gaining/losing its wildcard rule is itself visible),
     every catalog entry for that kind is backed by a literal rule (orphaned catalog entry) —
     **explicitly not claimed** for the other 56 wildcard kinds, where Cerbos's own semantics make
     that direction unprovable by static inspection (see the file's header for why);
   - no kind is defined twice across policy files.

2. **`platform-nest/src/rbac/permission-groups-catalog-parity.test.ts`** (9 tests, static) — the
   catalog↔groups gap. Proves group/advancedOnly key existence and grantability both directions,
   exhaustive coverage (every grantable key is in a group or `advancedOnly`, never silently
   missing), no group/advancedOnly contradiction, `_meta.counts` fully re-derived (catches a
   forgotten summary-block update), the mechanical `sensitive` flag rule the file's own `_meta`
   documents, and internal de-duplication.

3. **`platform-nest/src/rbac/iam-07b-chain-meta.test.ts`** (10 tests, static) — the meta-test the
   design ruling calls for explicitly ("assert the chain has no unpinned link... a meta-test
   enumerating the six"). Enumerates all 8 rows in §1's table (the six original links + the role axis
   + the 215/15 boundary, plus documents link 6 as tsc-guarded with no runtime test needed) and
   fails if any named guard file is deleted, emptied, or contains no test cases. Does not re-derive
   any authorization fact itself — it is a tripwire on the *chain's own bookkeeping*, the layer most
   likely to rot silently since a deleted test file with no production import looks like harmless

4. **Two new npm scripts + one new named CI step** (not a guard per se, but the CI wiring):
   `platform-nest/package.json` gained `test:iam-chain-alignment` (runs all three new files);
   `.github/workflows/ci.yml`'s `platform-nest` job gained a named step, "IAM permission-contract

## 4. What runs in CI vs what cannot

**All three new guards are STATIC** — pure `fs.readFileSync` + `js-yaml`/`JSON.parse`, no
`initTestDb()`, no `TEST_URL`, no live Cerbos PDP call. This matters for wiring: unlike
`role-permission-parity.db.test.ts` (needs Postgres + a running Cerbos container, per
`ci.yml`'s existing `platform-nest` job setup) or `permission-catalog.db.test.ts` (needs
Postgres), **link 1 and the groups link needed zero new service provisioning**. They already run
via the existing `npm test` step in the `platform-nest` CI job (matrix has no bearing here — this
is the dedicated `platform-nest` job, not the `test` matrix job), and the new named step
(`npm run test:iam-chain-alignment`) just makes that fact visible as its own gate before the full
suite runs, exactly mirroring the pre-existing mail-corpus step's rationale.

**Nothing in this ticket's scope is "cannot run in CI."** Every link in §1's table either already
runs in a CI job (links 2–5, role axis, 215/15 boundary — all inside the `platform-nest` or
`platform-ui` jobs, both of which run on every push to `main` and every PR per the top-of-file cost
controls) or now does after this ticket (link 1, groups link, the meta-test). Link 6 is `tsc`,
which is its own CI step (`npm run typecheck`) in the `platform-ui` job — also already wired,
also confirmed by reading the job definition, not assumed.

**Caveat, stated plainly rather than glossed over:** links 3–5 and the role axis depend on files
(`role-permission-bundles.json`, `rbac-capability-map.ts`, `permission-catalog.json`,
`permission-groups.json`) that — per `git status` at the time of this session — are either
mid-edit by other concurrently-running agents or (in the case of `permission-catalog.json` and
`permission-groups.json`) untracked (`??`), meaning **they have not yet been committed to the repo
at all.** This ticket's guards for links 1 and the groups link are real and pass against the
*current working tree*, but "the chain is green in CI on one commit" (the design ruling's own
acceptance bar, §4: "verify links 2–5 are green in CI on one commit") cannot be claimed here,
because there is not yet a single commit containing all of these files together. That verification
is DEV-VERIFIED against the live working tree in this session (§3e), not against a landed commit —
an honest gap, not a fixed one, and outside this ticket's ownership to close (I own `ci.yml` +
guard files + this report, not the catalog/groups/bundles JSON or the Cerbos policies three other
agents are actively editing).

## 5. Honest assessment — where the chain is still weakest

1. **The wildcard blind spot in link 1 is real and named, not hidden.** For the 56 of 61 kinds that
   carry a `platform_admin` (or similar) wildcard rule, `cerbos-catalog-alignment.test.ts` cannot
   prove a catalog entry is "orphaned" (no rule could ever grant it) by static inspection alone,
   because Cerbos's own `*` semantics mean any action asked of the PDP matches. The only way to close
   that residual 56-kind gap is to cross-check the catalog against what handlers actually *ask*
   Cerbos for (a grep over `authorize()`/`can()` call sites and their literal action arguments) —
   a different, larger piece of work this ticket did not attempt. Flagging it here rather than
   letting the 6-test green suite imply full coverage of both orphan directions.
2. **The chain's commit-level integrity is unverified**, per §4's caveat — three files central to
   links 2–5 are uncommitted or mid-edit by concurrent agents. The guards are correct and green
   against the working tree; nobody has yet proven they stay green on a single frozen commit,
   because that commit does not exist yet.
3. **Link 6 has no runtime test and structurally cannot need one** — this is by design (the
   `satisfies` construction makes it a compile error), not a gap, but it is worth remembering that a
   `tsconfig.json` edit that silently excluded `rbac-capability-map.ts` from typechecking would
   silently remove this guarantee with no test anywhere noticing. Nothing currently guards the
   typecheck's *own* scope.
4. **The meta-test (§2.3) only proves guard files exist and contain test cases — it cannot prove
   they still test the right thing.** A guard file could be gutted to a single trivial
   `expect(true).toBe(true)` and the meta-test would stay green. This is a deliberate, named
   limitation (documented in the file's own header) rather than an oversight: proving semantic
   non-vacuousness for every file in the chain is exactly the mutation-based teeth-check this report
   already performs by hand (§3) and is not something a static existence check can automate away.
5. **Positive finding, stated for balance:** the catalog↔DB link (0093) that the ticket brief
   flagged as suspect turned out to already be solidly pinned, with idempotency and trigger-rejection
   coverage exceeding what this ticket would have added had it been a real gap. Not every suspected
   weak link is one — worth recording so the next drift audit doesn't re-spend effort re-verifying
   what already has teeth.
