## Part 1 — the migration

`0097_webdev_module_roles.sql` follows the 0091/0095/0096 idiom exactly: `gen_random_uuid()` id,
`company_id IS NULL`, a `NOT EXISTS` guard scoped to `company_id IS NULL` (idempotent/re-runnable),
and a closing `DO $$ ... RAISE EXCEPTION ...` assertion block proving both roles exist exactly once
after the file runs, rather than assuming the INSERT did what it looks like it did. Confirmed by
reading `0073_dedupe_global_roles.sql` directly (not assumed) that `roles_global_name_uniq ON roles
(name) WHERE company_id IS NULL` already exists — no new index needed, matching 0095/0096's own
conclusion for their roles.

No RLS on `roles` (no `tenant_id`, no policy) — the "NOBYPASSRLS + unset tenant GUC → zero rows,
reports success" trap does not apply structurally; asserted anyway via the closing block.

**Rollout:** purely additive, zero-downtime, no backfill, no deploy-order constraint. Grants nothing
to any user — it only makes `webdev_staff`/`webdev_manager` grantable names. Zero authorization
decisions change for any existing user (no `service_assignments` row for `module_key='webdev'`
exists yet on gda-aicenter, per the ticket brief's own framing — this closes the gap before the
first webdev-department service assignment goes active, not after).

## Part 2 — the generalized guard (the real deliverable)

### How it works

`deriveModuleRoleRequirements()` in `role-catalog-drift.db.test.ts`:

1. Parses every `resource_*.yaml` file's `rules:` list (`parseResourcePolicyRules`) — a
   generalization, from two named files to all 61, of the block-scoped parsing technique already
   proven out in `src/core/approval-deciders-policy-drift.test.ts` (MAIL-23). It captures each
   rule's `actions`, `derivedRoles`, **and** the raw `blockText` between the `- actions:` line and
   the next sibling rule (MAIL-23's parser only needed `derivedRoles`).
2. For every rule whose `derivedRoles` includes `module_staff`/`module_manager`/`module_approver`,
   resolves the concrete module key in priority order, stopping at the first stage that yields
   any candidate:
   - **(a) in-rule condition literal** — a `module == "<key>"`/`module: "<key>"` inside that
     specific rule's own condition text. This is the shape `resource_report_document.yaml` and
     `resource_automation_approval.yaml` use, where ONE Cerbos kind is shared across modules and the
     rule itself must pin one (e.g. `resource_automation_approval.yaml`'s `module_manager` rule is
     gated on `request.resource.attr.module == "hr"` specifically, so it does not admit some other
     module's manager).
   - **(b) whole-file literal** — the same pattern anywhere else in the policy file (most files
     document the fixed module their handlers always pass as a header comment: `resource_hr_case.yaml`,
     `resource_webdev_change_request.yaml`, `resource_webdev_provisioned_site.yaml`,
     `resource_search_property.yaml`, `resource_member.yaml`).
   - **(c) production handler call-site literal** — the ticket's own warning proved necessary in
     practice, not theoretical. `resource_agency_approval.yaml`, `resource_hr_record.yaml`, and six
     of the seven `resource_search_*` files (`campaign`/`ledger`/`keyword`/`engagement`/`audit`/
     `report` — only `property` documents it in a comment) state **no** module literal anywhere in
     the policy file itself. For these, `handlerModuleLiterals()` scans every non-test `.ts` file
     under `src/` for `kind: "<thisResourceKind>"` and reads the co-located `module: "<value>"`
     literal off the **same line** — verified as a safe, general assumption for this codebase before
     relying on it (every `authorize()` call here is a single-line object literal). Concretely:
     `agency.controller.ts` → `agency`, `hr.controller.ts` → `hr` (for `hr_record`),
     `search.controller.ts` → `search` (for all six search kinds lacking an in-file literal).
3. **Fails loud** (adds to `unresolved`, asserted empty by a dedicated test) for any rule that
   resolves to zero or to more-than-one conflicting candidate — **unless** the file is on the small,
   hand-audited `MODULE_AGNOSTIC_POLICY_FILES` allowlist. There is exactly **one** entry:
   `resource_service_assignment.yaml`. Its `module_staff`/`module_manager` rule (gating `read`) is
   genuinely module-**polymorphic**: its own header states the controller sets
   `resource.attr.module` to "the assignment's `module_key`" at runtime, and I confirmed by reading
   all 11 of `service-assignments.controller.ts`'s `authorize()` calls for kind
   `"service_assignment"` that `module` is always passed as a **bare variable**
   (`module`, `module: moduleQ || undefined`) — never a quoted literal. So
   `handlerModuleLiterals` correctly returns the empty set for it, and that emptiness is a **proven
   property of the code**, not a parser gap: this file introduces no additional role requirement of
   its own — whatever module actually applies there is already required by whichever OTHER file
   pins that module concretely.

## Part 3 — the silent skip: assessed, NOT implemented (per the ticket's own caution)

`moduleRoleId()` returning `null` in `service-reconciler.ts` produces no operator-visible signal
anywhere — the caller pushes the affected `userId` into `ReconcileResult.skipped` and continues,
and nothing surfaces that array as an error, an alert, or even a warning log. I read the full
reconciler (`reconcileAssignment`, `reconcileProvider`, `sweepDriftAndOrphans`) end to end to assess
this, not just the one call site.

**Assessment: it should raise, but the fix is not "genuinely small and safe" enough to do inside
this ticket**, for reasons specific to this file rather than general caution:

- `service-reconciler.ts` is explicitly the highest-stakes file in the backbone program (its own
  header: "a bug here is a cross-tenant access leak") and is under active concurrent editing by
  other agents in this checkout right now (per the ticket brief itself).
- The `skipped` array is deliberately overloaded today — it already carries a **legitimate,
  expected** case (a stale/bogus `assigneeId` in the org blob that never had a valid provider
  membership, guarded explicitly: "closes the unvalidated-id hole") alongside the **defect** case
  (a real, valid staff member who should get a grant but the role row is missing). A caller reading
  `skipped.length > 0` today cannot distinguish "someone's org-chart data is stale" from "an
  operator forgot to run a migration" — conflating them in a hasty fix could make the *legitimate*
  case noisy (alerting on every routine stale-assigneeId skip) or, worse, make the *defect* case
  keep hiding inside a array nobody reads, if the fix just adds a log line without separating the
  two causes.
- `reconcileAssignment` returns a value consumed by three different call sites (the outbox
  consumer, the manual `/reconcile` endpoint, and the nightly `sweepDriftAndOrphans` sweep) with
  different appropriate escalation shapes (an API response vs. a scheduled-job log vs. a metric) —
  picking the right one is a design decision, not a mechanical patch.

**Recommendation for a follow-up ticket** (not this one): split `skipped` into two distinct reasons
— `skipped: { userId, reason: "invalid_provider_membership" | "unseeded_module_role" }[]` (or two
separate arrays) — and have `sweepDriftAndOrphans` (the one call site that already runs
unattended and is meant to catch exactly this class of drift) treat any `unseeded_module_role`
entry as a **hard alert-worthy condition** distinct from routine drift, since — unlike a stale org
node — an unseeded module role is fixable by nobody except a migration, and it will otherwise
recur silently for every future module exactly as it did for `reports`/`search`/`webdev`. This
generalized drift guard (this ticket) is the structural fix for "a module's roles were never
seeded"; the `service-reconciler.ts` change would be the complementary runtime fix for "and if it
ever happens anyway, someone finds out immediately instead of by accident."
