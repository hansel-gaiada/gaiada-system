## 1. The standing rule and the two hazards this ticket was warned about

**ZERO DECISIONS CHANGED.** Every rule added below is a permission-arm mirror in its **own** new
rule, at the exact `variables.inTenant && variables.notLow` condition of the plain company-scoped
role rule it mirrors — never mixed into an existing rule (Hazard 1), and never shaped after a
scope-narrower role's own rule (Hazard 2). Concretely, per the ticket's own framing:

- **Hazard 2, flavour 1 (`group_executive`, global-only):** every kind in this batch that carries
  a `group_executive`-only rule (`integration_connection`, `report_document`, `appraisal`) has that
  rule left completely alone, same reasoning IAM-04-B4 already established for the TRAP4 kinds — a
  company-scoped permission holder mirroring a `notLow`-only, no-`inTenant` condition would gain
  cross-tenant reach the role arm never gave them.
- **Hazard 2, flavour 2 (`org_unit_lead`, org-unit-only):** `report_document` and `appraisal` both
  carry `org_unit_lead`'s own subtree-cascaded rule. The ticket asked me to demonstrate an
  equivalent mitigation or not ship a mirror at all — I could not demonstrate one, and did not
  ship one. **This turned out to be stronger than "don't mirror `org_unit_lead`'s own rule"**: it
  blocks wiring **any** permission arm at all onto either kind, on any action, this ticket — see
  §4 for the mechanism and the empirical proof.
- **Hazard 3 (self-scope, deferred):** every Pattern-B self-scoped action on all 5 kinds is left
  unmirrored. Verified against the existing regression guard (`permission-arm-hazard-scan.
  test.ts`'s PART 3) that "mirror only the unconditional half, skip the self-scoped half" is **not**
  a safe partial mirror for a Pattern-B action — it is the exact over-grant Pattern B exists to
  catch, and the guard enforces this structurally (an unconditional `perm_*` rule on a Pattern-B
  action must re-apply the self-check or must not exist at all). So for every Pattern-B action,
  nothing was wired — not the self-scoped half, not the unconditional half either.

## 4. Why `report_document` and `appraisal` get zero rules — the kind-scoped blocker, verified not assumed

Both kinds carry `org_unit_lead`'s own rule — org-unit-scope-only, no `g.scopeType=="company"`
branch at all (`derived_roles.yaml`'s `org_unit_lead` definition: `g.scopeType == "org_unit" &&
g.scopeId in request.resource.attr.unitAncestors`). `permission-arm-hazard-scan.test.ts`'s PART 3b
"REACHABILITY (other-narrow direction, IAM-SEC-04)" check (added 2026-08-12, the same day as this
ticket) is **kind-scoped**: it fails if `kindsWithPermissionArm(kinds)` (any kind carrying **any**
`perm_*` rule, on **any** action) also carries a Pattern-C hit for a scope-narrower-than-company
role. `kindsWithPermissionArm` has no per-action memory — it is a `Set<string>` of kind names.

**Verified empirically, not just reasoned:** I added a candidate `perm_report_document_read_project`
rule (mirroring the clean, Pattern-A/B-hazard-free `read_project` action) and ran the suite:

```
 [31m×[39m ... REACHABILITY (other-narrow direction, IAM-SEC-04): no company/org-unit/attr-narrower-than-global
     role is named in a kind that ALREADY has a wired perm_* permission arm
   → Pattern C (other-narrow direction) found role(s)/kind(s) that are BOTH scope-narrower-than-implied
     AND already carry a wired perm_* permission arm on the same kind
     ([{"kind":"report_document","role":"org_unit_lead","reason":{"type":"no-disjunction",
       "fields":["unitAncestors"]}}]) — this is REACHABLE today via that arm, matching the
     platform_admin defect exactly, just in the opposite scope direction and with no
     GLOBAL_ONLY_ROLES-shaped guard available. STOP wiring that kind's permission arm and report
     this, do not tune the predicate to make it pass.
```

The mechanism (from the test's own comment and `admin-identity.controller.ts`'s
`ROLE_SCOPE_CONSTRAINTS`, read directly): an `org_unit_lead` grant mis-recorded at company or global
scope (schema-permitted at the DB row level; the ONLY thing preventing it today is
`admin-identity.controller.ts`'s write-path scope guard, `ROLE_SCOPE_CONSTRAINTS["org_unit_lead"] =
["org_unit"]`, which refuses the write at the one unrestricted assignment endpoint) would bundle
into `attr.perms` at that wider scope under migration 0094's methodology, and a generic
global-or-company mirror on **any** action of the same kind would honour it — reaching company-wide
(or global) access on that action even though `org_unit_lead`'s own role-arm condition would refuse
the grant outright (its `scopeType == "org_unit"` literal never matches a company/global-scoped
grant row). This is the exact hazard the ticket's own brief named ("a company-scoped mirror of that
rule would flatten the org-unit subtree boundary into whole-company reach"), just realized one level
removed: not by mirroring `org_unit_lead`'s rule directly, but by wiring *any* mirror on a kind that
rule also lives in.

The test's own comment confirms there is no `GLOBAL_ONLY_ROLES`-shaped exclusion available for this
direction ("the only thing standing between 'mintable at a scope the role denies' ... and 'actually
exploitable' is whether a perm_* mirror exists ANYWHERE for a kind this role is named in") and
instructs: "STOP wiring that kind's permission arm and report this, do not tune the predicate to make
it pass." I stopped, reverted the candidate rule, and am reporting it here per that instruction and
per the ticket's own Hazard 2: "if you think you can [demonstrate an equivalent], report the
reasoning and DON'T ship it." I do not have an equivalent mitigation to offer — closing this
properly needs either (a) a `ROLE_SCOPE_CONSTRAINTS`-shaped **runtime** guard treated as sufficient
by policy (the ticket's own hazard framing explicitly does not trust this, by design — defense in
depth against pre-existing/direct-DB-write rows), or (b) a new Cerbos-side exclusion mechanism for
"other-narrow" roles analogous to `team_lead`'s `attr.grants.exists(...)` scope-exclusion, which does
not exist for this role shape today and is a design decision, not something I should improvise.
**Flagged as a follow-up ticket; `report_document`/`appraisal` cannot receive any permission arm
until it lands.**
