### The dept-head grant rule — its own rule, never mixed

`resource_role_grant.yaml`:

```yaml
- actions: ["create", "revoke", "read"]
  effect: EFFECT_ALLOW
  derivedRoles: ["org_unit_lead"]
  condition: { match: { expr: "variables.inTenant && variables.notLow" } }
```

Reuses the **existing** `org_unit_lead` derived role (`derived_roles.yaml`'s HIER-2 definition,
condition over `resource.attr.unitAncestors`) rather than a new one — see "Deviation from the design
text" below for why. Never appears in the same `derivedRoles` list as `company_admin` on this kind
(the TRAP-4/REG1 lesson the brief named explicitly). Identical shape on `resource_position.yaml`'s
assign/unassign/read rule.

### The structural self-target `EFFECT_DENY`

`resource_role_grant.yaml`, verbatim:

```yaml
- actions: ["create"]
  effect: EFFECT_DENY
  roles: ["user"]
  condition:
    match:
      expr: >-
        has(request.resource.attr.targetUserId) && request.resource.attr.targetUserId != "" &&
        request.resource.attr.targetUserId == request.principal.id
```

`resource_position.yaml`'s self-assign DENY is byte-identical in shape, on `actions: ["assign"]`.
`roles: ["user"]` matches every principal by construction (`cerbos.ts`'s `principalPayload()` sets
the base role unconditionally) — Cerbos combines a kind's matching rules with deny-overrides
semantics, so this beats the `platform_admin` wildcard rule that sits above it in the same file.
**Live-probed** against `gaiada-test-cerbos` (restarted, verbatim wire shapes copied from
`cerbos.ts`'s own `principalPayload()`/`resourcePayload()`):

```
PASS — role_grant.create — SELF-TARGET as platform_admin (must beat the wildcard): expected EFFECT_DENY, got EFFECT_DENY
PASS — role_grant.create — SELF-TARGET as dept head (inside own subtree): expected EFFECT_DENY, got EFFECT_DENY
PASS — position.assign — SELF-ASSIGN DENY as platform_admin: expected EFFECT_DENY, got EFFECT_DENY
PASS — position.assign — SELF-ASSIGN DENY as dept head: expected EFFECT_DENY, got EFFECT_DENY
```

### No `perm_*` mirrors wired — confirmed

**Zero** `perm_role_grant_*`, `perm_position_*`, `perm_employee_*`, `perm_it_account_*` derived roles
exist anywhere in `derived_roles.yaml` or are referenced from any of the 4 new policy files.
`role_grant`/`position` are registered **permanently-unwired** (IAM-04c §9 option C precedent — the
dept-head rule's subtree containment is an attribute-instance check a flat `perms` array cannot
re-express). `employee`/`it_account` are role-arm-only **this wave** — their role-arm rules ARE safe
global-or-company shapes (would pass `permission-arm-hazard-scan.test.ts`'s classifier), but no
handler exists yet for either kind, so wiring a mirror ahead of an audited holder population would
be exactly the premature-mirror mistake the brief warned against. `iam-04-reg1-mirror-reach-
invariant.test.ts` (run UNSCOPED) confirms no new mirror was introduced — its `discoverMirrors()`
finds zero `perm_*`-prefixed derived roles on any of the 4 new kinds.

### Deviation from the design text, flagged

1. **`role_grant`'s dept-head attribute is `unitAncestors`, not `targetUnitAncestors`** (design
   §6.2's illustrative wording). Reusing the SAME attribute name `report_document`/`appraisal`
   already use for the org_unit_lead subtree cascade lets `role_grant` reuse the EXISTING
   `org_unit_lead` derived role. A second, differently-named derived role resolving to the identical
   literal-role-and-scope shape would need its own duplicate entry in `scope-constrained-roles.json`
   and `admin-identity.controller.ts`'s `ROLE_SCOPE_CONSTRAINTS` (both machine-checked by
   `permission-arm-hazard-scan.test.ts`'s Pattern-C completeness tests, keyed off the DERIVED ROLE's
   own name) — for zero behavioral gain. Flagging for the architect to fold into §6.2's text if
   preferred over living in the policy file's own comment.
2. **`position.read` is added** beyond §6.2's literal action list (assign/unassign/create/update/
   retire only). Every downstream ticket that depends on this kind (P2-11's roster page, P2-12's
   admin UI, P2-06's employee flows) needs to read positions, and no other kind in this repo lacks a
   read action. Tier mirrors the write-action split (company_admin/hr_people_ops tenant-wide,
   org_unit_lead own-subtree).

## PART B — the `ui_grantable` allow-list (P2-03)

### The mechanism

- **Catalog:** `uiGrantable: boolean` added as a REQUIRED field on all 282 entries (`permission-
  catalog.json`). `portal.*` (7 keys) and `class:"relationship"` (15 keys) are `false`; everything
  else (260 keys, including all 18 of Part A's new keys) is `true`.
- **Completeness test** (`src/rbac/ui-grantable-catalog.test.ts`): `findEntriesMissingUiGrantable()`
  — every entry must carry a real `boolean`. **Teeth-proven**: deleting the field from
  `core.role_grant.create` on an in-memory clone, and separately setting it to a non-boolean
  (`"true"` the string) on `hr.employee.read`, both turn the check red, each followed by a REVERT
  assertion that the real checked-in file still passes.
- **Pinned invariants**, each teeth-proven the same way (flip on a clone, assert red, then assert
  the real file is still green): every `portal.*` key is `false`; every `class:"relationship"` key
  is `false`.
- **`assertRoleUiGrantable(c, roleId, roleName?)`** (`platform-nest/src/rbac/ui-grantable.ts`) — the
  single enforcement helper. Queries `role_permissions ⨝ permissions` for `ui_grantable=false` rows
  on the role's bundle; throws a `BadRequestException` naming every blocked key, message-prefixed
  `not_ui_grantable` for future typed-code matching. **Not wired into any write path** —
  `GrantWriteService` (P2-04) is the intended caller; shipped with its own teeth test
  (`src/db/iam-phase2-ui-grantable-guard.test.ts`) proving it resolves for a clean role and throws
  for a role carrying `portal.read`.
- **`position_roles_guard()` extended in place** (migration `0110`, `CREATE OR REPLACE FUNCTION` on
  the SAME trigger `0109` shipped — no renumbering, no new trigger). Clause (b) added: rejects an
  INSERT/UPDATE onto `position_roles` whose role's bundle contains any `ui_grantable=false`
  permission. Clauses (a)/(c) are byte-identical to `0109`'s version (regression-tested).

### The three teeth proofs (per the ticket's own VERIFY instruction)

1. **Remove `ui_grantable` from one entry → completeness test RED.** `ui-grantable-catalog.test.ts`
   → "TEETH: deleting uiGrantable from one entry (in-memory clone) turns the check RED" — PASSED,
   followed by "REVERT: the real, checked-in file still passes" — PASSED.
2. **Flip a `portal.*` key to `true` → pin RED.** Same file → "TEETH: flipping one portal.* key to
   true (in-memory clone) turns the pin RED" — PASSED, followed by the REVERT — PASSED. (Also proven
   for the relationship-class pin, on `core.mcp_tool.call`.)
3. **Attempt a position bundle with a non-grantable key → trigger refuses.**
   `src/db/iam-phase2-ui-grantable-guard.test.ts` → a synthetic test-only role holding `portal.read`
   (grantable, `ui_grantable=false`) is attached to a real position via INSERT — REJECTED
   (`/non-ui_grantable permission/`); the SAME violation on UPDATE (re-pointing an existing row's
   `role_id`) — REJECTED; **TEETH**: `DROP TRIGGER trg_position_roles_guard`, the identical INSERT now
   SUCCEEDS (`rowCount === 1`), trigger restored, the identical INSERT is REJECTED again. A positive
   control (`org_unit_lead`, whose bundle is entirely `ui_grantable=true`) is proven to succeed
   throughout, so the rejection is shown to be clause (b) specifically, not RLS or an unrelated FK.

All three restored-and-green, confirmed by the passing test run below.
