## 2. Enforcement at the choke point — and the boundary that matters most

The invariant set is a property of the grant's **origin**. This is the single most important
judgment call in the ticket, so it is stated plainly with its evidence.

| Invariant (design §6.3) | `legacy_admin` | `ui` | `trusted_internal` |
|---|---|---|---|
| Scope validity (`assertRoleScopeAllowed`) | ✅ unchanged | ✅ | — |
| Self-target refusal | ✅ **NEW** | ✅ | — |
| Allow-list (`assertRoleUiGrantable`) | ❌ by design | ✅ | — |
| Elevated fence | ❌ by design | ✅ | — |
| Ceiling | ❌ by design | ✅ | — |
| Subtree bound | deferred P2-08 | deferred P2-08 | — |
| Sensitive routing | deferred P2-08 | deferred P2-08 | — |

**Why the legacy surface does NOT get the last three — this is not laziness, it is pinned by
existing tests.** Design §6.4 says the legacy surface "keeps today's semantics this wave — minus
one tightening: target == caller is refused", and §6.3's own preamble scopes its invariant list to
"all NEW surfaces". §6.3.6 is explicit that "the only doors to the elevated tier remain the
existing global-scope-guarded admin path and seeds". The evidence that this reading is correct and
the alternative would be an outage:

- `global-only-role-scope.test.ts` asserts `client @ company` **succeeds** through *both*
  `assignRole` and `inviteUser`. `client`'s bundle is 7 `portal.*` keys, **every one
  `ui_grantable = false`**. Applying the allow-list to `legacy_admin` breaks both tests and the
  live client-portal onboarding flow.
- The same file asserts `platform_admin @ global` **succeeds**. Applying the elevated fence to
  `legacy_admin` breaks it and removes the only remaining door to the elevated tier before
  IAM-16's two-person appointment flow exists.
- `company_admin`'s bundle (248 keys) does not contain `portal.*`, so applying the ceiling to
  `legacy_admin` would stop a company_admin granting `client` at all.

Both boundaries are **pinned in the new suite in the positive direction** ("BOUNDARY (deliberate)"
tests), so a future "let's make this consistent" change turns red with the reason attached rather
than silently breaking onboarding.

**Deferred to P2-08, explicitly:**
1. **Subtree bound** (§6.3.1) — needs the `role_grant` Cerbos kind live-probed with a
   server-derived `unitAncestors` feed from `org_unit_closure`. P2-02 registered the kind; no
   handler populates the attribute yet. A half-version invented here would be frontend-first drift
   applied to authorization.
2. **Sensitive-key routing to an override request** (§6.3.7) — needs `decide_override` and the
   `automation_approvals` seam, both P2-08's.
3. **Endpoint-level reach for the `ui` origin.** No endpoint uses it yet (P2-08 owns the
   controller), so the ceiling/allow-list/fence are proven at service level against the real DB,
   not through `app.inject`. Stated plainly rather than papered over: I did not build a P2-08
   endpoint to manufacture an endpoint-level proof, because that would step on its ticket.

### The one existing test I had to change — and why

**`src/admin/managed-by-invariant.test.ts`, part 6 (the static sweep) only.**

It asserted `["src/admin/service-reconciler.ts"]` is the only source file whose `INSERT INTO
user_roles/company_memberships` column list contains `managed_by`. Routing the reconciler's grant
into the choke point moves that SQL text to `grant-write.service.ts`, so the assertion's literal
file list had to become `["src/admin/grant-write.service.ts", "src/admin/service-reconciler.ts"]`
(the reconciler keeps its own `company_memberships` insert, untouched by this ticket).

**This is a source-text relocation, not a behavioural change, and the distinction is provable
rather than asserted:** parts 1–5 of that same file are RUNTIME probes against the live app —
*"assignRole never produces a managed_by-set row, even if the request tries to smuggle one"*,
*"inviteUser never produces one"*, *"the reconciler's own path is the one path that sets it"* —
and **all of them passed unmodified** across the refactor. Only the sweep that pins a file path
needed updating. There is no way to route the reconciler and leave this assertion untouched: it
names a file, and this ticket's purpose is to move the file.

**The invariant is now pinned tighter than before.** I added a companion sweep (part 6b): the
choke point merely has a `managed_by` *parameter*, and what matters is who fills it —
`insertGrantRow` writes `spec.managedBy ?? null`, so an omitting caller gets NULL. Part 6b asserts
**`service-reconciler.ts` is the only file in `src/` that supplies `managedBy:` at all.** A new
endpoint trying to forge a reconciler-owned grant must pass that field, and that is what reds.

## 4. The extended writer guard

`user-roles-writer-guard.test.ts` went from 5 tests to 14. The bar moved from *"calls the shared
helper"* to *"the statement lives in the choke point"* — a writer that calls the guard and then
runs its own INSERT is still a writer whose next author can forget the call.

**Three sweeps** (was one), all pure functions over `(path, source)` so their rejection paths can
be executed in-suite against synthetic files:
1. **MINT** — `INSERT INTO user_roles (... role_id ...)` (pre-existing).
2. **REVOKE** — `DELETE FROM user_roles` (**new**; never swept before — this is how a revoke path
   forgets the `managed_by IS NOT NULL` guard or the `user_id` pin).
3. **REPOINT** — `UPDATE user_roles SET ...` touching `role_id`/`scope_type`/`scope_id` (**new**;
   re-pointing an existing row at a different role is the same escalation as minting one and would
   sail past any INSERT-shaped sweep). Provenance-only updates are deliberately not flagged.

Plus a **fourth** guard the ticket did not ask for but the design implies: `trusted_internal` skips
every invariant, so `TRUSTED_INTERNAL_CALLERS` pins by name which files may request that origin.
Without it, a new writer could satisfy all three sweeps and then pick the origin that checks
nothing.

## 9. Blockers / follow-ups

**None blocking.** Recorded:

1. **P2-08 owns** the `ui`-origin endpoints, the subtree bound, sensitive routing, and
   endpoint-level proof of ceiling/allow-list/fence. The service is ready: pass `origin: "ui"`
   with `actorPerms: req.principal.perms` and `tenantId`.
2. **Import cycle, deliberate and documented.** `grant-write.service.ts` imports
   `assertRoleScopeAllowed` **from** `admin-identity.controller.ts` because
   `permission-arm-hazard-scan.test.ts` parses `const ROLE_SCOPE_CONSTRAINTS = {…}` out of that
   controller's **source text, by path** — moving the map would blind a machine check that exists
   to stop it drifting from `derived_roles.yaml`, and this ticket may not touch
   `scope-constrained-roles.*`. The cycle is safe (binding read at call time) and **not silently
   safe**: if it broke, the call would throw and `global-only-role-scope.test.ts`'s 400
   expectations would red. **Architect follow-up:** give the map its own module and repoint the
   scan's path pin, then this import straightens out.
3. **Ceiling scope semantics** are my implementation choice, not spelled out in §6.3.2: a
   permission held at `global` reaches everywhere; one held at `company:<tenant>` reaches that
   tenant's grants; an exact `(scopeType, scopeId)` match always counts; absent `perms` ⇒ holds
   nothing (fail-closed). Worth an architect confirmation before P2-08 makes it reachable.
4. **`ui`-origin revokes** currently run no invariants (create-only, matching P2-02's Cerbos DENY).
   P2-08 should decide whether a dept-head revoke needs its own subtree check.
