## 2. What 0095 seeds

`0095_iam_02e_baseline_roles.sql`, following 0091's idiom exactly: global rows
(`company_id IS NULL`), `gen_random_uuid()` ids, one `description` per role in the same
explanatory style, an `INSERT ... SELECT ... WHERE NOT EXISTS (... WHERE company_id IS NULL AND
name = ...)` guard for idempotency/re-runnability, and a closing `DO $$` block that asserts (a)
none of the six is still missing and (b) none is duplicated as a global row — added because the
ticket named this repo's two-strikes history with the "matches zero rows, reports success" trap
and asked for assertions, not assumptions, even though (see §3) no RLS is in play here.

Descriptions summarize each role's real Cerbos-enforced shape (superadmin wildcard bypass for
`platform_admin`, the `it_staff` synonym relationship for `it_admin`, the DR-1 approval-authority
carve-out for `manager`, etc.) rather than being placeholder text.

**What it does not do:** grant any role to any user, touch Cerbos policy, touch
`platform-ui/src/lib/rbac.ts`, or touch `permission-catalog.json`. Purely additive; zero
authorization decisions change for any existing user; a no-op on every live deployment today
(they all have `seed:agency` already run).

## 3. Does `roles` need the partial-index treatment? No — it already has it

This was the one place I expected to have to write DDL and didn't. `0073_dedupe_global_roles.sql`
(landed 2026-08-03, well before this ticket) already added
`CREATE UNIQUE INDEX IF NOT EXISTS roles_global_name_uniq ON roles (name) WHERE company_id IS
NULL` — the exact partial-unique-index fix the ticket asked me to check for and, if absent,
recommend. It is present. Read the file directly to confirm rather than trusting the name: 0073
also deduped the pre-existing live duplicates (10× `manager`, 3× `company_admin`, 2× `member`)
before adding the index, in the correct order (repoint `user_roles`/`role_permissions`/
`company_memberships.primary_role_id` first, delete losers, then index — cascade-safe).

Confirmed the index is load-bearing today, not decorative: `src/testing/fixtures.ts`'s
`createRole()` — the function `seed:agency` calls for exactly these six roles — already targets
`ON CONFLICT (name) WHERE company_id IS NULL DO NOTHING`, which only works because that index
exists. My new test's third case (§5) exercises this directly: calling `createRole()` for all six
baseline names *after* 0095 has already seeded them adopts the existing row every time, with zero
duplicates created.

**Recommendation: no further DDL needed.** `roles` does not need what `user_roles` needed 0092
for — it was already fixed, 18 migrations ago. My migration's `NOT EXISTS` guard is redundant
with the index for the same reason 0091's is (idiom consistency with 0026/0069/0091), not because
protection is missing.

## 4. `seed:agency`'s now-redundant role creation — recommend, do not implement

Once 0095 lands, `src/seed/agency.ts`'s six `createRole("manager")`-style calls for these baseline
roles are provably redundant: the row already exists, and the call becomes a guaranteed
`ON CONFLICT ... DO NOTHING` no-op followed by an adopt-by-`SELECT`. Verified this is genuinely
harmless, not just theoretically idempotent — my test's third case calls `createRole()` for all
six names against an already-0095-seeded database and asserts the returned id matches the
pre-existing row's id every time (no new row minted).

**Recommendation: leave `src/seed/agency.ts` unchanged for now; revisit as a small follow-up, not
in this ticket.** Two reasons for not touching it despite having "only if safe" latitude:

1. **Blast radius is wider than it looks.** `seedAgency()` is called directly (not just via the
   `npm run seed:agency` CLI entry) from `src/seed/agency.db.test.ts` and
   `src/agency-first-deploy.e2e.test.ts`, and transitively wires into `seed/departments.ts`. Every
   call path I could find runs `migrate()` first (either explicitly, as the CLI entry point does,
   or implicitly via `initTestDb()`), so converting the six `createRole()` calls to plain
   `SELECT`-only lookups would likely be safe — but "likely" after a partial audit is not the bar
   this repo holds migrations to, and this file is shared demo-data infrastructure several
   concurrent IAM tickets may still be touching today (2026-08-10, four other agents in this same
   checkout per the ticket brief).
2. **The redundancy costs nothing.** Unlike the `user_roles` duplicate-grant defect (0073/0092),
   which was actively corrupting data on every seed run, this redundancy is inert: `createRole()`
   already treats "role exists" and "role newly created" identically to its caller (it always
   returns the row's id via a follow-up `SELECT`), so there is no behavioral difference between
   "created by migration, adopted by seed" and "created by seed" from any caller's point of view.
   There is no live defect here to justify the risk of editing shared fixture code.

If this is picked up later: the safe shape is to replace the six `createRole(...)` calls with a
small helper that does `SELECT id FROM roles WHERE company_id IS NULL AND name = $1` and throws a
clear error if the migration hasn't run (rather than silently creating the role client-side),
which would also serve as a live tripwire if 0095 were ever reverted. Not implemented here.

## Rollout notes

Purely additive, zero-downtime, no backfill, no deploy-order constraint, no Cerbos restart (no
policy file touched). Safe to apply to a live database at any time — every live deployment
already has these six roles via `seed:agency`, so `0095` is a guaranteed no-op there (verified by
the `NOT EXISTS` guard's own logic, and by 0073's index making a duplicate structurally
impossible even if the guard were somehow bypassed). The value is entirely for **environments that
have not yet run `seed:agency`**: a fresh deployment, a disaster-recovery restore, or a new site
in the multi-site topology now comes up with all six baseline roles grantable immediately after
`migrate()`, with no manual step required.
