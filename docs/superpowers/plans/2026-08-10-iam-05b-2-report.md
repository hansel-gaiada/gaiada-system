## The map, summarized

All 34 capabilities from `rbac.ts`'s `CAPABILITIES` tuple are mapped, each to a named permission
set (catalog keys from `platform-nest/src/rbac/permission-catalog.json`) plus a declared
`"all"`/`"any"` semantics. 32 of 34 are `"all"`; 2 are `"any"` (below). Set sizes range from 1
(most reporting/appraisal/check-in capabilities, `org.edit`, `search.ledger.admin`,
`approvals.retry`) up to 15 (`search.manage`, the largest, matching it being the largest
call-site consumer at 42 sites) and 10 (`company.manage`).

Every entry's provenance is one of three tiers, stated explicitly in its comment:
1. **Direct 1:1 citation** — rbac.ts's own comment names the exact Cerbos action(s) and/or the
   catalog's description text is near-verbatim the capability's description. Most of the 34,
   and essentially all of the TR-25 reports/checkin/appraisal block (9 of the 12 grant-only
   capabilities) — despite being grant-only, these were the CLEANEST to pin, contrary to the
   ticket's expectation that grant-only entries would be the murkiest.
2. **Derived from a named tier comparison** — `pm.manage`/`pm.contribute` (Gap-2's "leads/admins
   tier" vs "any member's tier" split), `hr.view`/`hr.manage` (TR-25's reader/acting split),
   `search.view`/`search.manage`/elevated search capabilities (the module_staff/module_manager
   baseline-vs-elevated split).
3. **Judgement call, explicitly flagged** — `admin.access`, `rollups.view` (partially — the
   recompute half), `knowledge.review`. See below.

## The two `any`-semantics entries

- **`approvals.decide`** — `["core.automation_approval.decide", "agency.approval.approve",
  "core.pipeline_gate.decide"]`. Rationale: DR-2b's `agency_approver` holds exactly 1 of these 3
  Cerbos actions (`agency_approval:approve`, its entire Cerbos reach) yet must retain the
  capability — under strict `"all"` semantics the derivation would strip it, reverting DR-2b.
  Design doc §3.2 gives this exact set as its own worked example, so this entry is not a novel
  derivation, it's a direct transcription.
- **`company.manage`** — `["core.integration_connection.{create,read,update,delete}",
  "core.company.update", "billing.invoice.{create,read,update,delete}",
  "core.automation_approval.retry"]`. Rationale: the Gap-3 safe-direction judgment — `manager`
  holds only the `integration_connection` tier of this multi-Cerbos-kind UI capability (Billing,
  company-edit, automation-console-retry, seat-mapping all share this one name), and the owner
  chose to show the surface and let the server 403 the parts `manager` doesn't hold, rather than
  hide it. Under strict `"all"` the derivation would strip `company.manage` from `manager`,
  reverting that judgment — design doc §3.1's own worked counter-example is this exact case.

**No third `"any"` candidate was found.** I went through every capability checking whether its
backing policies disagree with each other about the role list (the actual test for needing
`"any"`, per the FIX-2 definition) and found none — every other multi-permission set's backing
policies carry the SAME role list under the SAME condition (explicitly confirmed for
`pipeline.write` — three policies, identical trio; `pipeline.manage` — two policies, identical
trio). `admin.access` was the closest call (it's also a multi-Cerbos-kind capability like
`company.manage`), but I found no citation proving `company_admin` holds a strict subset of its
ten permissions the way `manager` provably does for `company.manage` — so I left it `"all"` and
flagged the underlying set as unverified instead of guessing at `"any"`. If IAM-05b-3's bundles
show `admin.access` is actually partial, that becomes a genuine third `"any"` finding for the
owner at that point, not something to preempt here without evidence.

## Mismatches found against `ROLE_CAPS` (drift findings for IAM-05b-3 to adjudicate)

These are NOT new discoveries — both are already named in the design doc (§3.3, §7) as expected
first-run reds once the parity test exists. I re-derived them independently while authoring the
map and they land exactly where the design doc predicted, which is a good sign the map's
`company.manage` set is right:

1. **`it_admin` × `company.manage`** (design doc's drift finding #7, 1 live holder). Under `"any"`
   semantics, `it_admin` holds it in `ROLE_CAPS` but no policy grants `it_admin` any member of
   this map's 10-permission set → the `any` check will come back **false** → an over-claim. This
   is an owner decision (remove vs. register), not something this ticket touches.
2. **`company_admin` × `appraisal.read`** (design doc's finding #6, 9 live holders). My derived
   set for `appraisal.read` is the singleton `["reports.appraisal.read"]`. `company_admin` holds
   `appraisal.read` in `ROLE_CAPS`, but per the design doc's own finding, no Cerbos rule grants
   `company_admin` that action at all → under `"all"` (trivially, for a singleton) the check will
   come back **false** → an over-claim needing owner adjudication.

No other mismatch was apparent from static comment-reading alone — everything else I could check
by hand (pipeline.write's member/viewer split, pipeline.manage/webdev.provision's team_lead
exclusion, it.manage's team_lead exclusion, search_staff/search_manager's tier split, DR-1's
manager exclusion from approvals.decide, DR-2b's agency_approver inclusion) reproduced `ROLE_CAPS`
correctly under this map's sets and semantics. The genuinely unresolved ones (admin.access,
rollups.view's recompute half, knowledge.review, hr.view's hr_staff question) can't be checked by
hand at all — they need IAM-05b-3's real bundle data, which is exactly the point of building that
test next.

## Which of the 12 grant-only capabilities were hardest to pin

Design doc §1.4's 12 grant-only capabilities: `reports.person.view`, `reports.project.view`,
`reports.department.view`, `reports.company.view`, `reports.period.seal`, `reports.facts.admin`,
`reports.ops.poll`, `checkin.read`, `checkin.excuse`, `knowledge.review`, `search.view`,
`search.ledger.admin`.

**Contrary to the ticket's expectation, 9 of these 12 (everything in the TR-25 reports/checkin/
appraisal-adjacent block, plus `search.view` and `search.ledger.admin`) were the EASIEST in the
whole file** — each has an explicit Cerbos action name in rbac.ts's own comment, several are
literal 1:1 citations, and `search.ledger.admin`'s catalog key is textually identical to the
capability name. Being unconsumed by any call site didn't correlate with being hard to derive;
it correlated with rbac.ts's authors having had MORE room to write a precise comment, since there
was no live call site putting pressure on the wording.

**The one genuinely hard grant-only capability was `knowledge.review`** — zero backing-policy
citation, had to be derived from the catalog's own description text matching the capability's
description, which is weaker evidence than every other entry in the file gets. If this program
wants a second pass on citation quality before IAM-07a freezes the contract, `knowledge.review` is
where I'd start.
