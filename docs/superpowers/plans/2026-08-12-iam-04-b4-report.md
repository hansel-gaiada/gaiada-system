## 1. The standing rule and the hazard this ticket was warned about

**ZERO DECISIONS CHANGED.** Every rule added below is a permission-arm mirror in its **own** new
rule, at the **same** `variables.inTenant && variables.notLow` condition as the `company_admin`/
`manager`/`member` role-arm rule it mirrors — never mixed into an existing rule (Pattern A), and
never shaped after `group_executive`'s own `variables.notLow`-only rule (the TRAP4 fix). Mirroring
`group_executive`'s rule shape would have handed a company-scoped permission holder cross-tenant
reach the role arm never gave them — the exact defect this ticket's brief called out by name.
`group_executive`'s own rule is therefore role-arm-only on all 5 kinds, explicitly, everywhere below.

## 3. Why no exclusion clause was needed (unlike `pm_task`'s `team_lead` mitigation)

Re-ran `permission-arm-hazard-scan.test.ts` before and after (120 tests, green both times — see §6).
Pattern A found **zero** same-rule mixing on any of these 5 kinds, both before and after TRAP4: every
rule on these files names either a single scope-only role tier (`company_admin`/`manager`/`member`,
all SAFE) or `group_executive`/`platform_admin`/`module_manager` **alone** in their own rule.
Pattern B found no self-scoped condition anywhere on these 5 kinds. So the mitigation these kinds
needed was never "add an exclusion" (the `team_lead`/`pm_task` shape) — it was "mirror only the
SAFE-role rule, and structurally cannot mirror `group_executive`'s rule by picking a different rule
to copy in the first place," which is what §2 above did.

## 4. Live probe (the parity suite cannot see this bug class — established by IAM-TRAP4)

`gen:role-bundles`'s own abstraction treats every rule `condition` as satisfied and records only
which role NAME appears against which action — it cannot distinguish "the mirror respects
`inTenant`" from "the mirror ignores it," so a green bundle diff is not evidence for tenant
isolation. Probed `POST http://localhost:3592/api/check/resources` against a freshly-restarted
`gaiada-test-cerbos` (`StartedAt: 2026-08-12T09:49:06Z`, confirmed post-dating every policy edit in
this ticket) instead, exactly reproducing `principalPayload()`/`resourcePayload()`'s real shape from
`src/rbac/cerbos.ts`. All 5 kinds' mirrored actions checked in each scenario (not just one action);
output verbatim below.

## 5. Bundle regeneration — before/after

`npm run gen:role-bundles` → `wrote ... — 22 roles, 1023 total (role, permission) pairs.` **Before
and after are byte-identical** — confirmed both via `git diff --stat` (empty) and via the tool's own
count line (22/1023 unchanged). Expected, not a miss: the generator bundles role **names**
(`company_admin`, `manager`, `group_executive`, …) against actions their rules name; `perm_*` roles
are a compat shim the generator does not treat as a role a human/service account can hold, so adding
14 of them cannot move the bundle's own numbers — the same conclusion IAM-TRAP4's own report reached
for the identical reason.
