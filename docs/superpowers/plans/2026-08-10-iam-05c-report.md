## 1. The central design constraint, and how this ticket resolves it

A bulk "everything you can do" response can only be honestly built from **scope-only**
resolution (`can.scopeOnly()`, IAM-05a) — condition-dependent grants (`ownerId`,
`subjectUserId`, `teamId`, assurance floors) depend on a specific resource and cannot be
answered for a whole scope in advance. Treating the result as "may do X to any resource"
reproduces the IAM-04b regression (permission path granting what the role path denies) at the
UI layer.

**Decisions made to keep that boundary loud rather than implicit** (detail in §3):

1. The main field is named `scopeLevelPermissions`, not `permissions` or
   `effectivePermissions` — the name states what it is, not what a consumer might wish it were.
2. The response carries a fixed `caveat` string, in the payload itself (not just this doc),
   spelling out the exact hazard and pointing at `can()` for the authoritative per-resource
   answer.
3. The 15 relationship-class catalog keys are never asked about (never appear, cannot appear)
   and are additionally **listed explicitly** in the response as
   `excludedRelationshipClass` — a constant, catalog-derived list, not silently dropped.
4. Any role the principal holds that is a known Cerbos wildcard-bypass role (IAM-04c:
   `platform_admin`, `group_executive`) is surfaced in its own `wildcardBypassRoles` field,
   with the caveat naming the specific risk for those roles (bundle-snapshot drift, not a
   currently-measured gap — see §4).

## 2. Endpoint shape

Two GET routes, one controller (`AuthzPermissionsController`, `@Controller("api")` +
`AuthGuard`, same family as `AuthzCheckController`'s `POST :tenantId/authz/check`):

- `GET /api/:tenantId/authz/permissions` — company scope = `tenantId`. 403 (not 404) if the
  caller has no membership in that company and holds no global-admin bypass — mirrors
  `ModuleCatalogController.enabled()`'s existing pattern exactly.
- `GET /api/authz/permissions` — global scope. Always answerable for any authenticated
  principal (their own global-scope grants only); this is what a `group_executive`-shaped
  principal with zero company memberships uses.

Response body:

```jsonc
{
  "scopeType": "company",              // or "global"
  "scopeId": "<tenantId>",              // null for the global route
  "scopeLevelPermissions": ["core.task.read", "pm.task.create", "..."],   // sorted
  "excludedRelationshipClass": ["assistant.agent_run.read", "..."],       // sorted, constant
  "wildcardBypassRoles": ["platform_admin"],                             // sorted, may be []
  "caveat": "<fixed string, see controller source>"
}
```

The `caveat` string ships verbatim in every response (not just this doc), so a consumer that
never reads the docs still sees the boundary stated in the payload itself:

> scopeLevelPermissions answers 'does this principal hold this permission SOMEWHERE in this
> scope', resolved from the pre-computed role→permission bundle with NO knowledge of any
> resource-level condition (ownerId, subjectUserId, teamId, assurance floors). It can
> OVER-report for one specific resource whose real Cerbos rule is condition-dependent, and
> (only for roles listed in wildcardBypassRoles) it can UNDER-report if the bundle has drifted
> behind a live Cerbos policy change. Never treat this list as 'may do X to any resource' —
> gating access to ONE specific resource, or getting a fully authoritative answer for a
> bypass-holding role, must go through can(principal, key, resource) instead.

## 3. Implementation

`platform-nest/src/core/authz-permissions.controller.ts` — one new file:

- `computeEffectivePermissions(principal, scope)` — the pure computation. Iterates the
  catalog's 215 `class: "grantable"` keys (never the 15 `relationship` keys — filtered out at
  module load, a constant computed once, not per request) and calls `can.scopeOnly()` (IAM-05a,
  unmodified) for each. This is the ONLY authorization primitive the file uses — no new
  authz mechanism, no re-implementation of `principalHasPermission`'s scope cascade.
- `EFFECTIVE_PERMISSIONS_CAVEAT` — the fixed string above, exported so the test can assert the
  response actually carries it (not just a similar-sounding string).
- `WILDCARD_BYPASS_ROLES = ["platform_admin", "group_executive"]` — the two role names IAM-04c's
  bypass ruling and `can.ts`'s own header both cite as carrying Cerbos's non-delegatable `*`
  rule. Not derived from anything queryable (Cerbos policies carry no "this role bypasses"
  flag) — this is the same institutional fact already recorded elsewhere, not a new claim.
- `etagFor()` — SHA-256 over `{userId, sessionVersion, scopeType, scopeId, scopeLevelPermissions,
  wildcardBypassRoles}`. `sessionVersion` is part of the hash **by construction**, not as a
  bolted-on invalidation step: the cache key **is** the invalidation signal. `assemblePrincipal()`
  (untouched by this ticket) already re-reads `session_version` from the DB on every request, so
  a D11 revocation changes the very next request's `principal.sessionVersion`, which changes the
  hash, which makes any previously issued ETag stop matching — no separate purge mechanism exists
  or is needed.
- `respondCacheable()` — sets `Cache-Control: private, max-age=30, must-revalidate` + `ETag`;
  returns a bodyless response with `reply.status(304)` on a matching `If-None-Match`, otherwise
  returns the body for Nest to serialize normally (`@Res({ passthrough: true })`, the same
  pattern `webdev.controller.ts`'s `provision()` already uses in this codebase).
- `AuthzPermissionsController` — two routes:
  - `GET /api/:tenantId/authz/permissions` (company scope). Tenancy gate copies
    `ModuleCatalogController.enabled()`'s existing rule exactly: 403 (never 404) unless the
    caller is a member of `tenantId` or holds a global `platform_admin` grant.
  - `GET /api/authz/permissions` (global scope, no tenancy gate — "global" names no company).
    This is what a principal with zero company memberships (e.g. the live
    `group_executive`-shaped seed, memory `org-structure-contract`) uses to learn its own
    cross-company reach without first picking a company.

Registered in `platform-nest/src/app.module.ts` (import + controllers array), immediately after
`AuthzCheckController` — same file family, same `@Controller("api")` prefix, no route collision
(verified: no other controller declares `authz/permissions` or `:tenantId/authz/permissions`).

## 4. Superadmin / wildcard bypass — decision, and what was actually verified live

**Decision:** the endpoint answers purely from `principal.perms` (no Cerbos round trip per
key — that is the entire point of a bulk answer). For the two bypass roles, this is
**verified live, not just claimed from the bundle's known shape**:

- `platform_admin` holds all **215/215** grantable keys in its `role_permissions` bundle
  (migration 0094, `role-permission-bundles.json`). The live test
  (`scopeLevelPermissions vs can() — live parity sweep`) builds a principal with that exact
  bundle as `perms`, computes `scopeLevelPermissions` (215 keys), and then calls the real
  `can()` — live Cerbos — for **every one of the 215** with generic resource attributes.
  **Zero mismatches.** A second live test confirms `can()` also denies platform_admin on all 15
  relationship-class keys (no wildcard rule exists on those kinds — the exemption survives the
  bypass, as IAM-04c intended).
- `group_executive` holds **118/215**. Its `wildcardBypassRoles` flag is asserted, and a
  12-key spot sample of its bundle is confirmed live-ALLOW via `can()` (not a full 215-key
  sweep — bounded runtime; the exhaustive guarantee for every role already lives in IAM-02b's
  parity suite, which this endpoint's computation transitively relies on via
  `can.scopeOnly()` → `principal.perms`).

**What is NOT solved, stated rather than hidden:** this is a snapshot answer. If a future
Cerbos policy edit grants `platform_admin`/`group_executive` a new kind's wildcard before
`role_permissions` is regenerated (`npm run gen:role-bundles`) and re-migrated, `can()` sees it
immediately (always live) and this endpoint would not, until the next regen. Every response for
a principal holding either bypass role names it in `wildcardBypassRoles`, and the `caveat` text
calls out exactly this risk, so a consumer is told "this may be a floor, not a ceiling" rather
than left to assume completeness. No `*` permission was invented anywhere to work around this —
consistent with IAM-04c's ruling that the bypass never becomes a delegatable permission.

## 5. The 15 relationship permissions

Never asked about (the handler only iterates `class: "grantable"` catalog keys) and cannot leak
through `principal.perms` regardless (0093's DB trigger + `assemblePrincipal()`'s own filter,
pre-existing). Verified with an adversarial probe: a synthetic principal whose `perms` was
manually seeded with a relationship-class key (simulating a hypothetical upstream regression)
still never surfaces it in `scopeLevelPermissions` — the handler does its own filtering rather
than trusting the upstream guarantee alone (same defense-in-depth style as `can.ts`/0093). The
15 keys are additionally listed by name in every response's `excludedRelationshipClass`
(constant, catalog-derived, independent of principal/scope) rather than silently omitted.

## 6. Caching + revocation

- `Cache-Control: private, max-age=30, must-revalidate` — short-lived, never shared/CDN-cached.
- `ETag` embeds `sessionVersion`. Tested: (a) an unchanged principal gets a stable ETag across
  calls; (b) a matching `If-None-Match` short-circuits to a bodyless 304; (c) a permission
  change on an otherwise-identical principal does NOT 304 (fresh body served); (d) a
  `sessionVersion` bump alone (identical roles/perms) changes the ETag; (e) presenting the
  OLD ETag after a `sessionVersion` bump does NOT 304 — the caller gets a fresh 200, never a
  cached answer computed under the revoked session. (e) is the direct test of "D11 revocation
  is authoritative — a revoked principal must not be served a stale answer": `sessionVersion`
  is refreshed from the DB by `assemblePrincipal()` (untouched here) on every request, so this
  endpoint automatically sees the post-revocation value on the very next call; the ETag design
  makes sure a cache built on the pre-revocation value cannot masquerade as still valid.

## 9. Blockers / follow-ups (not this ticket's remit)

- **`platform-ui/` is untouched, per the ticket's constraint.** The UI does not yet consume this
  endpoint. IAM-05b's ruling (`2026-08-10-iam-05b-design.md` §3.4) already records how this
  payload is meant to plug into `can()`'s eventual custom-role-aware form
  (`can(me, cap, company) = semanticsEval(effectivePermissions(me, company), CAPABILITY_MAP[cap])`)
  — that wiring is out of scope here and flagged there, not assumed done.
- **Bundle-staleness risk for the two wildcard-bypass roles is disclosed, not eliminated** (§4).
  Closing it fully would require either a live Cerbos call per request (defeats the "no N round
  trips" point of a bulk endpoint) or a CI gate that fails whenever a policy edit outpaces a
  bundle regen — the latter is already IAM-07b's job (the pinned pairwise-link chain,
  `2026-08-10-iam-05b-design.md` §4), not this ticket's.
- **No batching across scopes in one call.** A caller needing both company- and global-scope
  answers makes two requests. Given each is a synchronous, no-round-trip computation over an
  already-resolved `perms` array, the cost of two calls is two JSON round trips, not two Cerbos
  round trips — judged not worth a combined-response shape for this ticket.
- **Verification gap that was found and closed in this session:** the first pass proved the
  304/`Cache-Control`/`ETag` logic only at the controller-method level (mocked `FastifyReply`),
  leaving open whether `@Res({ passthrough: true })` + `reply.status(304)` really produces a
  bodyless 304 through the actual Nest+Fastify pipeline once wired into `app.module.ts`. Closed
  by adding a Tier 4 (`buildApp()` + `app.inject()`, same idiom as `tasks-mine.test.ts` /
  `webdev-change-requests.controller.test.ts`): a real `If-None-Match` round trip over the wire
  returns a genuine `304` with an empty body, and a real cross-tenant request returns a genuine
  `403` (never `404`) — both against the live test DB + Cerbos, not mocked.
