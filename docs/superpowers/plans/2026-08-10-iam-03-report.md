## 1. The `perms` shape, and why

```ts
export interface PermissionGrant {
  key: string;                                                          // permissions.key, e.g. "core.task.update"
  scopeType: "global" | "company" | "team" | "project" | "record";
  scopeId: string | null;
}

export interface Principal {
  userId: string | null;
  assurance: Assurance;
  companies: string[];
  roles: RoleGrant[];        // UNCHANGED — same query, same shape, same every-call-site behaviour
  perms?: PermissionGrant[]; // NEW — see §1.2 on why this is optional, not required
  sessionVersion: number;
}
```

`PermissionGrant` is deliberately isomorphic to the pre-existing `RoleGrant` — same three fields,
same scope union, same "the scope is whatever the underlying grant row says" semantics. That was a
design choice, not a shortcut: it means a `perms` entry is the row-level expansion of a `roles`
entry through `role_permissions` (IAM-02a, migration `0094`), never re-derived at a different
scope than the grant it came from. Concretely: a `manager` role held `('company', companyA)`
yields every one of that role's ~109 permissions tagged `('company', companyA)`, not `'global'`
and not some other company. This is verified directly in
`principal-permissions.db.test.ts`'s "two roles at DIFFERENT scopes" test, which grants `member`
at company A and `manager` at company B on the SAME user and asserts a member-only key
(`hr.case.create`) comes back tagged company A while a manager-only key
(`core.pipeline_stage.update`) comes back tagged company B — proving scope is carried per-grant,
not merged or averaged.

**`org_unit` is deliberately absent from the scope union.** That scope doesn't exist yet (IAM-08,
Phase 2). Adding it later is a pure union-widening change to `PermissionGrant`/`RoleGrant`'s
`scopeType` — nothing about today's shape, query, or the `principalHasPermission` helper forecloses
it or needs restructuring when it lands.

### 1.1 The scope-lookup helper

```ts
export function principalHasPermission(
  p: Principal, key: string, scopeType: PermissionGrant["scopeType"], scopeId: string | null,
): boolean
```

The ticket asked for a shape a consumer can query "does this principal hold permission X in scope
Y" against "without re-deriving cascade rules." A flat grant array alone still leaves every
consumer to reimplement the one cascade rule that's actually settled today — a `global`-scope
grant satisfies every scope, everything else must match exactly — so this one small pure function
is exported alongside the data. It deliberately does **not** attempt narrower cascades (e.g.
"does a company grant also cover that company's teams/projects"): that cascade lives in Cerbos's
own derived-role policy conditions (D16 PlanResources) today, and is left there on purpose. This
is not `can()` — IAM-05a owns that name and that job (wrapping `check()`, incorporating the
IAM-04c bypass ruling, etc.) — this is scope-matching over already-resolved data, nothing more.

### 1.2 Why `perms` is `perms?:` (optional), not `perms:` (required)

The first attempt made it required, matching `roles`'s own non-optional declaration. `tsc --noEmit`
immediately surfaced ~20 pre-existing test files (`src/modules/reports/*.test.ts`,
`src/modules/search/*.test.ts`, `src/rbac/cerbos*.test.ts`) that hand-construct `Principal` object
literals for mocking and don't know about the new field — every one became a type error. Those
files belong to other tickets/other concurrently-running agents in this checkout, not to IAM-03,
and the ticket's own constraint list only grants me `principal.ts` and new files under
`src/rbac/`. Editing 20 files I don't own, mid-concurrent-session, to satisfy a type checker is the
opposite of "strictly additive." Making `perms` optional makes the true "additions are
additive-only, zero other files touched" claim hold literally: `tsc --noEmit` is clean except for
one pre-existing, unrelated `js-yaml` type-declaration warning in a file I did not write
(`role-permission-parity.db.test.ts`, owned by IAM-02a/02b, confirmed present before this session's
changes). `assemblePrincipal()` — the one real producer — always populates `perms`;
`principalHasPermission()` defends with `p.perms ?? []` for the synthetic literals that don't,
and has its own test for that exact case.

## 2. How relationship-class exclusion is enforced (and tested)

Two independent layers, both exercised in `principal-permissions.db.test.ts`:

1. **The DB trigger (0093, pre-existing).** `role_permissions_reject_relationship` fires on
   INSERT/UPDATE and refuses to let any of the 15 `class='relationship'` permissions become a row
   in `role_permissions` in the first place. Test: "the DB trigger blocks a direct attempt to
   grant a relationship-class permission" — inserts `platform_admin` + `core.mcp_tool.call`
   directly and asserts it throws.
2. **The resolution query's own filter (new, this ticket).** `assemblePrincipal`'s perms query
   carries `AND p.class = 'grantable'`. This is defense-in-depth, not decoration: the test
   "defense-in-depth: with the trigger DISABLED, the resolution query's OWN class='grantable'
   filter still excludes a relationship permission smuggled into role_permissions" literally runs
   `ALTER TABLE role_permissions DISABLE TRIGGER role_permissions_reject_relationship`, inserts the
   forbidden row directly (and confirms via a raw SELECT that the smuggled row is really there —
   so the next assertion isn't vacuous), calls `assemblePrincipal()` for `platform_admin`, and
   asserts `core.mcp_tool.call` is absent from `perms` while the other 215 grantable keys are
   unaffected. Then it deletes the smuggled row and re-enables the trigger in a `finally` so the
   shared test database is left clean for other suites (several other agents are on this same
   Postgres instance right now).

A third test ("no built-in role's bundle ever contains a relationship-class key") sweeps all 8
seeded personas (platform_admin, group_executive, company_admin, manager, member, viewer,
agency_approver, it_admin) and asserts none of their resolved `perms` intersects the 15
relationship keys loaded live from `permission-catalog.json` (not hardcoded, so a future catalog
edit can't silently stop being checked).

## 3. IAM-03b — the benchmark (`principal-perf.db.test.ts`)

### Method

Seeded a realistic table population approximating the documented live distribution (§6 of the
ticket doc): 18 `member`, 11 `manager`, 9 `company_admin`, 9 `client`, 1 each of
`platform_admin`/`group_executive`/`it_admin`/`agency_approver` — ~51 users, against the full
925-row `role_permissions` / 230-row `permissions` catalog, not a near-empty table. Measured three
things, all against the real `gaiada-test-pg` container (no mocks):

1. **EXPLAIN ANALYZE** of the new perms query alone.
2. **Marginal query cost** — the pre-existing roles-only query vs. the new roles+perms query,
   timed on the SAME already-checked-out connection (matching how `assemblePrincipal` itself now
   reuses one connection for both), 300 iterations per persona after 20 warmup iterations.
3. **Full end-to-end `assemblePrincipal()`** — the real function, unmodified, 300 iterations per
   persona after 20 warmup iterations.

"Before" is not a second copy of the module — this repo has no VCS in the harness's working
directory, and stashing mid-session while 3 other agents share the checkout was judged too risky.
Instead the pre-existing roles-only SQL is reproduced as a literal string in the benchmark file
(clearly labelled, with a comment explaining why) and timed directly against the same live schema,
which answers the actual question ("what did this ticket's query add to the hot path?") without
requiring two source trees.

### Results (real numbers, this session, `gaiada-test-pg` over loopback TCP)

**EXPLAIN ANALYZE** (company_admin, 199-permission bundle):

```
Unique (actual rows=199 loops=1)
  ->  Sort (actual rows=199 loops=1)
        ->  Nested Loop (actual rows=199 loops=1)
              ->  Hash Join (actual rows=925 loops=1)
                    Hash Cond: (rp.permission_id = p.id)
                    ->  Seq Scan on role_permissions rp (actual rows=925 loops=1)
                    ->  Hash (actual rows=215 loops=1)
                          ->  Seq Scan on permissions p (actual rows=215 loops=1)
                                Filter: (class = 'grantable'::text)
                                Rows Removed by Filter: 15
              ->  Index Only Scan using user_roles_user_id_role_id_scope_type_scope_id_key on user_roles ur
                    (actual rows=0 loops=925) Heap Fetches: 199
Planning Time: ~2-3 ms
Execution Time: ~1.0-1.8 ms
```

**Marginal query cost** (mean, 300 iterations, one reused connection):

| company_admin (199 perms) | 0.72-0.80 ms | 1.48-1.93 ms | ~0.68-1.21 ms |
| platform_admin (215 perms) | 0.70-0.72 ms | 1.66-2.01 ms | ~0.94-1.31 ms |

**Full end-to-end `assemblePrincipal()`** (mean, 300 iterations — includes the user lookup, the

| Persona | mean | p50 | p95 | max |
|---|---|---|---|---|
| member | 5.7-7.9 ms | 5.4-8.0 ms | 8.3-10.6 ms | 11.9-16.8 ms |
| company_admin | 4.5-7.5 ms | 4.3-7.4 ms | 6.4-9.8 ms | 10.4-20.2 ms |
| platform_admin | 4.1-6.6 ms | 3.7-6.7 ms | 6.9-9.2 ms | 10.3-19.1 ms |

(Ranges reflect two separate full runs in this session — machine noise from other concurrent

215 permissions, is not slower than member's 74 in either run.)

### Interpretation

The perms expansion adds roughly **1-1.3 ms mean** to a request that already costs **4-8 ms mean**
end-to-end — the marginal cost is a real, measured, positive number, but it is a fraction of the
pre-existing cost of the OTHER two queries this function already ran (the user lookup and the
RLS-transactional companies UNION), not a new bottleneck. The EXPLAIN plan confirms *why*:
Postgres sequentially scans `role_permissions` (925 rows) and `permissions` (230 rows) once, hashes
them, and nested-loops into `user_roles` per-user via an existing index — both reference tables
are small enough that a full scan of each is cheaper than any index-driven alternative the planner
could pick, and it correctly picks the seq-scan plan over an index-driven one.

### Index decision: NO new index (0098 not used)

The EXPLAIN plan already uses an existing index for the one large-cardinality lookup that matters
(`user_roles` filtered by `user_id`, via the pre-existing
`(user_id, role_id, scope_type, scope_id)` unique-constraint index) and correctly chooses NOT to
use an index for `role_permissions`/`permissions`, because both are small reference tables (925
and 230 rows respectively) where a full sequential scan is the genuinely cheaper plan — verified by
reading the actual `EXPLAIN ANALYZE` output, not assumed. Forcing an index scan here would very
likely make this query *slower*, not faster, at this table size. **This is a measurement-backed
"no," not a default "no":** if the permission catalog or the per-role bundle sizes grow by an
order of magnitude in a later phase, this conclusion should be re-measured, not assumed to still
hold — flagged as a note for whoever picks up catalog growth later, not an action item now.

### Cache decision: NO cache (with the measurement that justifies it)

**Decision: do not add a cache.** Justification:

1. **The absolute marginal cost is small** (~1-1.3 ms mean) relative to the request's other
   existing DB round trips (~4-8 ms mean total) and relative to any real HTTP request's total
   latency budget. There is no measured problem for a cache to solve.
2. **At the measured/live scale (≈50 users, 925 `role_permissions` rows, 230 `permissions` rows),
   a cache buys negligible upside** — the query is already close to the floor a network round trip
   to Postgres imposes regardless of what the query computes.
3. **A cache is a security liability, not a free perf win, per the ticket's own framing.** D11
   requires a revoked or downgraded user to be cut off immediately. This codebase already bumps
   `session_version` on every role-grant mutation path that matters —
   `admin-identity.controller.ts`, `identity.controller.ts`, `service-reconciler.ts` — and several
   existing tests already describe this explicitly as "(cached-principal invalidation)"
   (`service-reconciler-adversarial.test.ts`'s V7, `org14-preflight-adversarial.test.ts`'s T7),
   even though no principal cache exists yet anywhere in the codebase today. That is a real,
   already-correct invalidation contract sitting unused — a future cache keyed on
   `(userId, sessionVersion)` would be SAFE to add later specifically because that contract already
   exists, but adding one now, with no measured problem to solve, would be exactly the "machinery
   to look thorough" the ticket says not to build.
4. **A known limitation to flag for that future ticket, not fixed here:** `session_version` is
   bumped on USER-level grant changes (a role assigned/revoked from a specific user), but NOT on
   ROLE-level bundle changes (e.g., a future migration that adds a permission to the `manager`
   bundle). That class of change ships via a migration + redeploy today, mirroring the existing
   "a Cerbos policy edit needs a restart" discipline this whole program already operates under —
   consistent, not a new gap, but worth naming explicitly for whoever eventually builds the cache.

If a future ticket needs to revisit this (e.g., after IAM-04/05 add real per-request `can()` calls
that fan out to many permission checks, or after the user count grows by orders of magnitude), the
benchmark file (`principal-perf.db.test.ts`) is there to re-run and compare against these numbers
rather than re-deriving the method from scratch.

## 7. Blockers / follow-ups (not this ticket's remit)

- **IAM-04a** is the next real consumer: passing `perms` as a Cerbos principal attribute and adding
  permission-matching derived roles beside the role-name ones. `perms`'s shape (flat grants,
  `PermissionGrant["scopeType"]` union) is JSON-serializable as-is, so no transform is anticipated
  to be needed, but that's IAM-04a's call to make, not asserted here.
- **IAM-05a's `can()`** is the intended second consumer of `principalHasPermission()`'s scope-match
  primitive, once IAM-04c has ruled on the superadmin/owner bypass (a `platform_admin` grant
  reaching "every permission" today is a data fact of the seeded bundle, not yet a designed `*`
  semantic at the permission layer — that ruling is explicitly out of this ticket's scope).
  `principalHasPermission` is NOT `can()` and must not be mistaken for it — it never talks to
  Cerbos and knows nothing about the D9/D14 write-approval semantics `can()` will need to respect.
- **Cache re-evaluation trigger:** if IAM-04/05 make permission checks fan out to many per-request
  calls (rather than one `assemblePrincipal()` per request as today), or if user/role-bundle scale
  grows by an order of magnitude, re-run `principal-perf.db.test.ts` before deciding a cache is
  warranted — don't assume today's "no" still holds without re-measuring.
- **`perms?:` optionality** is a deliberate, temporary widening to avoid touching ~20 files this
  ticket doesn't own. Whoever next needs `perms` to be reliably present on every `Principal` value
  (rather than just on every value `assemblePrincipal()` itself produces) should tighten it to
  required in the same change that updates those test files' literals — flagged so it isn't
  mistaken for a permanent design decision.
