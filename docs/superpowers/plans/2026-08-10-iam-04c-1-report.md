## 1. The new test: `iam-215-boundary-pin.test.ts`

66 tests, static only (no DB, no live Cerbos, no PDP — pure YAML + JSON parse):

- 1 sanity check the catalog's 61 kinds all resolve to a real `resource_*.yaml` policy.
- 1 sanity check on the 4-kind exempt registry (no dupes, right size).
- **4 tests (`describe.each`)** — one per exempt kind (`assistant_thread`, `assistant_memory`,
  `mcp_tool`, `agent_run`): asserts the kind's policy contains **zero rules using `derivedRoles`
  at all** — strictly stronger than "platform_admin reaches nothing," so a restored
  `company_admin` rule fails this too, matching what the exempt policies' own headers forbid.
- 1 sanity check that 57 non-exempt kinds remain (61 − 4).
- **57 tests (`it.each`)** — one per non-exempt kind: asserts `platform_admin`'s reach (computed
  from that kind's OWN rules only, no cross-kind composition — `platform_admin` is never granted
  via string composition or permission-matching anywhere in this codebase, it is always named
  directly) equals the kind's full action universe from the catalog's `cerbosKind`/`cerbosAction`
  pairs (the catalog's `class` field is never read for this computation — see the file header for
  why that matters).
- 1 explicit `rollup`-needs-no-special-case test (its one explicit, non-wildcard rule already
  satisfies the generic assertion above — verified separately as a named case per the ticket's
  instruction, even though the `it.each` loop above already covers it).
- 1 test pinning that the 15 relationship pairs live exactly, and only, inside the 4 exempt kinds'
  action universes (61−4=57 kinds all have a non-empty universe; total across the 4 exempt kinds
  is exactly 15).

**Why this is a different derivation from the parity suite (and must stay a separate file):** the
parity suite's `computeCerbosCoverage()` filters relationship-class pairs out of its own coverage
computation before any test reads it (`if (classByPair.get(pairId) !== "grantable") continue`) —
that is precisely the vacuous-guard defect (Finding G1, §5). This test never asks "is this pair
grantable" at all; for the 4 exempt kinds it asks the syntactic question "does this kind have any
`derivedRoles` rule," and for the other 57 it asks "does `platform_admin`'s reach equal the
catalog's full action list for this kind" — using the catalog purely as an action-universe lookup,
never as a class filter.

## 5. G1 fix — `role-permission-parity.db.test.ts`

**The vacuous arm:** `computeCerbosCoverage()`'s pre-filter
(`if (classByPair.get(pairId) !== "grantable") continue`) is unchanged — it is CORRECT for this
function's real purpose (computing bundle-comparable reach over the 215 grantable pairs a
`role_permissions` bundle can actually hold; 0093's trigger forbids inserting a relationship-class
key into any bundle, so filtering them out of the Cerbos-side comparison is the right behavior for
THAT half of the check). What was wrong was the **header's claim** that this filtered function
would catch a restored `assistant_thread` wildcard, and the **absence of any documentation** on
the "none of the 15..." test's `cerbosLeak` arm explaining that it inherits the same filter and is
therefore structurally unable to fire.

**What changed:**
1. Header rewritten to state precisely what the file guarantees: bundle == live-Cerbos-derived
   reachability **restricted to the 215 grantable pairs**. Explicitly states it provides **no
   signal** on the exempt-kind question and points to `iam-215-boundary-pin.test.ts` as the file
   that does.
2. The `cerbosLeak` arm inside "none of the 15... is reachable by ANY role" is kept (removing it
   would remove a real, if narrow, sanity check that `computeCerbosCoverage()`'s own filter never
   regresses to leaking a relationship key) but is now annotated in-line as structurally vacuous
   with respect to the assistant_thread-wildcard scenario, and its failure message no longer claims
   to be the guard against that scenario. The `bundleLeak` arm (real — DB-side, protects against a
   trigger bypass) is unchanged and documented as the one with actual teeth in this test.

**Result:** 22/22 green (unchanged test count — no test was added or removed, only headers/comments
and the failure-message text on one existing assertion):

