## 1. Method

Source of truth is the actual Cerbos policies (`cerbos/policies/resource_*.yaml` +
`derived_roles.yaml`), parsed with a real YAML parser (not regex), `*` actions wildcard-expanded
against each kind's own action universe (`permission-catalog.json`'s 230 concrete pairs — the same
universe IAM-01b/01c already froze). A role "reaches" a `(kind, action)` pair if any `EFFECT_ALLOW`
rule names it — directly, or via the `it_staff` / `hr_people_ops` / `hr_people_reader` groupings, or
via the `module_staff`/`module_manager`/`module_approver` string-composition, resolved per kind by
reading which `module:` attribute value each resource kind's controllers actually pass (grepped, not
assumed). Resource-instance conditions (`inTenant`, `notLow`/assurance, self-ownership) are treated
as satisfied — the same abstraction `2026-08-10-iam-01a-02a-analysis.md` Part 4 and the drift
register both use, which is why e.g. `member`'s count includes self-scoped actions like
`hr.case.create`/`hr.case.cancel`.

This was done independently (a from-scratch policy parse, not a read of the drift register's
numbers) and then cross-checked against Part 4's published table. Every one of the 8 directly
comparable totals reproduced exactly: `platform_admin` 215/57, `company_admin` 199/55,
`group_executive` 118/35, `manager` 109, `member` 74, `team_lead` 60, `viewer` 30, `client` 6 — and
the module-composed derived-role aggregates (`module_staff` 34, `module_manager` 56,
`module_approver` 1, `it_staff` 3, `hr_people_ops`/`hr_people_reader` 5/5) also reproduced exactly
once summed across their real-role instances. This gave high confidence before a single migration
line was written.

`class='relationship'` permissions (the 15 assistant/mcp_tool exemptions, Ruling 3) are never
inserted into any bundle — enforced twice over: this migration's own SELECT excludes them by
construction, and 0093's `role_permissions_reject_relationship` trigger would refuse the INSERT at
the DB layer even if it tried.

## 4. NEW findings (provisioning gaps, not Cerbos↔UI drift — flagged, not fixed)

These fall out of needing every bundled role to actually have a `roles` row. Per the program rule
("document, don't fix silently"), neither is remediated here.

**(a) `agency_approver` has never been seeded by any migration, ever.** Grepped every
`migrations/*.sql` for the literal string — zero hits. It has existed live on gda-aicenter (1
holder, per the drift register's own live check) ONLY because `npm run seed:agency` creates it by
hand. This is the identical provisioning-gap shape IAM-02e (`0095`) closed for six OTHER roles
(`member`/`manager`/`company_admin`/`platform_admin`/`group_executive`/`it_admin`) — that ticket's
own list of six simply didn't include this seventh instance. `0094` seeds the `roles` row itself
(idempotent, same idiom) because `role_permissions` needed it to exist; a fresh migration-only
environment now has a grantable `agency_approver` row, closing the gap as a side effect, but this
was not a scoped fix — flagged here as its own follow-up so it's tracked as a deliberate decision
rather than an incidental one.

**(b) `webdev_staff`/`webdev_manager` are real Cerbos reach with no seeded role to claim them.**
`resource_webdev_change_request.yaml` and `resource_webdev_provisioned_site.yaml` both carry
`module_staff` and `module_manager` rules (7 `(kind,action)` pairs total: change_request `read`+
`triage` for module_manager, `read` for module_staff; provisioned_site `read`+`provision`+
`reconcile` for module_manager, `read` for module_staff) — but no migration and no seed script
creates a `webdev_staff` or `webdev_manager` `roles` row anywhere. This is byte-for-byte the same
defect shape IAM-02d (`0091`) found and fixed for `search_staff`/`search_manager` before any real
search service assignment existed to trigger it. **Not yet a live incident** for the identical
reason IAM-02d's finding wasn't: `service-reconciler.ts`'s `moduleRoleId()` returns `null` for an
unseeded role name and the caller silently skips (no grant, no error) — but the moment a real
webdev department service assignment goes active, it reproduces the pre-0069/pre-0091 silent-skip
bug a third time. **Not fixed here** — no ticket authorizes minting a new role, and 0094's bundle
correctly seeds ZERO rows for these two names (there is nothing to bundle onto a role that doesn't
exist). Worth pulling forward as an `IAM-02d`-shaped ticket before any real webdev service
assignment is created.

**(c) `it_admin`/`it_manager`/`it` cannot read the devices they can create/update/delete.**
`resource_device.yaml`'s `read` rule lists `company_admin, manager, member, viewer, team_lead` —
**not** `it_staff`. The `create`/`update`/`delete` rule lists `company_admin, it_staff`. This isn't
Cerbos↔UI drift (not compared against `rbac.ts` here) and isn't new — it's visible directly in the
bundle sizes (3/3/3, all write-only) — but worth a line in this report since it's a genuinely odd
enforcement shape (an IT operator can register a device they then can't look up via
`GET .../devices` unless they also hold `company_admin`/`manager`/etc.) that nobody appears to have
flagged before. Not touched; recorded for whoever next reviews `resource_device.yaml`.

## 5. How the module roles (`hr_staff`/`hr_manager`, `search_staff`/`search_manager`,
`reports_staff`/`reports_manager`) should bundle under IAM-02c

**They already do, in this migration, exactly the shape IAM-02c (Ruling 5, option (a)) wants.**
0094 does NOT seed a placeholder `module_staff`/`module_manager` bundle and rely on string
composition at the data layer — every one of the six module-tier roles gets its OWN concrete,
named bundle (`hr_staff` 13 pairs, `hr_manager` 23, `search_staff` 24, `search_manager` 37,
`reports_staff` 4, `reports_manager` 3), computed by resolving the module string per kind ahead of
time rather than deferring it to request-time composition. IAM-02c's remaining work is therefore
narrower than "build per-module bundles from scratch" — it's:

1. **Retire the Cerbos-side string composition** (`derived_roles.yaml`'s `module_staff`/
   `module_manager`/`module_approver` definitions) once IAM-04's permission-matching lands, since
   the data-side equivalent already exists here.
2. **Extend the SAME pattern to `webdev_staff`/`webdev_manager`** once finding (b) above is
   resolved and those roles are seeded — the bundle math is already computed (7 pairs: 2 for
   `webdev_staff`, 5 for `webdev_manager`; see this migration's header for the exact split) and
   just needs the `roles` rows to exist and two more `VALUES` blocks in a follow-on migration.
3. **Decide whether `service_assignment:read` and `core.member.read`'s generic (module-agnostic)
   reach should be pruned per-module or kept uniform.** This migration bundled both onto ALL THREE
   currently-seeded module_staff/module_manager pairs (hr/search/reports) because the underlying
   Cerbos rule genuinely has no module hardcode for these two kinds — any module_staff-composed
   role can reach them today. IAM-02c should decide whether that's the intended shape going
   forward (a new module automatically getting `service_assignment:read` the moment it's seeded) or
   whether it should be narrowed — a design call, not a data call.
4. **`module_approver` has exactly one live instance (`agency_approver`).** If IAM-02c wants to
   generalize the module_approver pattern to other modules, the bundle math is trivial (whatever
   `<module>_approval:approve`-shaped action exists for that module) but there is currently no
   second instance to generalize from.

No change to `service-reconciler.ts`'s materialization or the `managed_by` invariant was made or
needed — this migration only touches `role_permissions`, which nothing reads yet.
