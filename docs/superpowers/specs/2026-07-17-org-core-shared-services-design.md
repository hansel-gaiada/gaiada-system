# ORG-CORE: Shared-Services Architecture — Decided Design

> Produced 2026-07-17 by a 13-agent design workflow (5 code readers -> 3 independent architecture proposals -> 3-judge panel -> 2-agent red team). Winner: Proposal B (judge tally: {"A":151,"B":157.5,"C":137}). This document is the authoritative design input for the ORG-CORE workstream of the Backbone program.

## Title
Gaiada Shared-Services Layer — Minimal-Delta Design: Relational Service Assignments over the Existing Org Blob (org stays JSONB, access stays memberships+grants, cross-company stays fan-out)

## Thesis
Keep every load-bearing mechanism that works today — the per-company org JSONB blob as the presentation tree, company_memberships + user_roles as the sole access substrate, Cerbos derived-role cascade as the per-request gate, single-tenant withTenants([t]) transactions for all business SQL, and BFF fan-out for anything cross-company — and add exactly two new tables (org_units, service_assignments) plus two provenance columns (kind, managed_by) on the existing membership/grant tables. A "connect the dots" drag in the holding org view writes one service_assignments row linking an org-chart department node (by its existing blob node id) to a target company + module key. A small, idempotent reconciler is the ONLY new subsystem: it materializes that assignment into ordinary company_memberships rows (kind='service') and ordinary user_roles grants (role '<module>_staff', scope company:<target>, managed_by=<assignment>) for every person placed in that department's subtree, and removes exactly those rows on revoke or on org-chart edits — so Cerbos, RLS, principal assembly, the D11 revocation path, the UI company switcher, the MCP OBO flow, and the sync engine all work unchanged because they only ever see memberships and grants they already understand. Data never moves between tenants: HR work for company B lives in B's tenant_id rows forever (module tables use the standard tenant_isolation policy), which sidesteps the entire tenant-mutation/sync/rollup minefield. Cross-company "ALL" views are per-tenant fan-out (the proven approvals-inbox pattern), never widened RLS sets, so none of the ~100 multi-tenant-unsafe SQL hotspots need auditing. The one deliberate new policy class is the dual-side RLS policy on service_assignments itself (visible to provider AND target) — an explicit, narrow widening of D5 for one metadata table.

-- (B) service_assignments: THE connect-the-dots edge. One row = "unit U of provider P operates
-- module M for target company T".
CREATE TABLE service_assignments (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  unit_id             uuid NOT NULL REFERENCES org_units(id),
  provider_tenant_id  uuid NOT NULL REFERENCES companies(id),  -- denormalized = org_units.tenant_id (kept for RLS + queries)
  target_tenant_id    uuid NOT NULL REFERENCES companies(id),
  module_key          text NOT NULL,                            -- validated against the module registry at the API layer
  status              text NOT NULL DEFAULT 'active' CHECK (status IN ('proposed','active','revoked')),
  created_by          uuid NOT NULL REFERENCES users(id),
  created_at          timestamptz NOT NULL DEFAULT now(),
  accepted_by         uuid REFERENCES users(id),                -- target-side consent when not created by a global role
  accepted_at         timestamptz,
  revoked_by          uuid REFERENCES users(id),
  revoked_at          timestamptz,
  origin_site         text NOT NULL DEFAULT 'central',
  CHECK (provider_tenant_id <> target_tenant_id)
);
CREATE UNIQUE INDEX ux_service_assignments_active
  ON service_assignments(unit_id, target_tenant_id, module_key) WHERE status IN ('proposed','active');
CREATE INDEX ix_service_assignments_target ON service_assignments(target_tenant_id, module_key) WHERE status = 'active';
ALTER TABLE service_assignments ENABLE ROW LEVEL SECURITY;
ALTER TABLE service_assignments FORCE ROW LEVEL SECURITY;
-- NEW POLICY CLASS (deliberate D5 widening, mirrored on the site_subscriptions precedent of
-- non-tenant_isolation FORCE-RLS): a row is visible to a session authorized for EITHER side;
-- writable only from the provider side (creation) — status transitions go through the app anyway.
CREATE POLICY service_edge_visibility ON service_assignments FOR ALL
  USING (
    provider_tenant_id = ANY(string_to_array(NULLIF(current_setting('app.current_tenant_ids', true), ''), ',')::uuid[])
    OR target_tenant_id = ANY(string_to_array(NULLIF(current_setting('app.current_tenant_ids', true), ''), ',')::uuid[])
  )
  WITH CHECK (
    provider_tenant_id = ANY(string_to_array(NULLIF(current_setting('app.current_tenant_ids', true), ''), ',')::uuid[])
  );
-- NOTE: no column literally named tenant_id, so rls.test.ts's sweep does not cover it — 0026 ships
-- with a dedicated test asserting relforcerowsecurity + both policies on this table.

Key schema decisions: (1) the blob keeps zero new responsibilities — node ids ('d-hr') were already load-bearing external references (pm_tasks.assignee.refId), org_units just gives them a FK-able uuid identity; (2) no staff table — the set of people a unit contributes is derived from the blob subtree at reconcile time and MATERIALIZED as grants, so grants are the cache and the truth simultaneously; (3) no tenant_id mutation anywhere, ever; (4) rollup_metrics, outbox_events, files all untouched.

## Authorization Model (HR-serving-3-companies walked end-to-end)
PRINCIPLE: org placement never grants anything directly. Org placement + service_assignments are INPUT to a reconciler that emits ordinary memberships and grants; Cerbos and RLS only ever evaluate memberships and grants, exactly as today. This keeps the two-wall model intact (Cerbos inTenant + derived roles as the per-request gate; FORCE RLS on app.current_tenant_ids as the storage floor) with zero changes to withTenants, principal assembly, or the GUC contract shared with sync-engine-go.

NEW CERBOS PIECES (policy repo change, versioned):
1. derived_roles.yaml gains module_staff and module_manager, string-composed exactly like the existing module_approver:
   - name: module_staff
     parentRoles: ["user"]
     condition:
       match:
         expr: >-
           request.resource.attr.module != "" &&
           request.principal.attr.grants.exists(g,
             g.role == (request.resource.attr.module + "_staff") && (
               g.scopeType == "global" ||
               (g.scopeType == "company" && g.scopeId == request.resource.attr.tenantId)))
   (module_manager identical with "_manager"; both compose from resource.attr.module so ONE derived-role pair serves hr, finance, legal, it-as-a-service... no per-module policy explosion.)
2. resource_hr_case.yaml / resource_hr_record.yaml: read/create/update → module_staff, module_manager, company_admin (all under variables.inTenant && variables.notLow); delete + export → module_manager + company_admin, with an additional assurance=="high" condition on bulk export (first real use of the dormant high tier). inTenant is satisfied because the reconciler minted a real membership row in the target tenant.
3. resource_service_assignment.yaml, actions propose/accept/revoke/read:
   - read: company_admin (in provider OR target — the controller passes tenantId = whichever side the URL names), group_executive, platform_admin.
   - propose: company_admin (inTenant on provider), group_executive, platform_admin.
   - accept: company_admin (inTenant on TARGET), group_executive, platform_admin.
   - revoke: either side's company_admin, group_executive, platform_admin.
   The controller enforces the two-sided handshake: a global-role actor (the holding) creates status='active' directly (one gesture = done); a provider company_admin creates 'proposed' and a target company_admin must accept — so a child company can never be conscripted silently.
4. resource_member.yaml gains: read for module_staff when resource.attr.module is passed — HR staff may read the served company's directory (they need it); other served-module staff don't get it unless their module policy says so.

RLS: unchanged mechanism. HR endpoints run withTenants([<the one served tenant in the URL>]) like every other route. The ONLY new policy shape is the dual-side service_edge_visibility on service_assignments (metadata, not business data). Business SQL never runs with a widened set — "ALL companies" views are N parallel single-tenant requests.

THE ACCEPTANCE SCENARIO, END TO END:
Setup: holding H (companies.parent_company_id links A, B, C). Company A's org blob has department node d-hr with divisions/persons; persons p-1(user u1, HR lead), p-2(u2), p-3(u3). Actor: hansel (global platform_admin) or a holding exec (global group_executive).

STEP 1 — the drag. In the holding Organization view, the exec drags A's "HR" department card onto company B's card, then onto C's (or multi-selects B+C in the confirm sheet). UI issues POST /api/<A>/org-structure/units/d-hr/assignments {targets:["<B>","<C>"], module:"hr"}. Controller: (a) authorize(principal, {kind:'service_assignment', tenantId:A, module:'hr'}, 'propose') → group_executive derived role matches (global grant) → allow; actor is global so also implicit accept for B and C (otherwise: two more Cerbos checks with tenantId:B / tenantId:C for action 'accept', returning 'proposed' if they fail); (b) validates 'hr' against the module registry (allModules()) — junk keys rejected 422, closing today's unvalidated-enablement hole for this path; (c) withTenants([A]): upsert org_units(A,'d-hr'), insert two service_assignments rows status='active'; (d) runs the reconciler.

STEP 2 — reconciliation (the only new machinery, ~200 lines). For assignment (d-hr→B,hr): read A's blob under withTenants([A]), resolve the d-hr subtree, collect placed staff = distinct assigneeIds with an ACTIVE membership in A (this closes the "unvalidated assigneeId" hole — a bogus/stale assigneeId is skipped and reported, never granted). Desired rows in B: for u1: membership(kind='service', managed_by=asg) + user_roles(u1, hr_manager, company, B, managed_by=asg) [u1's person node sits under a 'role' node flagged lead — v1 simplification: subtree root's directly-assigned person or a per-unit lead marker gets _manager, everyone else _staff]; u2,u3: membership + hr_staff grants. Execute under withTenants([B]) in ONE transaction (single-tenant write convention preserved — WITH CHECK stays a real guard): diff desired vs rows WHERE managed_by=asg, insert/delete the difference ON CONFLICT DO NOTHING, bumpSession(u1..u3) (D11 — live sessions re-principal immediately), writeActivity(B, 'service.staff_granted'...), emitEvent(client, B, 'service_assignment','...','service_assignment.activated', {provider:A, unit:'d-hr', module:'hr', staff:[u1,u2,u3]}). Repeat for C. Audit lands in BOTH tenants (activity in B/C for the grants; activity in A for the assignment creation) — the "one cross-company action, per-tenant audit rows" answer.

STEP 3 — what B now sees. ModuleEnabledGuard('hr') is extended: enabled iff 'hr' ∈ companies.enabled_modules OR EXISTS active service_assignment(target=B, module='hr') — checked under withTenants([B]) (target side of the RLS policy matches). So /api/<B>/hr/* comes alive for B without mutating enabled_modules (enablement provenance stays clean; revoke needs no array surgery). B's company_admin opens HR: Cerbos resource_hr_case read → company_admin derived role, inTenant(B) → allow; withTenants([B]) → ONLY B's hr_cases rows exist under tenant B. B cannot see C's or A's HR data — those are different tenant_id rows and B's sessions never carry those ids. B's member directory does NOT show u1–u3 by default: GET /api/<B>/members now filters kind='employee' unless ?includeService=1 (and the response marks service rows with {kind:'service', via:{provider:'Gaia', unit:'HR'}}) — "each company sees only its own slice" holds in the social surfaces too.

STEP 4 — what HR staff u2 sees. Next login (or immediately after the D11 bump), assemblePrincipal reads memberships → companies=[A,B,C]; grants include (hr_staff, company, B) and (hr_staff, company, C). GET /api/me now also returns serviceScopes:[{module:'hr', providerTenantId:A, unitName:'HR', companies:[A,B,C]}] (computed from managed_by joins + home grants). UI switcher: A, B, C, and ALL (per module). Selecting B: nav renders only what u2's grants light up — in B their only grant is hr_staff, so ROLE_CAPS gives hr.* capabilities only; every non-HR endpoint in B Cerbos-denies server-side (hr_staff matches no other resource policy — same deliberate isolation trick as the 'client' role, which is the proven precedent). Selecting ALL: the BFF fans out GET /api/<A|B|C>/hr/cases?assignee=me in parallel and merges rows tagged {tenantId, company} — the exact approvals-inbox pattern from platform-ui/src/lib/data.ts; every leg independently Cerbos+RLS enforced, so a stale scope in the UI yields a 403 leg that's dropped, never data. UI gating is cosmetic; the server would return the same union to curl.

STEP 5 — My Work stays personal. u2's My-Work fans out over companies=[A,B,C] and every per-tenant PM/HR query already filters assignee=me (responsibleId/refId match). Nothing about being HR-for-B leaks B's whole board into My Work: the department-wide view lives under the HR module pages (Cerbos-gated to module_staff), My Work stays "rows where I am responsible". Department/division/person focus scoping per the vision maps to: department focus = the module workspace (all unit staff, via module_staff), division focus = filter by the unit subtree's division node ids (blob-derived, passed as query param, validated against org_units), person focus = assignee=me — three query params on the same endpoints, all inside one tenant per request.

STEP 6 — drag-undo. Exec deletes the edge (drag back / disconnect): DELETE /api/<A>/org-structure/assignments/<asgB> → authorize revoke → status='revoked', revoked_by/at set → reconciler: delete all user_roles/company_memberships WHERE managed_by=asgB (memberships soft-deleted per existing convention), bumpSession(u1..u3) → within one request u2's principal no longer contains B; Cerbos inTenant fails, hr_staff grant for B is gone, RLS set never includes B again. ModuleEnabledGuard for B/hr goes dark (404) unless B independently enabled 'hr'. B KEEPS its data: hr_cases rows are B's tenant rows; if B later hires its own HR or connects a different provider, the data is sitting there. Nothing is deleted, re-homed, or resynced. Revoke emits service_assignment.revoked into B's outbox with {openCases:n, orphanedResponsibleItems:k} so n8n/the target admin can chase reassignment.

STEP 7 — org shift while work is in flight. (a) Person moved OUT of d-hr in A's chart: PUT /api/<A>/org-structure detects (has active assignments) → reconciler re-diffs → u3's B/C grants+memberships (managed_by rows only) deleted, session bumped; u3's in-flight items in B keep u3 as responsibleId (data untouched) but u3 loses access — the revoke event payload lists them for reassignment; u1/u2 unaffected. (b) Node d-hr deleted or renamed-id from the blob: org_units row flips status='orphaned'; assignments STAY active and grants are FROZEN (not silently revoked — a fat-fingered chart edit must not sever HR for three companies); the UI shows an "orphaned assignment" warning banner on the org page and in the target's HR settings; explicit revoke or re-link (PATCH assignment unit_id) resolves it. (c) Whole-blob PUT last-write-wins races: unchanged risk from today, but the reconciler is deterministic from (blob, assignments) so the LAST write's reconcile is the correct final state — no drift accumulates. (d) Concurrent reconciles: per-target advisory lock (pg_advisory_xact_lock on hash(target_tenant_id)) serializes.

STEP 8 — automation/MCP acting for shared-service users: see downstream_impact; the key property is that OBO principals resolve to the SAME memberships+grants, so a WA/n8n action for u2 in tenant B passes tenantId:B per call and Cerbos evaluates the identical grant set — no new trust surface.

## API Contracts
All new endpoints follow the existing /api/:tenantId/* convention (Fastify-adapter Nest controllers, AuthGuard + Cerbos per route); nothing existing changes shape. Additions to docs/FRONTEND-BFF-CONTRACT.md:

ORG GRAPH / SERVICE LINKS (ServiceAssignmentsController, @Controller('api')):
- GET  /api/:tenantId/org-structure — UNCHANGED wire shape {root, updatedAt} (404-when-never-set semantics preserved; the UI's sanitize/fallback chain untouched). Side effect added server-side only: PUT now runs the reconciler when the tenant has active provider-side assignments, then returns {ok:true, reconciled:{granted:n, revoked:m, orphanedUnits:[...]}} — extra fields, additive.
- GET  /api/:tenantId/org-structure/assignments?direction=providing|receiving|all — rows {id, unit:{id,nodeId,name,kind,status}, providerTenantId, providerName, targetTenantId, targetName, module, status, createdAt, acceptedAt, staffCount}. Cerbos service_assignment:read with tenantId=:tenantId (RLS dual-side policy makes both directions visible to the right side).
- POST /api/:tenantId/org-structure/units/:nodeId/assignments — body {targets: string[], module: string}; :tenantId is the PROVIDER. Validates module against the registry; lazily creates org_units. Global actor → 'active' + reconcile; provider-admin actor → 'proposed' per target. Returns 201 {assignments:[{id, target, status}]}.
- POST /api/:tenantId/org-structure/assignments/:id/accept — :tenantId is the TARGET; Cerbos accept with tenantId=target; flips proposed→active, reconciles. 
- DELETE /api/:tenantId/org-structure/assignments/:id — revoke from either side (Cerbos revoke); reconciles removal; 200 {ok:true, revoked:{grants:n, memberships:m, openItems:k}}.
- POST /api/:tenantId/org-structure/assignments/:id/reconcile — idempotent manual re-run (admin repair; also the target of a nightly sweep cron).
- GET  /api/:tenantId/service-units — units SERVING this tenant, for the PM assignee picker and HR workspace header: [{assignmentId, module, unitName, providerName, staff:[{userId,name}]}] (staff resolved server-side from provider grants — the target never reads the provider's blob).

COMPANY SELECTOR / IDENTITY:
- GET /api/me — additive field serviceScopes: [{module, providerTenantId, unitId, unitName, companies: string[]}] derived from the caller's managed_by grants (plus home membership); companies[] itself already includes served tenants because memberships are real. UI uses serviceScopes to render the per-module A/B/C/ALL selector and to badge served companies in the switcher.
- GET /api/:tenantId/members — additive query param includeService=1 (company_admin only); default response now excludes kind='service' rows; when included they carry {kind:'service', via:{assignmentId, providerName, unitName, module}}. (The ONE behavioral change to an existing endpoint, and it's the privacy-correct direction.)

SCOPED MODULE DATA (HR module, standard module pattern — @Controller('api/:tenantId/hr') behind ModuleEnabledGuard('hr') with the OR-service-assignment extension):
- GET/POST /api/:tenantId/hr/cases (?status=&kind=&assignee=me&division=<nodeId>), GET/PATCH /api/:tenantId/hr/cases/:id, POST .../cases/:id/comments (reuses comments table)
- GET/POST /api/:tenantId/hr/records?subject=<userId>, GET/PATCH/DELETE /api/:tenantId/hr/records/:id (delete = module_manager/company_admin; export gated assurance high)
- All handlers: authorize(principal, {kind:'hr_case'|'hr_record', tenantId, module:'hr'}, action) then withTenants([tenantId]) — indistinguishable from the agency module's shape, which is why the guard extension is the only framework change.
- Aggregates for "ALL": NONE server-side in v1 — the BFF fans out per tenant (lib/data.ts pattern). If later needed, add hr.open_cases to metric_definitions and ride D12 rollups; never a widened raw-row query.

MODULE CATALOG (small enabler, closes an existing gap): GET /api/modules — registered module keys + labels from the registry (replaces the UI's KNOWN_MODULES hardcode); PATCH /api/:t/company/modules gains registry validation (422 on unknown keys).

EVENTS (outbox, v1 envelope unchanged — new event TYPES only): service_assignment.proposed|activated|revoked (tenant = target), service_staff.granted|revoked (tenant = target, payload {userId, module, assignmentId, role}), org_unit.orphaned (tenant = provider). Added to N8N_BRIDGE_EVENTS allowlist as needed.

## UI Behavior (org builder, connect-the-dots, company selector)
ORG BUILDER (per-company /companies/[companyId]/org): unchanged for intra-company editing — same drag-to-reparent, same whole-tree PUT, same sanitizer. Additions: department/division cards render a "Serving: B, C" chip row (from GET assignments?direction=providing) and served units are NOT part of the tree — no DAG is ever created; the blob stays a strict tree and countTree/isWithin/scan invariants hold. An orphaned-assignment banner appears if a linked node id disappears after an edit, with Re-link / Revoke actions.

CONNECT-THE-DOTS GESTURE (holding Organization view, /organization): this view already renders all companies' cards + trees (computed from parent_company_id). New: dragging a department node from company A's tree onto company B's company card opens a confirm sheet — "Connect HR (Gaia Digital) to serve: [x] Sanur Resort [x] Printing Co — as module: [HR ▾]" — listing the staff who will gain access (dry-run response from a ?dryRun=1 POST). Confirm writes POST /api/<A>/org-structure/units/d-hr/assignments {targets, module}. THE GESTURE NEVER MUTATES EITHER BLOB — it writes only the relational edge; the org charts of A and B are untouched (B's chart does not grow an HR subtree; B sees "Serviced by Gaia — HR" in its org page's new "Serviced functions" panel instead). Dragging the chip off / clicking disconnect issues the DELETE (undo). For a non-global company_admin the same gesture creates a 'proposed' edge rendered dashed, and B's admin gets a notification + accept button (rides the existing notifications table, href '/admin/services').

SIDEBAR / COMPANY SELECTOR: CompanyContext keeps ONE active company (no rewrite). The switcher lists me.companies as today, with served companies badged by module ("Sanur Resort · via HR"). For users with serviceScopes, module workspaces (e.g. /hr) gain a scope pill: A | B | C | ALL. ## Tradeoffs
ACCEPTED COSTS, chosen deliberately for minimal delta: (1) Fan-out instead of set-queries for "ALL" views — N parallel HTTP requests per aggregate page (N = served companies, single digits here), no server-side cross-company sorting/paging; in exchange, ~100 multi-tenant-unsafe SQL call sites need zero audit, WITH CHECK remains a real write guard, and the single-tenant transaction convention survives intact. If holdings grow to dozens of companies, revisit with PlanResources-driven set endpoints — the schema doesn't block it. (2) The blob stays semi-structured truth for org shape — node ids remain FK-less strings; mitigated by org_units anchoring + orphan detection + freeze-don't-revoke semantics, but a determined admin can still rename ids and cause orphan churn. The alternative (full normalization) rewrites the builder, the sanitizer pair, pm_tasks.assignee, and departments.ts for marginal gain. (3) Grants are materialized, not computed at check time — reconciler bugs or missed triggers can drift grants from org reality; mitigated by determinism (pure function of blob+assignments), idempotent manual /reconcile, a nightly sweep, and managed_by provenance making every generated row auditable and bulk-revocable. The alternative (Cerbos evaluating the org graph live) puts a JSONB tree walk in the hot authz path and a second source of truth in policy. (4) Service staff hold REAL memberships in served companies — inTenant, RLS, notify(), and the switcher all work for free, but every "who's in this company" surface needed the kind filter; there is a residual risk that new endpoints forget to filter kind='service' (add a lint/test convention). The alternative (a parallel non-membership access channel) would fork principal assembly and Cerbos variables — far more dangerous. (5) Whole-of-target module scope in v1 — hr_staff in B sees all of B's HR data, not "only records about served-population X"; finer slicing waits for a record-scope or attribute filter (the scope_type='record' value already exists in the CHECK, unused — a clean future hook). (6) Dual-side RLS on service_assignments is a new policy class and a real (if narrow) D5 widening — one metadata table, no business rows; it needs its own test since the tenant_id-column sweep misses it. (7) Lead-vs-staff role mapping from the chart is crude in v1 (unit-lead marker → _manager); org 'role' nodes carrying explicit platform-role bindings is a natural v2 but expands the blob contract, so deferred. (8) ModuleEnabledGuard gains a second query per module request (indexed partial-index hit; cacheable later — the guard is already uncached SQL today, so this matches existing cost shape). (9) The two-sided consent handshake adds a 'proposed' state the holding actor never sees — small state-machine complexity bought to prevent silent conscription of a child company, which the verbatim vision's holding-drags gesture would otherwise allow any provider admin to do.

## Red-team findings (to be resolved as tickets)
### [CRITICAL] Reconciler is a cross-tenant writer, and the only structural coincidence that made the missing withTenants subset-check safe is exactly what it breaks
Verified in code: db/index.ts withTenants() sets app.current_tenant_ids to whatever array the caller passes, with ZERO check that those tenants are in the principal's authorized set. Today this is safe only by coincidence — every controller (e.g. agency.controller.ts) calls authorize(...,{tenantId}) and withTenants([tenantId]) with the SAME variable, so Cerbos is a de-facto gate for the tenant the query will run under. The design's reconciler deliberately severs that coincidence: it authorizes a service_assignment on the PROVIDER (tenantId:A, action 'propose'/'active') and then writes company_memberships and user_roles for the TARGET under withTenants([B]). Worse, user_roles has no tenant_id and NO RLS at all (0001_core.sql:55-62 — it is a 'global table'); company_memberships has FORCE RLS but the reconciler runs it under [B] which it chose, so RLS rubber-stamps it. The entire safety of minting (user, hr_staff, company:B) therefore rests on one app-layer branch: 'global actor => active+reconcile; provider-admin => proposed, no reconcile until target accepts.' Any bug in that branch (mis-classifying a provider company_admin as global, an accept endpoint that doesn't re-check the TARGET side, an actor with a global company_admin grant which the derived role treats as company_admin for every tenant) mints real memberships in a company the actor was never authorized for — and a minted membership satisfies inTenant everywhere and a minted grant is invisible to RLS. There is no second wall behind the branch.
**Fix:** Make the C-graft withScopes choke point a HARD, non-optional invariant in the db layer, but split it: (1) a default assertion that declared tenant set ⊆ principal.companies for ALL normal handlers; (2) ONE explicitly-named privileged writer (e.g. reconcilerWrite(assignmentId,target)) that is the sole code path allowed to write a tenant outside the principal set, and only after it re-reads the service_assignments row and re-verifies status='active' AND a recorded target-side accepted_by (or a global actor) for THAT assignment inside the same transaction. Grep-lint that withTenants with an unvalidated set appears nowhere else. Because user_roles has no RLS, also add an application-invariant test asserting the reconciler is the only module that INSERTs user_roles with managed_by NOT NULL.

### [CRITICAL] Grant materialization coalescing (ON CONFLICT DO NOTHING + single UNIQUE row) loses provenance, leaving cross-company standing access alive after revoke
user_roles has UNIQUE(user_id, role_id, scope_type, scope_id) (0001_core.sql:62) and the design explicitly reconciles with ON CONFLICT DO NOTHING and revokes with DELETE WHERE managed_by=asg. A single grant row cannot carry two provenances. Concrete leak paths: (a) u2 already holds a MANUAL (hr_staff, company:B) grant (e.g. B once ran its own HR). Assignment A->B is created; reconciler's insert conflicts and does nothing, so no managed row exists. When A->B is later revoked, DELETE WHERE managed_by=asg removes nothing — but the manual row was never the reason u2 could see A's-perspective HR either; the coalescing means the two are indistinguishable and revoke can only ever leave the row. u2 (an A employee) retains hr_staff on B after the service relationship ends. (b) Two overlapping assignments asg1(A->B) and asg2(A'->B) both want (u2, hr_staff, company:B). Only asg1's row exists; asg2's insert is swallowed. Revoking asg1 DELETEs the row and bumps sessions — u2 loses access asg2 should still grant (availability break) — OR, if implementers make revoke conservative to avoid that, u2 keeps access after BOTH are revoked. Either way the model cannot represent 'this grant is live because of N reasons.' Cross-company data access outliving the relationship that authorized it is the exact failure this design claims to prevent.
**Fix:** Stop coalescing provenance. Either add managed_by to the uniqueness so multiple provenance rows coexist (UNIQUE(user_id, role_id, scope_type, scope_id, managed_by), with principal assembly DISTINCT-ing at read time), or introduce a grant_sources(user_role_id, assignment_id) junction and treat a grant as live iff >=1 source remains; revoke removes only its own source and deletes the grant only when the last source is gone (reference counting). Manual grants get a sentinel source so the reconciler can never resurrect or delete them. Add a test: create manual grant, add+revoke an overlapping assignment, assert the manual grant's liveness is unchanged; and revoke one of two overlapping assignments, assert access persists.

### [MAJOR] scopeCovers over-grant is real in code, and the feature's independently-shippable steps let it land before the fix
rbac.ts:58-64 confirms the flaws the design flags but defers to step 6: scopeType==='team' returns true (covers EVERY company), and scopeType==='company' returns true when scopeId==null (a null-scope company grant covers every company in me.companies). The design's own migration_path says steps 4-5 (backend + HR module, which turn the feature on) are independently shippable and 'frontend-first is also fine,' while the rbac.ts fix is in step 6. The defense 'Cerbos denies whatever the UI over-promises' holds ONLY for surfaces that do a per-resource Cerbos check with the exact tenantId. The new serviceScopes-driven switcher and ALL fan-out iterate accessibleCompanies()/me.companies to decide which tenants to fetch; any served-company nav item whose backend is a BFF aggregation route, a /api/me-derived view, or any endpoint added without a per-resource authorize() will expose data for tenants the user only 'covers' via the team/null-scope bug. The design also DELETES holding_head but leaves the null-scope company-grant coverage that any seed/manual grant can still trip.
**Fix:** Ship the scopeCovers fix (team scope must NOT blanket-cover; null-scope company grant must NOT cover all companies) in the SAME release train as steps 4-5, and gate the feature flag on it. Add a server-side invariant test that every new served-company route (hr/*, service-units, me serviceScopes) calls authorize() with the resolved tenantId before any withTenants(), and a UI test that a team-scoped or null-company grant does not surface any company in accessibleCompanies() beyond DB membership.

### [MAJOR] service_assignments target is unconstrained: a provider admin can name any company (even cross-holding) as target; dual-side RLS then leaks the edge to it
The schema's WITH CHECK on service_edge_visibility only validates provider_tenant_id ∈ session set; target_tenant_id has no holding constraint in the schema or the described controller, even though companies.parent_company_id exists (0001_core.sql:12). A provider company_admin can therefore INSERT status='proposed' rows naming ANY company_id as target — including companies in a different holding entirely. The USING clause of the dual-side policy makes every such proposed row visible to that target (its admins see 'A wants to serve you / accept'), i.e. unsolicited cross-holding info + notification spam and a social-engineering accept surface. If a target admin is tricked into POST accept, or a mis-scoped global actor auto-accepts, a cross-holding service link and its grant fan-out form. The two-sided handshake prevents SILENT conscription but not the proposal/visibility itself, nor a cross-holding link once accepted.
**Fix:** At assignment creation validate target_tenant_id shares a holding with provider (walk parent_company_id to a common root, or require an explicit allowed-target ACL like site_subscriptions). Reject cross-holding targets 422. Optionally tighten the dual-side USING so a 'proposed' row is visible to the target only after the provider is confirmed same-holding. Add the FORCE-RLS + dual-policy test (the rls.test.ts sweep keys on column_name='tenant_id' and provably misses provider_tenant_id/target_tenant_id) AND a test that a cross-holding target is refused.

### [MAJOR] service-units and serviceScopes hand stable cross-tenant userIds/names across the provider↔target boundary
GET /api/:tenantId/service-units returns provider A's staff [{userId,name}] to the TARGET company's admin ('staff resolved server-side from provider grants'), and GET /api/me serviceScopes returns providerTenantId to served staff. userId is a global, stable identifier (users is a global table). Handing B's admin the userIds of A's HR employees is a cross-tenant identifier disclosure that enables enumeration against any endpoint that accepts a userId and does not re-derive membership under RLS — e.g. hr_records.subject_user_id, notify() recipient resolution, or any /people-style lookup. It also inverts the design's own privacy stance (members?includeService=1 is gated to company_admin and marks rows, but service-units hands raw provider userIds to the target with no equivalent minimization).
**Fix:** Do not expose raw provider userIds to the target. Return opaque per-assignment staff handles (or just display names + a role label) for the target-facing service-units view; keep real userIds only on the provider side. Audit every endpoint that accepts a userId/subject_user_id param to re-verify the subject has an active membership in the URL tenant under RLS before returning or writing (don't trust that a userId the caller learned is one they may act on).

### [MINOR] Cross-tenant reconcile is not atomic: org-blob PUT and target grant writes are separate transactions
The org PUT reads/writes A's blob under withTenants([A]) and the reconciler writes grants/memberships under withTenants([B]) / [C] — necessarily separate transactions on separate connections (RLS forbids one tx spanning both tenant sets). A crash or error between committing A's blob and committing B's grants leaves grants drifted from org reality: either stale cross-company access (blob removed the person but grant persists) or lost access. The design acknowledges determinism + nightly sweep + idempotent /reconcile as mitigation, but the drift window is real and, in the stale-access direction, is a (bounded) cross-company exposure until the sweep runs.
**Fix:** Make the reconcile intent durable rather than best-effort: on org PUT / assignment change, write a reconcile job to the existing transactional outbox in the SAME transaction as the blob/assignment write, and have a consumer perform the per-target grant reconciliation with at-least-once semantics (idempotent by managed_by diff). That closes the crash window without needing one cross-tenant transaction. Keep the nightly sweep as backstop, but alert if it ever finds drift (drift should be zero, not routine).

### [MINOR] Silent 403-leg drops and indefinite orphan-freeze hide loss/persistence of cross-company access from operators
Two acknowledged behaviors combine into an operability/security-signal gap. (1) The ALL fan-out reuses getPendingApprovals' pattern of silently dropping failed/403 legs (confirmed as the platform-ui/src/lib/data.ts convention). A served user whose scope was partially revoked sees a merged view that is silently incomplete — indistinguishable from 'no data' — so neither they nor an admin can tell access was lost. (2) freeze-don't-revoke leaves grants LIVE indefinitely when a chart edit orphans a unit; a fat-finger delete that orphans d-hr keeps three companies' HR access standing until a human notices the banner. Freezing forever is the wrong default for an access-bearing relationship whose provenance just disappeared.
**Fix:** Adopt A's inclusion-tagged aggregate envelope {items, companies:[{id,included,reason}]} so dropped legs are visible and auditable instead of silent. For orphan-freeze, keep grants live but escalate: emit org_unit.orphaned, show the banner, AND auto-alert the target admins + a TTL after which the assignment auto-suspends (grants off, edge kept) if unresolved — so an accidental orphan cannot leave cross-company access standing indefinitely.

### [CRITICAL] The two-sided handshake is blocked by the design's own RLS policy: target-side accept/revoke UPDATEs fail WITH CHECK
service_edge_visibility is FOR ALL with WITH CHECK (provider_tenant_id IN set). In Postgres, a FOR ALL policy's WITH CHECK applies to the NEW row of every UPDATE. The accept endpoint runs under withTenants([target]) (the design says so explicitly: ':tenantId is the TARGET; Cerbos accept with tenantId=target'), so flipping proposed→active rewrites a row whose provider_tenant_id=A while the session GUC set is [B] → WITH CHECK fails → RLS error. Same for target-side revoke (UPDATE status='revoked'). The runtime role is NOBYPASSRLS (see rls.test.ts's NOSUPERUSER NOBYPASSRLS harness and the db-topology role split), and 'status transitions go through the app anyway' does not help — the app IS subject to RLS. There is no legal session that fixes it: a target admin is not authorized for A, so a widened GUC would violate the design's own withScopes subset rule, and withGlobal (no GUC) sees zero rows under the USING clause. The headline anti-conscription graft is dead on arrival exactly as specified; it would fail in the first integration test of accept.
**Fix:** Split the policy per command in 0026 (renumbered from 0024 by WS0-1, 2026-07-22): CREATE POLICY sa_select FOR SELECT USING (provider OR target in set); sa_insert FOR INSERT WITH CHECK (provider in set); sa_update FOR UPDATE USING (provider OR target in set) WITH CHECK (provider OR target in set) — column immutability (provider/target/unit/module frozen after insert) enforced by an app-layer UPDATE that only touches status/accepted_*/revoked_*, or a BEFORE UPDATE trigger. Extend the dedicated 0026 test to exercise a target-side accept under withTenants([target]).

### [CRITICAL] Reconciler diff model collapses on UNIQUE(tenant_id,user_id) and UNIQUE(user_id,role_id,scope_type,scope_id): overlapping assignments and revoke/re-grant cycles silently sever or strand access
Verified in migrations/0001_core.sql: company_memberships has UNIQUE (tenant_id, user_id) (not partial on deleted_at) and user_roles has UNIQUE (user_id, role_id, scope_type, scope_id). Three concrete breaks: (1) Person in two units serving the same target+module (u2 in d-hr and d-finance→B, or two dept→B assignments for module 'hr'): both assignments desire membership(B,u2) and grant(u2,hr_staff,company,B); only ONE row can exist, managed_by points at ONE assignment; revoking asg1 deletes rows WHERE managed_by=asg1 → u2's membership and hr_staff grant vanish while asg2 still legitimately requires them → live HR access to B severed mid-work with no error. The ON CONFLICT DO NOTHING + 'records nothing' rule makes asg2's claim permanently invisible. (2) Revoke then re-assign: revoke soft-deletes the membership (deleted_at set), but the plain UNIQUE means the re-grant INSERT hits the dead row and ON CONFLICT DO NOTHING skips it → user holds hr_staff grants but principal assembly (src/rbac/principal.ts line 53: status='active' AND deleted_at IS NULL) excludes B from companies → Cerbos inTenant fails everywhere, module dead, no error surfaced. (3) Target-hires-the-contractor: B hires u2 as a real employee — the service row occupies the unique slot; there is no specified upgrade path, and if an admin flips it manually the next reconcile diff sees an unexpected row it may delete or double-count.
**Fix:** Make the ownership model refcounted, not row-owned: a join table service_grant_claims(assignment_id, membership_id/user_role_id) or managed_by uuid[] — reconciler adds/removes CLAIMS, and deletes the underlying membership/grant only when claims drop to zero AND kind='service'. Membership upsert must be ON CONFLICT (tenant_id,user_id) DO UPDATE SET deleted_at=NULL, status='active' (only when the existing row is a dead service row — never resurrect an ex-employee row silently; if kind='employee' exists, record a claim against it and change nothing). Define hire-conversion explicitly: admin 'convert to employee' clears kind/service claims. Add reconciler unit tests for exactly these three sequences before any UI ships.

### [MAJOR] The design's primary actor (group_executive) cannot see the holding view at all today — /api/companies only widens for platform_admin
Verified: src/core/core.controller.ts GET /companies returns ALL companies only when principal has platform_admin/global; everyone else gets id = ANY(principal.companies), and principal.companies is membership-derived. docs/FRONTEND-BFF-CONTRACT.md line 34 states outright: 'a group_executive has no company memberships (me.companies:[]) by design → the app shows "select a company" everywhere'. platform-ui/src/lib/organization.ts getHolding() builds the holding from listCompanies(userId) → a group_executive gets an EMPTY holding. STEP 1 ('a holding exec drags A's HR onto B') is unreachable for the named actor; only hansel-as-platform_admin can perform the gesture. Every 'group_executive can propose/accept/revoke' line in the Cerbos section is moot until this pre-existing gap is closed, and the design never schedules it.
**Fix:** Add an explicit step-0 to the migration path: widen GET /api/companies (and getMe's companies derivation for switcher purposes) to include all non-deleted companies for global group_executive — or adopt the contract's own suggestion and seed execs with memberships in every company. Decide which before building the holding canvas; it changes whether exec fan-out ('ALL' views, My Work) iterates anything.

### [MAJOR] Target-side endpoints can't read org_units: tenant_isolation on org_units blocks the very rows GET /service-units and assignments?direction=receiving must return
org_units carries tenant_id = provider and a standard tenant_isolation policy. GET /api/:t/org-structure/assignments?direction=receiving and GET /api/:t/service-units run under withTenants([target]) — the join to org_units for unit {nodeId, name, kind, status} returns zero rows (RLS filters the provider-tenant row), so the target's 'Serviced functions' panel, the orphan banner on the target side, and the PM picker entries render nameless or empty. The design explicitly promises 'the target never reads the provider's blob' but forgot the target also can't read the provider's org_units row. Same class of bug as finding 1: the dual-side policy exists only on service_assignments, and every contract field sourced from org_units leaks the assumption.
**Fix:** Denormalize unit_name and unit_kind (and unit_status for the orphan banner) onto service_assignments, refreshed by the reconciler on every run — the reconciler already refreshes org_units.name from the blob, so this is one more UPDATE in the same transaction. Keep org_units strictly provider-side. Cheaper and narrower than a second dual-side policy class.

### [MAJOR] UI claim is false: the holding /organization view renders company cards + counts only — the drag-connect gesture is a new interactive canvas, not an extension
Verified in platform-ui/src/app/(app)/organization/page.tsx and lib/organization.ts: the page is a read-only SERVER component rendering a one-level holding→company chart (org-box per company) plus KpiTiles; getHolding() fetches each company's structure only to COUNT nodes (countTree). No department nodes are rendered, nothing is draggable, and OrgBuilder (the only DnD code, components/org/OrgBuilder.tsx) is per-company with drag = re-parent within one tree via a ref'd dragId. 'Dragging a department node from company A's tree onto company B's company card' therefore requires: a new client component rendering N full trees (or expandable dept rails), cross-tree HTML5 DnD with provider context in dataTransfer, drop targets on company cards, the dry-run confirm sheet, proposed/dashed edge rendering, chips, and orphan banners. Feasible — but it's the single largest UI work item in the design and it's budgeted as 'this view already renders all companies' cards + trees'. On a small team this is the line item that blows the estimate.
**Fix:** Re-scope step 6: v1 ships a 'Connect service' BUTTON on the department card in the existing per-company OrgBuilder (opens the same confirm sheet with a company+module picker, calls the same POST) — zero new canvas, same API, same dry-run. The holding-view drag becomes a later polish item. The backend contract is unchanged, so nothing else moves.

### [MAJOR] Reconcile-after-commit has no durable retry: a failed target leg drifts grants for up to 24h with the failure buried in a 200 response
The flow is: PUT org-structure commits the blob (withTenants([A]) txn in company-admin.controller.ts putOrg), THEN the reconciler runs one separate transaction per target (withTenants([B]), withTenants([C]) + advisory lock). If leg C fails (lock timeout, transient DB error, process restart between legs), the blob and B are updated but C's grants are stale — including STALE REVOCATIONS: a person moved out of d-hr keeps access to C until the nightly sweep. The design's only remedies are the manual /reconcile endpoint and a nightly n8n cron — a security-relevant revocation path with a 24h repair SLA and no operator signal (PUT returns {ok:true, reconciled:{...}} with unspecified partial-failure semantics). It also serializes N target transactions + session bumps into the interactive Save-structure request, so a held advisory lock makes the org editor's save hang.
**Fix:** Use the transactional outbox that already exists (src/events/, 0010): the assignment-write/org-PUT transaction emits reconcile.requested(assignmentId) events; an idempotent consumer (the reconciler is already a pure diff) executes per-target legs with the existing dead-letter + retry machinery. PUT returns immediately with per-target status ('queued'/'done'/'failed') and the UI shows a reconciling badge. This deletes the nightly-cron-as-correctness crutch (keep it as drift insurance only) and takes the lock wait out of the save path.

### [MAJOR] Revocation-by-org-edit can silently land in a browser cookie: the UI's local-save fallback swallows the PUT that was supposed to strip grants
Verified in platform-ui/src/lib/org.ts: persistOrgStructure() falls back to a per-company cookie when the backend PUT throws, and OrgBuilder shows 'Saved locally — will sync when connected' — but getOrgStructure prefers the backend copy when present, so a cookie save made while the backend was flaky is never pushed and is silently shadowed on next load. Under this design, 'move u3 out of d-hr' IS a revocation across three companies (STEP 7a). If that PUT lands in the cookie, the admin sees a success message while u3 keeps hr grants in B and C indefinitely, and no reconcile ever fires. The pre-service-layer risk was cosmetic (org chart drift); the design upgrades it to an access-control gap without mentioning it.
**Fix:** When the company has any active provider-side assignments (cheap: GET assignments?direction=providing is already fetched for the chips), disable the cookie fallback and make save failure loud ('Could not save — access changes NOT applied'). Longer term: delete the cookie fallback entirely now that the backend endpoint is live per the contract ('persists!' — FRONTEND-BFF-CONTRACT.md line 22).

### [MINOR] The v1 lead→hr_manager mapping has no data source: department nodes cannot carry an assignee and both sanitizers strip any 'lead' flag
Verified: OrgBuilder's ASSIGNABLE set is {division, role, person} — a department node (the unit root) cannot have assigneeId; there is no lead marker in OrgNode; and the server sanitizer (company-admin.controller.ts sanitizeStructure) whitelists exactly {id,name,kind,assigneeId,assigneeName,children}, so any new flag is stripped on PUT (the UI sanitizer pair likewise). 'Subtree root's directly-assigned person or a per-unit lead marker gets _manager' is therefore unimplementable as written without touching the blob contract the design promises to leave alone. Impact is bounded — target company_admin still holds manager-level actions, everyone else gets _staff — but the acceptance scenario's 'u1 gets hr_manager' is false in v1.
**Fix:** Put the lead where the design already has relational state: service_assignments.lead_user_id (nullable), chosen in the confirm sheet's dry-run staff list and editable on the assignment row. Reconciler grants _manager to that user, _staff to the rest. Zero blob/sanitizer changes, per-target leads for free.

### [MINOR] Blob node ids are weaker anchors than claimed: sanitizer regenerates missing ids positionally and never enforces uniqueness
sanitizeStructure assigns id = `n-${count}` (a position-dependent counter) to any node missing a string id, and does not deduplicate — a crafted or buggy PUT can carry two nodes with id 'd-hr', making the reconciler's subtree resolution ambiguous (which subtree's staff gets granted?), or silently RETARGET an org_units anchor to a different node that inherited the id. Orphan-freeze semantics cover disappearance but not duplication/retargeting, which changes grants without any banner.
**Fix:** In step 4, harden PUT when the tenant has org_units rows: reject structures with duplicate node ids (422), and treat an anchored node id whose kind changed (department→role) as orphaned rather than resolvable. One tree-walk in the existing sanitize pass.

### [MINOR] Manual-grant vs managed-grant collision on user_roles produces 409s and surprise revocations
Because user_roles is UNIQUE(user_id, role_id, scope_type, scope_id) with no managed_by dimension, an admin manually granting hr_staff@B to a user who already holds the reconciler-managed row gets a 409 from the admin endpoint (managed rows are human-edit-blocked by design); conversely if the manual grant came first the reconciler skips and records nothing (correct), but the asymmetric case — admin WANTS the grant to survive the assignment — has no path: when the assignment is later revoked, the role vanishes even though an admin believed it was independently granted.
**Fix:** Admin grant endpoint, on unique-collision with a managed row: convert it (SET managed_by=NULL) with an audit entry 'converted service grant to manual', instead of 409. The reconciler's claim model from finding 2 then naturally leaves it alone.

### [MINOR] app_current_tenants() helper: keep it inlinable and keep the re-pointing scoped to the six broken tables, or 0025 becomes an all-estate policy churn shared with the sync engine (renumbered from 0023 by WS0-1, 2026-07-22)

New 0026+ policies compose from it; legacy correct policies stay untouched until a quiet window.

## Runners-up (for the record)
### Proposal A: Gaiada Org-Graph-First Architecture: the normalized org chart as the single source of permission topology
Promote the display-only company_org_structure JSONB blob to a first-class relational org graph (org_units, org_placements) plus a cross-tenant edge table (org_service_links: department → served company, module-scoped), and make ALL derived access — company_memberships of kind 'service', module-scoped user_roles grants, and module enablement — a materialized projection of that graph, maintained transactionally by a grant projector that runs on every graph mutation. Data never moves between tenants: an HR department of company A serving B and C operates ON B's and C's own rows (hr_* tables tenant_id = served company), so RLS, sync, rollups, and the outbox keep their immutable-single-tenant_id invariant untouched; what widens is the actor's authorized-tenant-set, which the DB layer (withTenants + CSV GUC) and principal assembly (Principal.companies) already natively support. Cerbos gains one new grant shape (scope_type 'company_module' + scope_module column, matched by a service_operator derived role) and one new dual-tenant RLS policy class for the edge table itself. Drag-and-drop therefore literally rewires access: the projector diffs graph-desired state against managed rows (provenance columns managed_by/source_ref), bumps session_version (D11) on every affected user, and emits per-tenant outbox events — drag-undo is the same recompute converging to the empty set. The legacy JSONB GET/PUT contract survives as a shim assembled from the tables (legacy_node_id preserves the load-bearing 'd-webdev'-style string ids that pm_tasks.assignee.refId references), so the shipped UI keeps working through the whole migration.

### Proposal C: Gaiada Scope-Set Architecture: Computed Authorization over a Flexible Org Graph (Policy-Engine-First)
Authorization becomes a COMPUTED projection, not a stored convention: a Scope Resolver in platform-nest compiles (org placement × service links × legacy role grants) into a materialized `principal_scopes` table — rows of (user, tenant, role, module, org-unit-path) — which feeds both Cerbos (as a `scopes` principal attribute evaluated by new derived roles) and Postgres RLS (via a two-GUC session context: the existing `app.current_tenant_ids` CSV set as the coarse blast wall, plus a new `app.scopes` JSON GUC that slices module-owned tables per tenant). The org chart stays a flexible drag-and-drop graph (the frozen JSONB wire contract is preserved; a normalized `org_units` projection is derived from it transactionally), and cross-company serving is expressed as first-class `org_service_links` edges ("HR dept of A serves B and C for module hr") that the resolver expands into per-user scopes — created by a connect-the-dots drag, revoked by an undo drag, with D11 session bumps making both take effect immediately. Data never moves between tenants (rows stay in the served company; no tenant_id mutation, so sync/HLC/rollups are untouched); what changes on reorg is only the computed scope-set. Existing single-tenant endpoints, the sync engine's GUC contract, and the D5 fail-closed floor are all preserved; multi-company aggregate reads get a NEW, deliberately multi-tenant-safe `/api/scoped/*` surface instead of retrofitting ~100 RLS-reliant queries.
