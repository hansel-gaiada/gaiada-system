# Client Centre — CMC's layout and categorisation as native ERP pages

**Status: PROTOTYPED — DEPLOYED to gda-aicenter in `v1.0.0-alpha.341`** (2026-09-29, release run 36513771830). CMC data IMPORTED 2026-09-29: 28 profiles (600 fields, reconciled exactly against the export), 4 new clients, 32 `cmc-import` activities. Caviar Indonesia is not imported (owner mapped the ERP client "Caviar" to D&A Caviar). Not yet driven end to end by a logged-in user.

## What this is

`cmc.gaiada.com` (the "Company Management Centre", built 2026-09-19 on helios outside git) has a
client-first layout the ERP does not: every client company is a workspace organised by the
departments that serve it (Reservations, Marketing with 19 sub-sections, Accounting, HR, Legal,
Sales, Communication, IT & security, Operations, plus an industry module per business type).
Each section has an overview and a settings page. The settings page holds the setup fields a
specialist needs, drawn from a shared ~150-field registry in 16 groups, and the connections and
data sources for that section, drawn from a ~150-provider registry.

The Client Centre rebuilds that experience **inside the ERP**, on the ERP's login, database,
Cerbos policy and deploy pipeline, for **both** employees and the client's own contacts.

## The registry

`platform-nest/src/modules/clients/centre/registry.json` is the **single source**. A byte-identical copy lives at
`platform-ui/src/lib/clientCentreRegistry.json`, pinned by a parity test. Both were generated by
`scripts/cmc/extract-registry.cjs` from the gitignored CMC snapshot.

| Key | Content |
|---|---|
| `fieldGroups` | 16 group names, in CMC's display order |
| `fields` | 149 fields: `key → {label, type: text\|textarea\|url\|email\|tel…, group, help?}` |
| `connections` | 147 providers: `key → {name, idLabel}` |
| `connectionStatuses` / `connectionMethods` | `Not connected · Connected · Needs attention` / `Manual · Claude connector · API · Zapier / n8n` |
| `businessTypes` | `[{id, label}]` (hotel, restaurant, hospital, spa, agency, services, retail, ecommerce, saas, other) |
| `defaultOffDepartments` | per business type, department ids that start switched off |
| `generalFields` | the Company settings page: `[{title, keys}]` |
| `departments` | 9 departments → pages (`{name}`), or sub-sections (`{id, name, pages}`); 28 section ids in total |
| `industryModules` | per business type, the extra first department (id `ix`) with its pages and settings |
| `sectionSettings` | section id → `{fields: [...], connections: [...]}` (28 entries, one per section) |
| `icons` | CMC's inline SVG per department id |

Semantics carried over from CMC exactly:
- A field value entered on one section's settings page is **the same value everywhere** the field is
  used ("Shared · N" badge = the number of other sections that use it).
- `departments[id]` present → that boolean; absent → on unless listed in `defaultOffDepartments[businessType]`.
- Section list for a client = `[industryModules[businessType]]` (if any) + `departments`.
- Leaf pages are "Coming soon" placeholders in CMC; they stay placeholders (with CMC's copy).

## Data model

```sql
client_centre_profiles (
  tenant_id          uuid NOT NULL REFERENCES companies(id),
  client_id          uuid NOT NULL REFERENCES clients(id),
  business_type      text NOT NULL DEFAULT 'other',
  profile            jsonb NOT NULL DEFAULT '{}',  -- field key -> string
  connections        jsonb NOT NULL DEFAULT '{}',  -- connection key (registry or custom 'x…') -> ConnectionEntry
  departments        jsonb NOT NULL DEFAULT '{}',  -- department id -> boolean
  custom_connections jsonb NOT NULL DEFAULT '{}',  -- section id -> [{id, name}]
  registry_version   int  NOT NULL DEFAULT 1,
  revision           int  NOT NULL DEFAULT 0,      -- +1 per write
  legacy_cmc_id      text,                         -- CMC companies.id this row was imported from
  created_at, updated_at timestamptz, updated_by uuid REFERENCES users(id), origin_site text NOT NULL,
  one row per (tenant_id, client_id)
)
```
Tenant RLS matching `clients`. A missing row means an empty profile: GET synthesises the defaults and
the first PATCH inserts it.

`ConnectionEntry = {tool?, account?, url?, owner?, creds?, method?, status?, notes?}` (all strings).
`creds` is *where* a credential lives ("1Password → Marketing vault"), never the credential.

## API contract (`platform-nest`, clients module, `ModuleEnabledGuard("clients")`)

`CentreProfile`:
```ts
{ clientId: string; clientName: string; clientStatus: string | null;
  businessType: string;
  profile: Record<string, string>;
  connections: Record<string, ConnectionEntry>;
  departments: Record<string, boolean>;
  customConnections: Record<string, { id: string; name: string }[]>;
  revision: number; updatedAt: string | null; updatedBy: { id: string; name: string | null } | null;
  canEdit: boolean }
```
`CentrePatch`, merged key by key (last write wins per key; CMC's autosave sends only what changed):
```ts
{ businessType?: string;                                        // a registry businessTypes id
  profile?: Record<string, string | null>;                      // registry field keys; null or "" DELETES the key
  connections?: Record<string, Partial<ConnectionEntry> | null>;// registry key or an existing custom id; null deletes the entry;
                                                                //   inside an entry, null/"" deletes that sub-key
  departments?: Record<string, boolean | null>;                 // registry department id or "ix"; null = back to default
  customConnections?: Record<string, { id: string; name: string }[]>; // REPLACES that section's list; section must exist;
                                                                //   id /^x[a-z0-9]{4,40}$/, name 1..120
}
```

| Method + path | Authz | Notes |
|---|---|---|
| `GET /api/:t/clients/centre` | `client` read | Every client of the tenant: `[{clientId, clientName, clientStatus, businessType, city, fieldsFilled, connectionsConnected, updatedAt}]` |
| `GET /api/:t/clients/:clientId/centre` | `client` read | `CentreProfile`; `canEdit` = `client` update allowed |
| `PATCH /api/:t/clients/:clientId/centre` | `client` update | returns `CentreProfile` |
| `GET /api/:t/portal/centre` | `portal` read + portal scope | the caller's clients: `[{clientId, clientName, canEdit}]` |
| `GET /api/:t/portal/centre/:clientId` | `portal` read + clientId ∈ scope | `CentreProfile` (404 outside scope, never 403) |
| `PATCH /api/:t/portal/centre/:clientId` | `portal` **edit_company_profile** + clientId ∈ scope + CC-D4 editor check | returns `CentreProfile`; notifies the client's project owners |

Validation (both PATCH routes, one shared function):
- Unknown keys are refused with **400** `{error}` naming the key. Strings are capped at 5,000 characters,
  and the body at 256KB.
- **Credential refusal scans VALUES, not just keys** (CMC-SEC-1 follow-up 3). A value that looks like a
  secret is refused with 400 and the field named: a PEM private-key block, `AKIA…`, `sk-…`, `ghp_`/`github_pat_`,
  `xox[abp]-`, a JWT (`eyJ…​.…​.…`), or `password=`/`pwd:`-style pairs.
- Every accepted write records one activity with `{via: "client-centre" | "portal", changes: [{path, before, after}]}`,
  values truncated to 200 characters. This closes CMC-SEC-1 follow-up 4: CMC logged field names only.
  It also emits `client.centre_updated` in the same transaction.

## UI (`platform-ui`)

- **Staff:** a new sidebar row **Business → Client Centre** (`/client-centre`) directly after Clients.
  `/client-centre` lists every client with business type, city and completion.
  `/client-centre/[clientId]/…` is the CMC layout: a client switcher, an in-page department tree
  (Home · Company settings · departments → sub-sections → pages · Settings), and the content area.
  The client hub (`/clients/[clientId]`) gains a link to it.
- **Client:** a new portal tab **Company** (`/portal/company/…`) with the same components, scoped to
  the caller's client(s), and read-only unless `canEdit`.
- Autosave: debounced ~600ms, sends only the changed keys, shows a "Saved" note, and toasts errors.
- CMC's copy is preserved: ledes, the no-credentials callout, "Shared · N", stats, "Coming soon".

## Data import (CC-D2)

A read-only `pg_dump` of `cmc_app.companies` from helios → matched to ERP `clients` by name, with a hand-reviewed
mapping → an idempotent import keyed on `legacy_cmc_id`. All files are `*.local.*`, and the import runs on the ERP
server only after the owner confirms.
