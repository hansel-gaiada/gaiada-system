## What the owner asked for

A CMS for every piece of the site's content, blog writers included, that also
works as a powerful admin panel. It should have analytics that track every
section, visitor behaviour and preferences, and IP-based tracking. It should be
the main integration point for SEO, AEO and GEO, Google Analytics, Google Ads,
Meta and the company ERP, including the new-client questionnaire.

## The recommendation

**Don't add a second CMS. gaiada.com becomes WebDesk's first internal site (the
v2 §12 P2 "one internal site" proof), and the admin panel is a "Website"
workspace in platform-ui.**

Most of what was asked for already has a home here: WebDesk content and forms,
`agency_leads` with the AD-1 Discovery Intake, the `search` module's Search
Console, GA4 and Google Ads reads, crawler and AI-visibility work, the
`social-media` module, and `mcp-hub`.

A Payload, Strapi or Directus install would duplicate WebDesk and fail the
2026-09-21 no-seat and no-enterprise-tier ruling. Payload SSO needs its
Enterprise tier, which is why D37 is removing Payload.

### Principles carried from the plan

1. **One system of record per data kind:**
   - content in WebDesk;
   - leads and clients in platform-nest;
   - search data in `search`;
   - behaviour data in the analytics store.

   The admin panel shows all of it and copies none of it.
2. **The site stays static.** The CMS is never on a visitor's request path. The
   only live public endpoints are the forms API and the analytics collector.
3. **The CMS edits content, not design.** The bespoke deck components stay in
   the site repo. Their words, numbers, images, order and visibility become
   per-tenant collections.
4. **Stable ids everywhere.** Each page, section, CTA and form has a CMS id that
   analytics, search data and leads all key on.
5. **Consent first.** Raw IPs are never analytics data.
6. **The agentic-native bar applies:** every admin capability is an endpoint and
   an MCP tool with an impact class. Publishing, consent and deletion are
   high-impact.
7. **AI only through `ai-gateway-go`.**
8. **Every new dependency gets a row in the vendor register.**

## ERP-side work, by plan phase

The site-side work (the tracker, consent banner and event list) is done in
gaiada-web-revamp. Everything below is ERP and WebDesk work.

**Phase 0: launch measured.** The site goes live without the CMS.
- **Rule on OQ-5:** unpark Umami. Then deploy it, with one website per
  `search_properties` row; gaiada.com uses the D36 sentinel internal client.
- **Legal:** the website-visitor addendum, drafted for counsel. The site ships a
  consent banner (Google Consent Mode v2, denied by default) with categories
  *analytics* and *marketing*.

**Phase 1: content in the CMS.** This depends on the E0–E3 authoring track and
the P2 proof.
- **Rule:** gaiada.com is the P2 internal proof site, and D37 is ratified.
- **Content model:** per-tenant collections for each bespoke section type. The
  site keeps ~3,900 lines of section copy in `src/config/**`.
- **Long-form collections** for the 315-page package (78 pages shown at launch).
- **Globals:** company, navigation, footer, redirects.
- **A visibility field** on pages and sections: shown / SEO-only / held / hidden.
- **An importer** from the repo's markdown, TypeScript config and JSON.
- **The parity gate:** the CMS-built site must equal the git-built site page for
  page. The site's own build gates (`manifestParity`, `unresolvedTokens`,
  `schemaCoverage`) also run on save in the editor.

**Phase 2: writers' room.**
- **Roles** as Cerbos policies on ERP identities: writer, editor, SEO reviewer,
  translator, publisher. Freelancers get ERP logins.
- **Flow:** brief → draft → review → SEO/AEO check → approve → schedule →
  publish → refresh. Briefs come from `search`.
- **Needs:** the scheduled-publish worker (unwritten) and per-draft preview
  tokens.
- **AI assist** through the gateway, with a human accepting every suggestion.

**Phase 3: leads into the ERP.**
- **Forms:** gaiada.com's 3 forms (contact, audit, onboard) move from Web3Forms
  to the WebDesk forms API. The field ids are a contract, kept equal to the live
  site's.
- **Attribution fields on every submission:**
  - `utm_*`, `gclid`, `gbraid`, `wbraid`, `fbclid`, `_fbp` / `_fbc`;
  - landing page, first and last touch, and sections seen;
  - a submission id, which is also the ad-platform event id for de-duplication.
- **Lead intake:** `form.received` → `wd-zoneb-intake` → `agency_leads`, then
  wa-chat-bot alerts. This needs legal Gate 1.
- **Questionnaire:** `/onboard/` (short, sent by link) seeds the lead, and AD-1
  (122 questions, token link) follows the first call. *Owner to confirm the
  split.*

**Phase 4: close the ad loop.**
- Lead stage + value in platform-nest.
- **Conversion uploads** from `search` when a lead's stage changes:
  - Google Ads click conversions using the gclid, plus enhanced conversions for
    leads using hashed email and phone;
  - the Meta Conversions API, which is blocked on Business Verification (SMM);
  - the LinkedIn Conversions API.

  Every live write is WS4-gated, as `SEARCH_ADS_WRITE_MODE` already is.
- **New connectors:** Google Business Profile (rating, reviews, calls), Bing
  Webmaster plus an IndexNow ping on publish, and an AI-crawler log ingested
  from web server access logs (GPTBot, ClaudeBot, PerplexityBot,
  OAI-SearchBot, Google-Extended).
- **SM-16** AI-visibility panels.

**Phase 5: visitor intelligence.**
- **The enrichment collector:** IP → country/city, network, company and bot
  flag, then the IP is dropped. The vendor review covers the geo and company
  data sources (DB-IP Lite, CC BY 4.0, or MaxMind GeoLite2). Neither is in the
  register.
- **Visitor data:** interest profiles by industry and service viewed, lead
  scoring, and content-decay alerts.
- **Experiments and replay:** A/B tests on blocks, and optional sampled session
  replay for consented visitors only.
- **After that:** offer it to client sites on WebDesk.

**Admin workspace areas (platform-ui "Website"):**
- Overview, Content, Writers' room, SEO & AI search, Analytics.
- Visitors (individual views for consented visitors only), Leads.
- Integrations: health, last sync, and keys held in `integration_connections`.
- Governance: roles, audit, consent versions, retention, data requests.

| Universal Analytics | `UA-238259-61` | Dead since July 2023 and still firing |

**Problems in the live container.** They matter for the ERP because they will
be in the history the `search` module reads.

- **Personal data sent to GA4.** A custom HTML tag scrapes name, message, email
  and phone from the contact form into GA4 event parameters, and the *Leads*
  event sends Email and Phone. Google's terms forbid this.
- **Unrelated cross-domain domains.** The conversion linker carries **~50
  unrelated cross-domain linker domains** (coupon, "adctracksystem", temu-store
  and similar). This looks like a container imported from elsewhere or tampered
  with. **Audit the GTM and Google Ads user lists.**
- **No consent.** There is no consent banner or Consent Mode, and the Meta
  Pixel and Clarity load for every visitor.
- **Bad event names and triggers.** GA4 event names contain spaces ("Click WA",
  "Contact Form Submission"). The triggers depend on WordPress classes
  (`wpcf7-form`, `mc-embedded-subscribe-form`), so the container cannot carry
  over to the Astro site.
- **Wrong WhatsApp number.** The live site's WhatsApp link is
  `wa.me/6281337568977`. The new site uses 0812 3894 471 (owner decision).

The new site drops GTM and carries GA4, both Ads accounts, the Meta Pixel and
Clarity in code, behind consent. The event list lives in gaiada-web-revamp
under `src/config/tracking.ts` and `src/scripts/tracking/` (branch
`feat/tracking`). That list is the contract an Umami or WebDesk collector must
accept later.
