# The AI plan: routing, model use, department context, usage and cost (AIP-*)

**Status: PLANNED.** Nothing in this document is implemented. It is a measured map of what exists, a
proposed design, tickets, and the questions the owner must answer before anything is built.

**Why this plan exists.** The department-workspaces plan (`docs/plans/2026-10-13-department-workspaces.md`,
section 6, DW-D9 and DW-D17) made the AI Assistant one row in every workspace and kept "today's engine,
threads, streaming, proposals, memory, model picker and routing" unchanged. It deferred three things to a
separate AI plan: **model use**, **department context** and **usage and cost**. This is that plan.

**Binding rules this plan works inside.**

- **Only the Gateway holds provider keys** (root `CLAUDE.md`; `ai-gateway-go/CLAUDE.md`). Every choice
  below keeps that true, and Section 1.6 lists the places where today it is not.
- **A chat runs under the chatting user's principal, and threads stay private to their owner**
  (`docs/blueprints/assistant-foundation.md` section 6). Reaching another person's data needs Cerbos.
- **Personas are deferred to late staging, one per department, optional** (owner, 2026-08-03;
  `docs/superpowers/plans/2026-08-03-agentic-native-erp-plan.md`, "Deferred", and the persona item that
  says there are zero personas today). Nothing here needs a persona, and nothing here creates one.
- **No seat defaults to Opus** (`ai-agents/CLAUDE.md`). Model choice is a budget decision.

### 1.2 How routing works now

In [`internal/chain/chain.go`](../../ai-gateway-go/internal/chain/chain.go) and `server.go`:

- **First available, healthy provider in the chain wins.** A failure opens a per-provider circuit breaker
  (default 3 failures, 60 s cooldown) and the next provider is tried. A 429 opens it for the Retry-After window.
- **A caller can send one hint, `provider`**, on both `POST /complete` and `POST /complete/stream`. It only
  **reorders** the chain; an unknown or unavailable name falls through silently (`RunWithHint`).
- **There is no model hint.** Each provider has exactly one fixed model from its environment variable. A caller
  cannot ask for "a cheaper model" or "a stronger model" on the same provider.
- **There is no task hint.** Nothing tells the gateway whether a request is a chat reply, a thread-title, a
  compaction summary, an agent step or a DLP check. Every call is treated the same.
- The chain order and caps can be changed at runtime by the admin console (`PUT /admin/config`,
  [`internal/adminconfig/adminconfig.go`](../../ai-gateway-go/internal/adminconfig/adminconfig.go)); provider
  credentials and the egress allowlist cannot (env and restart only, by design).
- **Safety layers on every call:** fail-closed bearer auth, a DLP scrub of the prompt (card and national-ID
  patterns, [`internal/dlp/`](../../ai-gateway-go/internal/dlp/)), an optional local model classifier
  (`DLP_CLASSIFIER_ENABLED`, off by default), a response-side stream scrubber, a dial-time egress allowlist
  ([`internal/egress/`](../../ai-gateway-go/internal/egress/)), and an egress audit line per request.

### 1.3 What the brain picker does

- UI: [`BrainPicker.tsx`](../../platform-ui/src/components/assistant/BrainPicker.tsx), options in
  `BRAIN_OPTIONS` in [`platform-ui/src/lib/assistant.ts`](../../platform-ui/src/lib/assistant.ts):
  Auto (failover chain), Ollama (local), "Ollama Cloud" (the `openai` slot), Hermes, Gemini, Claude.
- It is **per thread**. The choice is stored as `assistant_threads.brain_provider` and sent as the gateway's
  `provider` hint on every later reply in that thread.
- It is **a hint, never a requirement.** The reply carries a "served by" badge from the gateway's `meta` event,
  which always names the real server.
- **Known mismatch, not a bug in the picker:** the option labelled "Ollama Cloud" is really whatever
  `OPENAI_BASE_URL` points at. Today that is OpenRouter (GLM 5.3 Flash), so the label is wrong on the live
  box. The Gemini and Claude options are inert while their keys are empty, and "Hermes" does nothing unless
  `hermes` is in `LLM_CHAIN` (`BRAIN_OPTIONS` comment and the compose comment). Most of the picker is therefore
  a no-op today.
- The picker is shown to every user who can open the assistant. There is no per-role or per-department limit
  on which brain a person may choose [no limit found in `assistant.controller.ts`].

### 1.5 What department context the assistant gets today

- The prompt is **one string**: a generic system preamble, the thread's rolling summary, the recent transcript,
  the user's **confirmed** memory, and up to a few retrieved knowledge chunks
  ([`assistant/context.ts`](../../platform-nest/src/modules/assistant/context.ts)). The preamble is explicitly
  generic: "no per-department persona".
- **Page context** (ASST-22, `pageContextPrefix`) is a short preamble naming the record the user was looking at.
  The workspaces plan adds a department chip and suggested prompts, and says they "send nothing different to
  the model".
- **Knowledge retrieval** runs as the chatting user: candidates from the store, then DW-D26 filters them with
  the per-record read check as the thread owner, plus public-tier hits
  (`retrieveReadableKnowledge`). So an assistant citation never shows a record the person could not open.
- The knowledge store has an `acl text[]` column and a two-tier `audience` (public website corpus, internal ERP
  records), with tenant as the pre-filter ([`ai-agents/src/knowledge/store.ts`](../../ai-agents/src/knowledge/store.ts),
  [`modules/knowledge/README.md`](../../platform-nest/src/modules/knowledge/README.md)). **There is no department
  dimension**: the filter is the company plus the record-level read check.
- Tools run through the MCP hub as the chatting user, so tool reads are authorized per record by Cerbos already.
- Memory is owner-only. Threads are private to (owner, company).

**So today the assistant knows the company and the person, not the department**, except through what the person
can open.

## 2. Model use and routing

### 2.1 The options

| Option | What it means | For | Against |
|---|---|---|---|
| **A. One fixed default** | Every call uses the first chain provider (today's Auto) | Simplest; already works | The same model answers a title and a hard analysis; cost and quality are both wrong somewhere; no basis for budgets |
| **B. Per-task routing** | The caller names a **task class**; the gateway maps it to a cheap or strong model | The biggest cost saving for the least user effort. Titles, compaction, classification and triage go cheap; reasoning and drafting go strong | Needs a new gateway field and an admin table; needs a few evals so "cheap" is safe |
| **C. Per-department defaults** | Each department gets its own default tier or model | Matches how departments differ (SEO drafting versus HR policy) | Needs a store and an admin screen; premature without usage data; risks a model zoo |
| **D. User choice within limits** | A person picks a tier from a list the company allows | Respects the picker we already have; power users get control | A free choice is a cost lever the user holds; needs an allow-list and, at a cap, a rule |

### 2.2 Recommendation: B first, then a thin D, C only when the data asks for it

1. **Add a task class and a tier to the gateway call, not a model name.** The gateway chooses the model; the
   caller states intent. Proposed classes: `chat`, `summarise` (compaction, titles), `classify` (DLP, triage),
   `agent_step`, `draft`, `embed` (already a separate chain). Proposed tiers: `fast`, `standard`, `strong`.
   An admin table (in the existing runtime-config override file) maps class to tier and tier to
   `provider + model`. Keys still live only in the gateway; the model name is data in that table.
2. **The `provider` hint stays**, unchanged and ranked **above** the tier, so nothing that exists today breaks
   (the contract file says byte-for-byte parity is binding).
3. **The brain picker becomes Auto, Fast, Strong**, plus the named providers for people holding an
   "advanced" grant. This is honest because a named provider that has no key today is a no-op; the picker should
   list only providers the gateway reports as available (`GET /health` already reports them).
4. **Hermes leaves the picker** until it is behind the gateway (Section 1.6, finding 1).
5. **Per-department defaults (C) are deferred.** Decide after two weeks of real usage data from the new ledger
   (Section 4). Until then a department is just a reporting dimension, not a routing one.
6. **The default stays cheap.** The only live model today is GLM 5.3 Flash through OpenRouter. Routing is
   only useful once a second tier exists (an owner decision on keys and models; see question Q1).

**Why this order.** B needs no new UI and no new identity model; it cuts cost from day one, and it produces the
per-task data that D and C would need. It also fits the rule: the gateway chooses, the gateway holds the keys.

**What stays out.** No new model provider, no fine-tune and no local-model eval work here. The model registry
and eval gate in `ai-agents/` (D13) already govern which model may serve a write agent; this plan reuses them
and does not widen them.

## 3. Department context

### 3.1 What "real context" means

The workspaces plan says the department chip and suggested prompts "send nothing different to the model".
This plan changes that, in three layers, each added only when the one before it is proven:

| Layer | What the model sees | Where the data comes from | Who is the principal |
|---|---|---|---|
| **1. Where you are** | One line: the department, the page, the record ("You are helping someone in the SEO department, on the Rankings page") | The workspace registry (`platform-ui/src/lib/workspaces.ts`) and the existing page-context preamble | The chatting user; carries no data, only a label |
| **2. Department knowledge, scoped retrieval** | Knowledge chunks relevant to the question, from the department's own documents first | The knowledge store, filtered by company **and** department scope | The chatting user, through the existing per-record read filter (DW-D26) |
| **3. The person's own scope** | What the person's tools can read: their department's tasks, requests, reports | MCP hub tools, as today | The chatting user, Cerbos per record |

### 3.2 How the department enters retrieval

- Give each knowledge document an optional **department tag** (a new column, or use the existing `acl` scope
  strings, which already express "readable by this scope"; the first is clearer, the second needs no migration.
  See question Q4).
- Retrieval ranks the current department's documents first and still returns company-wide documents; it never
  widens to another department's documents the person could not already open.
- The department's runbooks and SOPs are the first corpus. The `persona/dept-pm/` documents show the shape
  (identity, boundaries, runbooks) but are **not** loaded as a persona; they would be ingested as plain
  knowledge documents tagged `pm`, so no persona is created.
- A per-department **system preamble** (short, owner-editable text in the workspace registry) states the
  department's vocabulary and boundaries. It is plain configuration, not an identity, and it does not
  contradict the deferral of personas: a persona is a `users` row with roles; this is a paragraph.

### 3.3 The authorization line (binding)

1. **A chat runs as the chatting user.** The principal for retrieval and tools is the user's own, never a
   service principal and never the department's.
2. **Department context is a filter that narrows, never an authority that widens.** The model may see a
   department's documents only if the existing record-level read check passes for this user. The department tag
   decides ranking, not access.
3. **Threads stay owner-private.** Department context is assembled per turn and is not stored in a shared place.
   A head reading "the department's AI activity" sees counts and cost (Section 4), never thread text. Reading
   another person's thread remains the separate audited action the blueprint already defines.
4. **Reaching another person's data needs Cerbos.** For example, "summarise my team's overdue requests" is a tool
   call that Cerbos authorizes per record for the asking user. If it is denied, the answer says it could not read
   it; it does not fall back to a broader path. A new capability here (a head asking about a report's work) must
   be a registered tool with its own Cerbos resource, not a prompt trick. An unlisted resource kind is a silent
   deny in this estate, so each new kind is a named ticket.
5. **No cross-person data in a shared prompt.** Compaction summaries and memory are per owner already. A
   department-level "shared memory" is **out of scope** and needs an owner ruling and its own plan.
6. **DLP stays on every call**, and the department preamble and chunks pass through the same scrub.

### 3.4 Agents per department

`ai-agents/` specialists are global today (`specialists.ts`). Per-department agents are a **visibility**
question first (which specialists a department's workspace lists, and which may a person hand work to) and an
**identity** question second (personas, deferred). This plan does the first only: a registry field
"departments this specialist is shown in", so the roster in the Details panel shows relevant agents. No agent
gets its own identity. The eval rule in `ai-agents/CLAUDE.md` still applies: an agent change needs an eval case first.

## 4. Usage and cost

### 4.1 What to meter

One row per gateway call that reaches a provider, written by the **platform**, because only the platform knows
the person, the department and the thread. The gateway reports facts; it does not know people (it only sees the
company header).

| Field | Source |
|---|---|
| Time, company (tenant), user, department (when known) | The caller (platform-nest, ai-agents runner, knowledge, search) passes them; the gateway echoes the ids it was given |
| Capability, task class, tier | The new routing fields (Section 2) |
| Provider and model that served | Already in the gateway's `meta` event |
| Prompt tokens, completion tokens, and **whether real or estimated** | Gateway `usage` event. The live `openai` provider must be taught to report them (ticket AIP-02); until then, labelled estimates, as the assistant already does |
| Cost in USD, and whether it came from the provider or from a price table | OpenRouter returns usage and cost in its responses [UNVERIFIED: not read in the code today]; otherwise a small price table per `provider + model` |
| Outcome (ok, blocked by DLP, blocked by cap, failed over, error) | Gateway, as today in the audit row |
| Source surface (assistant, agent, compaction, knowledge, search, bot) | The caller |

**Never store prompt or answer text in this table.** The egress audit already follows that rule; keep it.

### 4.2 Where it lives

- A new table `ai_usage_events` in the platform database (company-scoped, with row-level security like the
  other tenant tables), append-only, with an index on (company, department, day) and (company, user, day).
  A daily roll-up view feeds the screens.
- **Why not the gateway's JSONL audit:** it has no tenant, user or tokens, it is a file on one box, and it
  restarts empty. It stays as the security record. The new table is the business record.
- **Why not the existing `assistant_threads.total_cost_usd`:** it covers only assistant threads, is never
  written, and misses agents and compaction. The columns can be filled from the new table later, or left.
- **Budget counters move out of memory.** Today the daily call count resets on restart. The cap check should read
  the same durable source (or be seeded from it at boot), so a deploy cannot hand out a fresh allowance.
- The search ledger (`modules/search/providers/ledger.ts`) is the pattern to copy for "incurred" rows: a call
  that was charged but delivered nothing is still recorded.

### 4.3 Who sees what

| Viewer | Sees | Gate |
|---|---|---|
| Any person | Their **own** usage this month: tokens, cost estimate, calls | Own rows only |
| A department head | Their department's totals by day, by surface, by model, and **per-person totals within the department** | The existing head scope (a head is an active position with the `org_unit_lead` role); counts and cost only, never text |
| The owner and the GM | Company-wide, per department and per model; the cap settings | Cerbos on a new resource kind `ai_usage` (a **new kind is six artifacts**, so it is a named ticket) |
| IT, for operations | Provider health, failover rate, cap hits; not per-person cost | Existing monitoring access |

The department head's view is one tab in the workspace (candidate name: "AI usage", next to the other head
views from DW-4), not a new top-level page. Per-person figures inside a department are visible to that head and
the owner only. [Q6 asks whether a person should also see their own rank against peers; the default is no.]

### 4.4 Budgets and caps, and what happens at a cap

| Level | Proposed default | What happens at the cap |
|---|---|---|
| **Gateway global** (exists) | The existing daily call cap, durable | 429 "degraded until tomorrow" (today's behaviour). Keep, and show it in the UI as a clear message, not an error |
| **Company** | A monthly USD budget set by the owner | At 80 percent: a notice to the owner and the GM. At 100 percent: **soft stop** (below) |
| **Department** | A monthly USD budget, default "none" (report only) | At 80 percent: a notice to the head. At 100 percent: the same soft stop for that department, which the head or the owner can lift |
| **Person** | A daily message allowance, default generous | At the allowance: a friendly "you have used today's allowance" with the reset time; the owner can raise it per person |

**Soft stop, not a wall.** At a cap the assistant **downshifts** instead of failing: the tier drops to `fast`
(the cheapest), long-context features such as large knowledge retrieval are trimmed, and agent runs are
queued for approval rather than started. Only at the hard company cap does it return the gateway's degraded
message. A DR-burst override already exists in the gateway (`POST /admin/dr-mode`) and stays the owner's only
way to lift the hard cap.

**Cost runaway guards** (apply regardless of budgets): a per-request maximum prompt size, a maximum number of
agent steps per run (exists), and an alert when one person or one agent exceeds, say, five times their own daily
average. The alert goes to IT and the owner.

## 5. Knowledge, AI Agents and The Office: where they live

Per the workspaces plan (the mapping table near line 1287, DW-D17), they sit under **Company** for now:
**Company > Knowledge**, **Company > AI Agents**, **Company > The Office** (rows in `platform-ui/src/lib/workspaces.ts`,
lines ~1154 to 1157). This plan keeps that, and adds only what it needs.

| Item | After this plan | Why |
|---|---|---|
| **AI Assistant** | Stays a row in every workspace (DW-D9). Gains the department chip's real context (Section 3), the tier picker, and a small "your usage" line in the Details panel | The one place a person talks to AI |
| **Knowledge** | Stays in **Company** as the library. Gains the department tag on documents and a "show this department's documents" filter. Each workspace gets **no new row**; its AI Assistant reads the department's slice | Moving it into every workspace would create ten copies of one library |
| **AI Agents** | Stays in **Company** (run history, approvals). The Assistant's Details panel shows the agents relevant to the current department. A department row is **not** added now | Per-department agents are a visibility field first (Section 3.4) |
| **The Office** | Stays in **Company**, unchanged. It is a presence view, not an AI control surface | Nothing in this plan needs it to move |
| **AI usage** | A tab in each head's workspace (department totals) and a Company-level view for the owner and the GM | Section 4.3 |

When per-department agents or knowledge prove their worth (a measured rise in use), a later revision of the
workspaces plan can promote one of them to a workspace row. That is an owner decision, not part of this plan.

## 6. Phased tickets

Sizes: **S** = under half a day, **M** = about a day, **L** = two to three days. Seats follow the house rule:
Haiku for mechanical, exactly specified work; Sonnet for most implementation; Opus only where judgement is

the server, never local).

## 8. Risks

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | **A provider outside the gateway** (Hermes naming Gemini; a second gateway in `wa-chat-bot`) bypasses DLP, the cap and the audit | Medium (the configs are in the repo; live state UNVERIFIED) | High | Phase 0 first. Add a CI check that fails if any service outside `ai-gateway-go` imports a provider SDK or reads a provider key variable |
| R2 | **Cost runaway**, for example a looping agent or a long chat on the strong tier | Medium | Medium to High | Per-run step budgets (exist), per-person allowance, per-department budget with soft stop, the runaway alert, and the global call cap made durable (today a restart resets it) |
| R3 | **Estimates presented as measurements.** Live assistant tokens are a 4-characters estimate today | High until AIP-02 | Medium (wrong cost views) | Store the source (`provider`, `estimate`, `table`) on every row and show the label in the UI |
| R4 | **Cross-person data in context** (department retrieval or a head's question exposing a record the user cannot open) | Low if the record filter stays in front | High | Department tag ranks and never grants. Adversarial test in AIP-12. A head's question about others goes through a registered tool and Cerbos per record |
| R5 | **Cheap-tier regressions** (a weak model writes a poor title or summary and the user blames the product) | Medium | Low to Medium | AIP-09 eval before `fast` becomes the default for any task; a per-company flag to turn routing off |
| R6 | **The usage table becomes a surveillance tool** (per-person counts used against staff) | Medium | Medium | Counts and cost only, never text; per-person view limited to the head and the owner (Q6); documented in the privacy notice |
| R7 | **A new Cerbos resource kind is a silent deny** if one of the six artifacts is missing | Medium | Medium | AIP-15 is a named Opus ticket with a test that proves allow and deny for each role |
| R8 | **Personas stay deferred** (owner, 2026-08-03) while department context grows, tempting a shortcut | Medium | Medium | This plan adds a preamble and a roster filter only; no `users` row, no roles, no identity. Personas are AIP-22, late staging, optional |
| R9 | **The gateway contract drifts.** Five services call `/complete`; a changed field breaks them all | Low | High | AIP-06's new fields are optional; absent means today's behaviour byte for byte; the gateway keeps its contract tests |
| R10 | **Single live provider.** One OpenRouter model is the whole estate's brain, a shared dependency with latency and rate limits | High (measured in the compose comments) | Medium | Routing helps only with a second tier (Q1); the `echo` fallback is alerted (`GatewayServedByEcho`) |
